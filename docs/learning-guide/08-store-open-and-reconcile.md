# 8. Opening SQLite, the write check, and startup reconciliation

Files: [internal/store/sqlite.go](../../internal/store/sqlite.go), [internal/store/writable.go](../../internal/store/writable.go), [internal/store/run_interruptions.go](../../internal/store/run_interruptions.go)

Revision: commit 1c4786e

## Role in the system

These three files are the startup half of the `store` package. Chapter 3 showed `runServer` calling them in a fixed order right after it takes the database lock: `store.Open` at `cmd/server/main.go:75`, `store.CheckWritable` at `main.go:88`, and `store.MarkUnfinishedRunsInterrupted` at `main.go:96`. Each runs exactly once per process, on the main goroutine, before the runner exists (`main.go:107`) and before the HTTP listener starts (`main.go:129`). Together they answer three questions in sequence. Is this file a Patchbay database that this build may use, with the current tables? (`Open`, which hands identity checks and migrations to `migrate` at `internal/store/schema.go:56`.) Can this process actually commit a write to it? (`CheckWritable`.) What does saved history say was in progress when the previous process died, and how should that be relabelled so nobody mistakes it for live work? (`MarkUnfinishedRunsInterrupted`.)

Data comes in as a file path from the `-db` flag (`main.go:32`) and as the signal context `stop` (`main.go:38`), wrapped in a five-second deadline for the second and third calls (`main.go:87`, `main.go:95`). Data goes out as one `*sql.DB` value and as rewritten rows. The `*sql.DB` is the only handle the rest of the program ever gets to SQLite: the runner's save closures capture it (`main.go:107-111`) and call `store.CreateRun` and `store.UpdateRun` (`internal/store/runs.go:17`, `runs.go:68`); the API captures it (`main.go:123`) and calls `store.ListRuns` and `store.GetRun` (`internal/httpapi/api.go:92`, `api.go:107`). The rewritten rows are the `queued` and `running` runs, and their `running` and `pending` steps, that a crash left behind. After reconciliation they read `interrupted` and `skipped`, which the browser shows as **Interrupted**, **Skipped**, and **Finish time unknown** (`web/src/format.ts:9`, `format.ts:11`, `format.ts:101`).

On the path from a browser click to a saved run, these files sit before the click. A click reaches `runner.Start` (`api.go:65`), which saves the new run through the closure at `main.go:107-109` using the `db` that `Open` returned. If `Open` refused the file, or the write check failed, or reconciliation failed, that handler never exists, because `runServer` returned an error first (`main.go:76-78`, `main.go:90-92`, `main.go:98-100`). That ordering is a stated rule: "After opening and recognizing the database, commit a bounded write check before interruption cleanup or HTTP startup" (`AGENTS.md:110-111`). The server finds out that saves cannot work before it promises the browser that they will.

## Concepts you need

- **Package doc comments.** A comment directly above `package store` that starts with "Package store ..." is the package's documentation. `go doc` and pkg.go.dev show it. Only one file in a package needs it; `sqlite.go:1` carries it for the whole `store` package, so `writable.go` and `run_interruptions.go` start with a bare `package store`. [Go Doc Comments](https://go.dev/doc/comment)
- **Blank imports and driver registration.** `import _ "modernc.org/sqlite"` compiles the package into the binary and runs its `init` function, which calls `sql.Register("sqlite", ...)`. Nothing else in the file names that package. Later, `sql.Open("sqlite", ...)` finds the driver by that registered name. This is how `database/sql` stays independent of any particular database engine. Chapter 3 saw the same idiom with `time/tzdata` (`cmd/server/main.go:17`). [database/sql.Register](https://pkg.go.dev/database/sql#Register), [modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite)
- **`*sql.DB` is a pool, not a connection.** `sql.Open` returns a handle that opens real connections lazily and reuses them. It is safe to share between goroutines. `SetMaxOpenConns(1)` makes the pool hold at most one connection, so every statement in the program takes turns on it, and a caller that wants it while another holds it waits inside the pool. [database/sql.DB](https://pkg.go.dev/database/sql#DB), [DB.SetMaxOpenConns](https://pkg.go.dev/database/sql#DB.SetMaxOpenConns), [Go wiki: SQLInterface](https://go.dev/wiki/SQLInterface)
- **`sql.Open` is lazy; `PingContext` is the real test.** `sql.Open` only checks that the driver name is registered and that the connection string parses. It does not touch the file. `PingContext` forces one connection to open, which is where a missing file or a bad path is reported. [database/sql.Open](https://pkg.go.dev/database/sql#Open), [DB.PingContext](https://pkg.go.dev/database/sql#DB.PingContext)
- **Contexts inside `database/sql`.** Every method ending in `Context` stops early when its context is canceled or past its deadline: while waiting for a free connection, while a statement runs, and for `BeginTx`, until the transaction ends. If the context ends before `Commit`, the package rolls the transaction back for you. `ctx.Err()` returns `nil` while a context is still live, and `context.Canceled` or `context.DeadlineExceeded` once it is not. [DB.BeginTx](https://pkg.go.dev/database/sql#DB.BeginTx), [context](https://pkg.go.dev/context)
- **Transactions: `BeginTx`, `Tx.ExecContext`, `Commit`, and `defer tx.Rollback()`.** A transaction groups statements so they all become visible at once or not at all. `BeginTx(ctx, nil)` starts one with default options. The idiom `defer tx.Rollback()` right after `BeginTx` means every early `return` undoes the partial work. After a successful `Commit`, the deferred `Rollback` returns `sql.ErrTxDone` and does nothing, which is why its return value is ignored. [Tx.Rollback](https://pkg.go.dev/database/sql#Tx.Rollback), [Tx.Commit](https://pkg.go.dev/database/sql#Tx.Commit)
- **`sql.Result` and `RowsAffected`.** `ExecContext` returns a `Result`, from which `RowsAffected()` reports how many rows the statement changed. It can itself fail, so it returns `(int64, error)`. [database/sql.Result](https://pkg.go.dev/database/sql#Result)
- **`os.OpenFile`, `O_EXCL`, octal modes, and umask.** `os.O_RDWR|os.O_CREATE|os.O_EXCL` means "create for read and write, and fail if anything already exists at this path". With `O_EXCL`, the kernel refuses even when the path is a symbolic link, dangling or not. `0o600` is an octal literal: owner read and write, nobody else. The process umask can only remove bits from that mode, never add them. [os.OpenFile](https://pkg.go.dev/os#OpenFile), [open(2)](https://man7.org/linux/man-pages/man2/open.2.html), [umask(2)](https://man7.org/linux/man-pages/man2/umask.2.html)
- **`errors.Is`, `%w`, and `os.ErrExist`.** `fmt.Errorf("...: %w", err)` wraps an error so callers can still recognize what is inside. `errors.Is(err, os.ErrExist)` walks the chain and reports whether the failure was "file exists", however many layers wrapped it. Every error these files return is wrapped with a short verb phrase, so a startup log line reads like a stack of causes. [errors.Is](https://pkg.go.dev/errors#Is), [fmt.Errorf](https://pkg.go.dev/fmt#Errorf), [os.ErrExist](https://pkg.go.dev/os#pkg-variables)
- **`if err := f(); err != nil` and shadowing.** An `if` may begin with a short statement. A variable declared there lives only inside the `if`, and `:=` creates a new variable even when an outer one has the same name. `sqlite.go:36` relies on this: its inner `err` is a fresh variable, and the outer `err` from L34 stays `nil`. [Spec: Declarations and scope](https://go.dev/ref/spec#Declarations_and_scope)
- **Building a connection string with `net/url`.** A `url.URL` struct value with `Scheme` and `Path` set turns into text with `.String()`, which percent-encodes characters that would otherwise change the URL's meaning. `url.Values` is `map[string][]string`; `Set` replaces a key's values, `Add` appends one more, and `Encode` produces `key=value&key=value` text. [net/url.URL](https://pkg.go.dev/net/url#URL), [net/url.Values](https://pkg.go.dev/net/url#Values)
- **SQLite URI filenames and `mode=rw`.** SQLite accepts `file:` URIs as database names. The `mode` query parameter chooses `ro` (read only), `rw` (read and write, but never create), or `rwc` (create if missing). `rw` is the "existing-file mode" that the README and `AGENTS.md` refer to. [SQLite: URI filenames](https://sqlite.org/uri.html)
- **SQLite pragmas.** A `PRAGMA` is a SQLite-specific statement that reads or sets an engine setting. `foreign_keys` and `busy_timeout` are per-connection settings and reset on every new connection. `user_version` and `application_id` are two integers stored in the database file's header, so they persist. Patchbay uses `user_version` for its migration number and `application_id` for its "this is a Patchbay file" marker. [SQLite: PRAGMA](https://sqlite.org/pragma.html), [foreign_keys](https://sqlite.org/pragma.html#pragma_foreign_keys), [busy_timeout](https://sqlite.org/pragma.html#pragma_busy_timeout), [user_version](https://sqlite.org/pragma.html#pragma_user_version), [application_id](https://sqlite.org/pragma.html#pragma_application_id)
- **Autocommit, explicit transactions, and the rollback journal.** Outside an explicit `BEGIN`, SQLite runs each statement as its own tiny transaction and commits it immediately; this is autocommit. Any commit that changes a page first writes a journal file beside the database, then the page, then deletes the journal. So a commit needs write permission on the directory, not only on the file. [SQLite: Transactions](https://sqlite.org/lang_transaction.html), [SQLite: Atomic commit](https://sqlite.org/atomiccommit.html)
- **`fmt.Sprintf` into SQL versus `?` placeholders.** Normally values go into SQL through `?` placeholders, as `runs.go:29-33` does, so user data can never change the statement's shape. A `PRAGMA` takes its value as literal text, not as a bound parameter, so `writable.go:17` formats the value in with `Sprintf`. That is safe only because `schemaVersion` is a compile-time integer constant. [fmt.Sprintf](https://pkg.go.dev/fmt#Sprintf)
- **Package-level constants across files.** `const schemaVersion = 3` lives in `schema.go:9`, yet `writable.go:17` uses it without an import, because every file in a directory with the same `package` clause shares one namespace. [A Tour of Go: Constants](https://go.dev/tour/basics/15)
- **Raw string literals for SQL.** Text between backticks can span lines and contains no escape sequences, so multi-line SQL can be written as it would be typed into a SQLite shell. [Spec: String literals](https://go.dev/ref/spec#String_literals)
- **SQL `CASE` expressions and subqueries in `UPDATE`.** `CASE status WHEN 'running' THEN 'interrupted' ELSE 'skipped' END` picks a new value per row. `WHERE run_id IN (SELECT id FROM runs WHERE ...)` filters one table's rows by a condition on another table. [SQLite: CASE](https://sqlite.org/lang_expr.html#the_case_expression), [SQLite: UPDATE](https://sqlite.org/lang_update.html)
- **Multiple return values.** A Go function can return several values; `(int64, error)` is the convention for "a number, or a reason there is none". Callers write `count, err := f()`. [A Tour of Go: Multiple results](https://go.dev/tour/basics/6)
- **`filepath.Abs` and `filepath.ToSlash`.** `Abs` turns a relative path into an absolute, cleaned one using the current working directory. `ToSlash` replaces the operating system's path separator with `/`; on Linux and macOS it changes nothing, on Windows it turns backslashes into slashes. [path/filepath.Abs](https://pkg.go.dev/path/filepath#Abs), [path/filepath.ToSlash](https://pkg.go.dev/path/filepath#ToSlash)

## Walkthrough

### internal/store/sqlite.go

**L1–L2** — The package doc comment and `package store`. Line 1 is the documentation for the entire `store` package: "SQLite access for persistent application data". Everything under `internal/store/` shares this clause and this one-line promise. The roadmap fixes the storage decision this package implements: "SQLite through `database/sql`, explicit SQL queries, and versioned migrations" (`docs/roadmap.md:84`).

**L3–L3** — Blank line.

**L4–L12** — Standard library imports. `context` for the cancellation parameter, `database/sql` for `*sql.DB`, `errors` for `errors.Is` at L39, `fmt` for wrapping every error, `net/url` for the connection string at L44-52, `os` for `os.OpenFile` and `os.ErrExist`, and `path/filepath` for `Abs` and `ToSlash`. Go refuses to compile an unused import, so this list is a true inventory of what the file does.

**L13–L14** — The blank import of the SQLite driver and the closing parenthesis. The comment says why: it registers the pure-Go `"sqlite"` driver with `database/sql`. The module is pinned at `go.mod:7` (`modernc.org/sqlite v1.58.0`). "Pure-Go" matters for packaging: the Docker build compiles with `CGO_ENABLED=0`, which a C-based SQLite driver could not survive (`README.md:496-497`). Without this line, `sql.Open("sqlite", ...)` at L54 would fail with `sql: unknown driver "sqlite"`.

**L15–L15** — Blank line.

**L16–L19** — The doc comment for `Open`. It states the contract in four sentences: the function opens or creates, verifies identity, and migrates; the parent directory must exist; new files get mode `0600` before umask while existing files and directories keep their permissions; and the caller owns the returned database and must close it. The permission sentence restates the rule "Create new database files with mode `0600` before SQLite opens them ... Preserve existing file and directory permissions" (`AGENTS.md:108-109`) and the README's promise at `README.md:86-89`. The ownership sentence is honoured by the deferred `db.Close()` at `cmd/server/main.go:80-84`.

**L20–L20** — `func Open(ctx context.Context, path string) (*sql.DB, error)`. Context first, as in every Go function that can block. The caller passes `stop`, the signal context from `cmd/server/main.go:38`, so an operator who presses Ctrl+C during a slow startup is honoured. Every test in this package goes through this function too, for example `internal/store/sqlite_test.go:12` and `runs_test.go:18`.

**L21–L23** — Reject an empty path at once. Without this guard, `filepath.Abs("")` at L24 would quietly turn the empty string into the current working directory, L34 would see that directory as an existing file, and the failure would only surface at L63 as a less clear SQLite error about opening a directory. `lockDatabase` has the identical guard (`cmd/server/database_lock.go:19-21`), so in the server this branch is unreachable, but the store package is used on its own by tests (`sqlite_test.go:54`) and must not depend on the caller.

**L24–L27** — Resolve the path to an absolute, cleaned one. Two reasons: the `file:` URI built at L44 needs an absolute path to be unambiguous, and the error messages elsewhere are easier to act on. `filepath.Abs` fails only if the working directory cannot be read, so the wrapped `resolve database path` error is rare. Note that, unlike `database_lock.go:29-43`, this does not resolve symlinks. The lock must map every alias to one lock file; `Open` can simply hand the name to SQLite, which follows symlinks the normal way.

**L28–L30** — Stop if the context is already done. This sits deliberately before L34, the line that creates a file. A startup that was interrupted before it got here must not leave a brand new, empty `.db` on disk. `TestOpenWithCanceledContextDoesNotCreateDatabase` (`internal/store/sqlite_permissions_test.go:145-159`) proves both halves: the error satisfies `errors.Is(err, context.Canceled)` and the path does not exist afterwards. The later `PingContext` and `migrate` calls would also notice cancellation, but by then the file would exist.

**L31–L31** — Blank line.

**L32–L33** — The comment that explains the next nine lines. Patchbay creates the file itself, privately, before SQLite ever sees it, and `O_EXCL` guarantees that an existing file (or a symlink, including one pointing nowhere) is left exactly as it is. "Never truncate or chmod them here" is the promise that reopening an older, more permissive database does not silently tighten or loosen it (`README.md:88-89`).

**L34–L34** — `os.OpenFile(absolute, os.O_RDWR|os.O_CREATE|os.O_EXCL, 0o600)`. Three flags combined with bitwise OR: open for reading and writing, create if missing, and fail if something is already there. The mode `0o600` applies only when the file is created, minus the umask, so the file is never more open than owner-only. This is the line that implements "Create new database files with mode `0600` before SQLite opens them" (`AGENTS.md:108`). `TestOpenCreatesPrivateDatabase` (`sqlite_permissions_test.go:16-49`) runs this in a child process with umask cleared and asserts `0600` on the file and an untouched `0755` on the directory. Without `O_EXCL`, a dangling symlink at this path would be followed and its target created, which `TestOpenDoesNotCreateThroughDanglingDatabaseSymlink` (`sqlite_permissions_test.go:123-143`) forbids.

**L35–L38** — If the create succeeded, close the file immediately. The only purpose of L34 was to make the inode with the right mode; SQLite will open it on its own at L63. The inner `err :=` is a new variable scoped to this `if`, so the outer `err` (which is `nil` here) is not touched. A failed close on a just-created empty file is nearly impossible, but it is still reported rather than swallowed, because an unreported error here would mean SQLite opens a file the program does not fully understand.

**L39–L41** — The other outcome of L34. `errors.Is(err, os.ErrExist)` means "the file already exists", which is the normal case on every restart and is not an error: the branch does nothing and execution continues to L44. Any other error (parent directory missing, permission denied) is fatal and wrapped as `create database file`. `TestOpenRejectsUnavailablePaths` (`sqlite_test.go:52-70`, case "missing parent") lands here. Note the consequence for a half-finished first start: the empty `0600` file created at L34 stays on disk if a later step fails. The README says so (`README.md:91-92`), and it is harmless because an empty file is exactly what `migrate` accepts as "empty and unmarked" next time (`schema.go:76-83`).

**L42–L42** — Blank line.

**L43–L44** — Build the `file:` URI as a `url.URL` value rather than by string concatenation. The comment says why: a path containing `?` or `#` must stay part of the filename. In a hand-built string, `?` would start the query section and `#` a fragment, and SQLite would open a different file. `TestOpenPersistsAcrossReopen` uses the filename `history ?#.db` (`sqlite_test.go:11`) for precisely this reason. `filepath.ToSlash` replaces backslashes with slashes for the URI on Windows, where `Abs` returns them; on Linux and macOS it changes nothing.

**L45–L45** — An empty `url.Values` to collect query parameters. It is a map from key to a list of values, which is what lets one key (`_pragma`) carry two entries at L50-51.

**L46–L48** — Set `mode=rw`. Read and write, but never create. The comment gives two reasons. First, `database/sql` may open a fresh connection at any later time (after an error, for example), and that reopen must not quietly recreate a database that an operator removed. Second, if the configured path is a symlink whose target has gone, SQLite must refuse rather than create the target. L34 already failed with `ErrExist` for that symlink, so this parameter is the only thing standing between a dangling link and a surprise new file. This is "keep SQLite in existing-file mode" (`AGENTS.md:109`) and `README.md:90-91`. The dangling-symlink test at `sqlite_permissions_test.go:123-143` checks the error and that the target still does not exist.

**L49–L51** — Two `_pragma` parameters, added with `Add` so both survive. The comment states the driver's behaviour: these pragmas are applied whenever the driver opens a new connection, so they cannot be lost on a reconnect. `foreign_keys(1)` switches on foreign key enforcement, which SQLite leaves off by default; the schema relies on it for `run_steps.run_id ... REFERENCES runs(id) ON DELETE CASCADE` (`schema.go:29`). `busy_timeout(5000)` makes SQLite retry for up to five seconds when another process holds the file lock before returning `database is locked`, which the README describes at `README.md:493-494`. Without `foreign_keys(1)`, a step row for a nonexistent run would be accepted silently; without `busy_timeout`, a `sqlite3` shell left open in a transaction would make the next save fail at once.

**L52–L52** — `dsn.RawQuery = options.Encode()`. `Encode` sorts the keys and percent-encodes the values (the parentheses become `%28` and `%29`), and `url.URL.String()` at L54 assembles `file:///abs/path?_pragma=...&_pragma=...&mode=rw`. The driver decodes it again.

**L53–L53** — Blank line.

**L54–L57** — `sql.Open("sqlite", dsn.String())`. The first argument is the name registered by the blank import at L13. This call is lazy: it validates the driver name and the connection string and returns a pool with zero connections. Its error path is therefore about configuration (an unknown driver), not about the file. The wrapped message `open database` is reused by `main.go:77`, which prefixes it with the path.

**L58–L60** — Limit the pool to one open connection and keep that one idle rather than closing it. The comment states the intent: database access stays serialized. With one connection, SQLite never has to arbitrate between two of Patchbay's own connections, and every goroutine that wants the database waits in Go's pool, where that wait respects the caller's context (`internal/store/writable_test.go:141-152` depends on this). Keeping the single connection idle means per-connection settings survive between statements: the write-check test can set `query_only` on it knowing the check will see the same connection (`writable_test.go:119-122`). (The pragmas at L50-51 do not depend on this; the driver reapplies them on every new connection.) The roadmap asked for "a deliberate connection policy" (`docs/roadmap.md:93`); this is it, and the README documents it at `README.md:493`.

**L61–L61** — Blank line.

**L62–L66** — `db.PingContext(ctx)`: open one real connection now, so a bad path is reported here and not on the first save. For a missing file or a dangling symlink, this is where `mode=rw` bites, and the error is wrapped as `connect to database`. On failure the pool is closed before returning; the `Close` error is deliberately ignored because the ping error is the one the operator needs. The dangling-symlink test (`sqlite_permissions_test.go:123-143`) is the one that lands here. A file whose contents are not SQLite is not caught here: SQLite opens the file without validating its header and only reads it on the first transaction, so `TestRunServerReleasesDatabaseLockAfterOpenFailure` (`cmd/server/main_test.go:184-198`), which feeds a text file in place of a database, fails inside `migrate` at L67 instead; it asserts only that `runServer` reports `open database` and that the lock is free afterwards.

**L67–L70** — `migrate(ctx, db)` (`schema.go:56-118`). In one transaction it reads `application_id` and `user_version`, refuses a foreign or unsupported file, recognizes legacy layouts, applies the migrations up to version 3, and marks the file as Patchbay's. Chapter 9 covers that file. Here the point is the order: identity verification and migration happen inside `Open`, which `runServer` calls only after `lockDatabase` succeeded (`main.go:66`, `main.go:75`). That satisfies "Take the database ownership lock before migrations or interruption cleanup" (`AGENTS.md:95`) and "Verify database identity before migration or startup cleanup" (`AGENTS.md:105`). A migration failure closes the pool and returns `migrate`'s own already-wrapped error unchanged, so messages such as `refuse database belonging to another application` reach the log intact (`schema.go:68`).

**L71–L72** — Return the open, verified, migrated handle, and the closing brace. From here on the caller owns `db`. In the server that ownership is the deferred `db.Close()` at `main.go:80-84`, registered after the lock's defer so that it runs before the lock is released, and before the `runner.Close` defer at `main.go:115` so that it runs after the runner has stopped and no run goroutine is still writing (`AGENTS.md:96`).

### internal/store/writable.go

**L1–L1** — `package store`. No doc comment: `sqlite.go:1` already documents the package.

**L2–L2** — Blank line.

**L3–L7** — Imports: `context` for the parameter, `database/sql` for `*sql.DB`, `fmt` for `Sprintf` and `Errorf`. Nothing else is needed; the whole file is one statement.

**L8–L8** — Blank line.

**L9–L11** — The doc comment. Three facts. The check "commits a small write without changing schema or run history", which is the whole design constraint: it must be a real commit, yet leave `user_version`, `application_id`, the tables, and every run row exactly as they were. It is to be called "after Open succeeds, while holding database ownership and before starting the runner", which is the position `runServer` gives it (`main.go:86-92`, between L75 and L107). And "the caller supplies a context deadline for the entire check", which `runServer` does with `context.WithTimeout(ctx, 5*time.Second)` at `main.go:87`; the function adds no timeout of its own.

**L12–L12** — `func CheckWritable(ctx context.Context, db *sql.DB) error`. The only caller outside tests is `main.go:88`. Tests call it at `writable_test.go:56`, `:124`, `:138`, `:150`, and `:156`.

**L13–L16** — Four comment lines that justify the single statement below, and they deserve reading twice. L13-14: writing `user_version` marks the database header page dirty even when the new value equals the old one, so SQLite must run its full journal-and-commit sequence. That is what makes this a real write check on an empty database with no run rows to update. L15-16: the write is one autocommit statement instead of `BeginTx` plus `Commit` because, as the author notes, this driver's `sql.Tx.Commit` runs with a background context. In other words, if the check used an explicit transaction, the commit (the part that actually touches the journal and the disk) would not be bounded by the caller's five-second deadline. With a single statement, `ExecContext` owns the whole commit under `ctx`. `TestCheckWritableHonorsContext` (`writable_test.go:130-159`) pins this: a canceled context yields `context.Canceled`, and a 20 millisecond deadline while another caller holds the only connection yields `context.DeadlineExceeded`.

**L17–L19** — The statement: `PRAGMA main.user_version = <schemaVersion>` through `db.ExecContext(ctx, ...)`, with failure wrapped as `commit database write check`. `main.` names the primary database explicitly. The value is `schemaVersion` from `schema.go:9`, the number `migrate` just left in the header, so a successful check changes nothing observable; `TestCheckWritableCommitsWithoutChangingSchemaOrHistory` (`writable_test.go:12-106`) proves the commit happened by watching `PRAGMA data_version` change on a second connection, then reopens the file and asserts the version, the marker, the stored schema text, and the run and step counts are unchanged. `Sprintf` is used because a pragma cannot take a `?` parameter; `schema.go:110` does the same for `application_id`. What this catches that `Open` cannot: `migrate` commits nothing for a current, marked database (`schema.go:87-89`), so `Open` succeeds even when the directory forbids creating the rollback journal. `TestRunServerRejectsUnwritableJournalDirectoryBeforeCleanup` (`cmd/server/database_write_test.go:21-126`) builds exactly that situation with a `0555` directory and a writable `0600` file, and asserts that startup stops with `check database writeability` before reconciliation and before any listener, in both the empty-history and unfinished-history cases. The README documents the message and the cleanup at `README.md:499-511`.

**L20–L21** — Return `nil` on success, and the closing brace. There is no second check and no retry. The README is explicit that this is a one-time confirmation, not a guarantee: "It does not reserve space for future runs or guarantee later writes will succeed; runtime save failures retain their existing handling" (`README.md:509-511`), which echoes "a successful startup check does not guarantee future writes" (`AGENTS.md:112`).

### internal/store/run_interruptions.go

**L1–L1** — `package store`.

**L2–L2** — Blank line.

**L3–L7** — Imports: `context`, `database/sql`, and `fmt`. The same three as `writable.go`; this file needs nothing from the engine or workflow packages because it works on status strings in SQL.

**L8–L8** — Blank line.

**L9–L14** — The doc comment, which is the specification for the two `UPDATE` statements below. Runs that are `queued` or `running` become `interrupted`; their `running` steps become `interrupted` and their `pending` steps become `skipped`. "All existing results and timestamps are preserved: a missing finish time stays unknown" rules out inventing a `finished_at`, which is why the frontend prints **Finish time unknown** for these runs (`web/src/format.ts:101`) instead of a duration. "Call only at startup before any runner uses this database" is the ownership condition: this function rewrites rows that a live runner would otherwise own. "This changes saved history and does not stop executors or resume work" is the rule "Startup marks leftover queued/running records interrupted; it does not resume actions" (`AGENTS.md:98-99`) and the roadmap's position at `docs/roadmap.md:128`. The last sentence defines the return value: a count, or zero when the transaction failed.

**L15–L15** — `func MarkUnfinishedRunsInterrupted(ctx context.Context, db *sql.DB) (int64, error)`. Called once from `main.go:96` with a five-second deadline derived from the signal context (`main.go:95`), after the write check and before `engine.New` (`main.go:107`). `int64` matches what `RowsAffected` returns at L36.

**L16–L19** — Begin a transaction. `nil` options means default isolation and read-write. The transaction is the reason this function can promise "steps and runs change together": the step update at L24 and the run update at L31 commit as one unit or not at all. `TestMarkUnfinishedRunsInterruptedRollsBackStepChanges` (`internal/store/run_interruptions_test.go:75-98`) installs a trigger that rejects the run update after the step update has already executed, and asserts that the stored run is byte-for-byte what it was. A canceled context fails here with `begin run interruption` wrapping `context.Canceled`, which `TestMarkUnfinishedRunsInterruptedHonorsCancellation` (`run_interruptions_test.go:100-116`) checks along with "no rows changed".

**L20–L20** — `defer tx.Rollback()`. The same idiom as `runs.go:27`, `runs.go:73`, and `schema.go:61`. Every `return 0, err` below leaves through this line, so the partially updated steps are undone. After the `Commit` at L40 succeeds, this call returns `sql.ErrTxDone` and changes nothing, so ignoring its result is correct.

**L21–L21** — Blank line.

**L22–L23** — The comment that fixes the order of the two statements. Steps must be updated first, "while their parent runs still have status queued or running", because the step statement finds its rows through the run statuses. If the run update ran first, the subquery at L27 would find no `queued` or `running` runs, and every step would stay `running` or `pending` beside an `interrupted` run. "Terminal steps and steps belonging to other runs keep their saved state" announces the two filters in the `WHERE` clause.

**L24–L27** — The step update. `SET status = CASE status WHEN 'running' THEN 'interrupted' ELSE 'skipped' END` is the per-row rule: a step that was executing when the process died is `interrupted`; a step that had not started is `skipped`, the same word `finishRun` uses for never-reached steps on a normal finish (`internal/engine/runner.go:303-306`). The `WHERE` clause has two parts. `status IN ('running', 'pending')` leaves `succeeded`, `failed`, and already-`skipped` or `interrupted` steps alone, so a run whose steps all completed but whose final save never landed keeps every result (the `afterExecution` fixture at `run_interruptions_test.go:36-39`). `run_id IN (SELECT id FROM runs WHERE status IN ('queued', 'running'))` restricts the rewrite to runs that were in flight; a terminal run with an oddly `running` step is deliberately out of scope (`run_interruptions_test.go:44-45`). These are the strings the runner writes: `pending` at `runner.go:134`, `running` at `runner.go:232`. No timestamp column is touched.

**L28–L30** — Report a failed step update as `mark unfinished run steps`. The deferred rollback discards anything SQLite had already changed.

**L31–L32** — The run update: every `queued` or `running` run becomes `interrupted`. `queued` is what `Start` saves for a run that waited for capacity (`runner.go:128`) and `running` for one it launched at once (`runner.go:131`) or promoted later (`runner.go:222`). Again no timestamps change. A queued run keeps its `NULL` `started_at`, so the browser shows **Never started** (`format.ts:96`); a running run keeps its `started_at` and `NULL` `finished_at`, so it shows **Finish time unknown** (`format.ts:101`). The result is captured because L36 needs it.

**L33–L35** — Report a failed run update as `mark unfinished runs`. This is the branch the rollback test forces with its trigger (`run_interruptions_test.go:87-93`, and the server-level copy at `cmd/server/main_test.go:122-130`).

**L36–L39** — Ask SQLite how many run rows the statement changed. `RowsAffected` is a method on the `Result` from L31 and can itself return an error, wrapped here as `count interrupted runs`. The count is what `runServer` logs when it is nonzero (`main.go:101-103`), and it is zero on a clean restart, which is why `TestMarkUnfinishedRunsInterruptedPreservesSavedResults` expects `0` on an empty database (`run_interruptions_test.go:21`) and, after saving its fixtures, calls the function twice more and expects `4` then `0` (`run_interruptions_test.go:64-66`): reconciliation is idempotent.

**L40–L42** — Commit, with failure wrapped as `commit run interruption`. Until this line nothing is visible to any other connection. If the five-second deadline from `main.go:95` expires between L16 and here, `database/sql` rolls the transaction back and `Commit` returns an error, so startup fails rather than half-reconciles. `TestRunServerReconcilesHistoryBeforeListening` (`main_test.go:85-182`, case "failed cleanup prevents startup") asserts that a failure anywhere inside this function (its trigger fires at the run update, L31, not at the commit) stops `runServer` with `mark unfinished runs interrupted` before any listener and that the lock is free afterwards.

**L43–L44** — Return the count, and the closing brace. The doc comment's "or zero if the transaction fails" holds because every error path above returns `0`.

## State, concurrency, and cancellation

**Goroutines.** All three functions run on the main goroutine, one after another, inside `runServer` and before anything concurrent exists: `engine.New` (`main.go:107`) has not created the runner, so no run goroutine exists (`runner.go:197`), and the listener goroutine (`main.go:129`) has not started. While they run, nothing else in this process touches SQLite, which is the precondition the comment at `run_interruptions.go:12` demands. Afterwards the one `*sql.DB` that `Open` returned is shared by every run goroutine (initial saves through `runs.go:17`, progress and final saves through `runs.go:68`), by every HTTP handler goroutine (`api.go:92`, `api.go:107`), and by the main goroutine at shutdown (`main.go:80-84`). `*sql.DB` is safe for concurrent use; with `SetMaxOpenConns(1)` (`sqlite.go:59`) the pool is the serialization point, and a goroutine that needs the connection while another holds it waits inside `database/sql` with its own context.

**Mutexes and lock order.** These files hold no mutex and define none. The one ordering worth knowing is the runner's: `Start` takes `r.mu` and, still holding it, calls `recordNewRun` (`runner.go:114-141`), which waits for the pooled connection inside `CreateRun`. The order is therefore `runner.mu`, then the pool's single connection. Nothing ever takes `runner.mu` while holding a transaction, so there is no cycle; the cost is that a slow initial save delays every other `Start` for up to its five-second `saveCtx`. Progress and final saves run outside `mu` (`runner.go:246`, `runner.go:286`), which is the rule "Execution and progress/final writes stay outside the history mutex; initial creation currently holds it to serialize admission" (`AGENTS.md:80-82`). Contention from another process, such as a `sqlite3` shell, is handled by `busy_timeout(5000)` at `sqlite.go:51`, and a second Patchbay process is kept out entirely by the `flock` from chapter 3 (`database_lock.go:51`).

**Contexts.**

| Call | Context | Created at | Cancels when | Effect of cancellation |
| --- | --- | --- | --- | --- |
| `Open` (`main.go:75`) | `stop` | `main.go:38` | `SIGINT` or `SIGTERM` | L28 returns before any file is created; later, `PingContext` or `migrate` returns a wrapped `context.Canceled` and the pool is closed |
| `CheckWritable` (`main.go:88`) | `writeCtx` = `stop` + 5 s | `main.go:87` | signal, or five seconds | The single `ExecContext` returns `context.Canceled` or `context.DeadlineExceeded`, including while waiting for the connection; the commit is inside that scope by design (`writable.go:15-16`) |
| `MarkUnfinishedRunsInterrupted` (`main.go:96`) | `interruptionCtx` = `stop` + 5 s | `main.go:95` | signal, or five seconds | `BeginTx` or an `ExecContext` fails, or `database/sql` rolls the transaction back before `Commit`; no partial rewrite is visible |

Both timeouts are released immediately after the call (`main.go:89`, `main.go:97`), so they do not leak timers. None of these contexts is the one the runner later uses: the runner derives its own from `context.Background()` (`runner.go:97`) precisely so that a signal does not cancel a run mid-save (`AGENTS.md:84-85`).

**Failure paths.**

| Fails at | What is on disk | What the caller sees | Pinned by |
| --- | --- | --- | --- |
| `sqlite.go:21` or `:24` | nothing new | `database path must not be empty` / `resolve database path` | `sqlite_test.go:54` |
| `sqlite.go:28` | nothing new | `open database: context canceled` | `sqlite_permissions_test.go:145-159` |
| `sqlite.go:34` (not `ErrExist`) | nothing new | `create database file: ...` | `sqlite_test.go:55` |
| `sqlite.go:63` | possibly a new empty `0600` file | `connect to database: ...` | `sqlite_permissions_test.go:123-143` |
| `sqlite.go:67` | an unchanged existing file, or the empty new file | `migrate`'s own message | `main_test.go:184-198`, chapter 9 |
| `writable.go:17` | unchanged header, schema, and rows | `commit database write check: ...` wrapped by `main.go:91` | `database_write_test.go:111-123`, `writable_test.go:124` |
| `run_interruptions.go:16-42` | unchanged rows, thanks to the rollback | `begin/mark/count/commit ...` wrapped by `main.go:99` | `run_interruptions_test.go:94-97`, `main_test.go:150-153` |

In every row, `runServer` returns the error, the deferred `db.Close` runs if `Open` had returned, and the deferred lock close runs last (`main.go:70-84`), so a corrected restart can take the same lock again. No step is executed and no run row is created on any of these paths.

**Rules from `AGENTS.md` that this code implements.**

- "Take the database ownership lock before migrations or interruption cleanup. Stop the runner before closing SQLite and releasing the lock." (`AGENTS.md:95-96`) `Open` runs `migrate` only after `lockDatabase` (`main.go:66`, `main.go:75`), and `MarkUnfinishedRunsInterrupted` runs under the same lock; the defer order at `main.go:80` and `main.go:115` stops the runner before `db.Close`.
- "Startup marks leftover queued/running records interrupted; it does not resume actions. Never infer that an uncertain external action is safe to repeat." (`AGENTS.md:98-99`) `run_interruptions.go:24-32` rewrites statuses only. It reads no outputs, starts no executor, and leaves recovery to milestone 7 (`docs/roadmap.md:168`, `docs/roadmap.md:188`).
- "Preserve atomic run/step snapshots and existing data." (`AGENTS.md:103`) One transaction at `run_interruptions.go:16-40`; timestamps, outputs, errors, and definition JSON are not in either `SET` clause.
- "Verify database identity before migration or startup cleanup. Only initialize an empty, unmarked database." (`AGENTS.md:105-106`) `Open` calls `migrate` at `sqlite.go:67`, which performs that check before any write, and the write check and cleanup come after `Open` returns.
- "Create new database files with mode `0600` before SQLite opens them, and keep SQLite in existing-file mode. Preserve existing file and directory permissions." (`AGENTS.md:108-109`) `sqlite.go:34` and `sqlite.go:48`; nothing in the file calls `Chmod` or opens with `O_TRUNC`.
- "After opening and recognizing the database, commit a bounded write check before interruption cleanup or HTTP startup. Preserve schema metadata and run history; a successful startup check does not guarantee future writes." (`AGENTS.md:110-112`) `writable.go:17` writes back the value that is already there, under the caller's deadline, and `main.go:88` places it between `Open` and cleanup.

## Check yourself

1. `Open` creates the file with `O_EXCL` at L34 and then also passes `mode=rw` at L48. Trace a dangling symlink at the configured path through both lines. Why is neither line enough on its own?

<details><summary>Answer</summary>At L34, `O_CREATE|O_EXCL` on a path that is a symlink fails with `EEXIST` regardless of where the link points, so Go takes the L39 branch: `errors.Is(err, os.ErrExist)` is true and nothing is created. Then `sql.Open` succeeds (it is lazy), and `PingContext` at L63 asks SQLite to open the link's target with `mode=rw`. The target does not exist and `rw` forbids creation, so the ping fails and `Open` returns `connect to database: ...`. Without `O_EXCL`, L34 would follow the link and create the target with mode `0600`, and SQLite would then open it happily. Without `mode=rw`, L34 would still refuse, but SQLite's default `rwc` would create the target during the ping. `TestOpenDoesNotCreateThroughDanglingDatabaseSymlink` (`sqlite_permissions_test.go:123-143`) checks both that the error occurs and that the target was never created.</details>

2. Why does `CheckWritable` issue one autocommit `PRAGMA` instead of `BeginTx`, a statement, and `Commit`, and what would an operator observe if it did the latter?

<details><summary>Answer</summary>The comment at `writable.go:15-16` says the driver's `sql.Tx.Commit` uses a background context. The commit is the step that writes the journal and the page to disk, so with an explicit transaction that part would run outside the caller's five-second deadline from `main.go:87`. On a hung filesystem the server could sit in startup with no bound, instead of failing with `check database writeability: ... context deadline exceeded`. A single `ExecContext` keeps the entire write, including its commit, under `ctx`. `TestCheckWritableHonorsContext` (`writable_test.go:130-159`) would still pass its "canceled before starting" case with a transaction, but the deadline case exists to keep the bound on the whole check.</details>

3. Swap the two `UPDATE` statements in `MarkUnfinishedRunsInterrupted`. What would the stored history look like after a crash, and would the function still return the right count?

<details><summary>Answer</summary>The run update would set every `queued`/`running` run to `interrupted` first. The step update's subquery `SELECT id FROM runs WHERE status IN ('queued', 'running')` would then match nothing, so every `running` step would stay `running` and every `pending` step would stay `pending`, next to a parent that says `interrupted`. The browser would show an interrupted run whose step badge still says **Running**. The returned count would still be correct, because it is taken from the run statement's `RowsAffected`, which is why the count alone cannot tell you the function is right; `assertStoredRun` in `TestMarkUnfinishedRunsInterruptedPreservesSavedResults` (`run_interruptions_test.go:68-71`) compares every step. The comment at `run_interruptions.go:22-23` exists to stop this swap.</details>

4. `Open` succeeds and `CheckWritable` fails. Which bytes on disk changed during this startup, is the lock still held, and what happens to history that was already `running`?

<details><summary>Answer</summary>For an existing, current, marked database, `migrate` commits nothing (`schema.go:87-89`), and the write check's own statement did not commit, so the file is unchanged. The `.lock` file was opened or created by `lockDatabase` but is released when `runServer` returns, because the deferred close at `main.go:70-74` runs after the deferred `db.Close` at `main.go:80-84`. Reconciliation never ran (`main.go:96` is after `main.go:88`), so a `running` run is still `running` in the file; it will be marked `interrupted` by the first startup that gets past the write check. `TestRunServerRejectsUnwritableJournalDirectoryBeforeCleanup` (`database_write_test.go:111-123`) asserts the message, that the lock can be taken again, and that history is identical before and after.</details>

5. Two run goroutines call `store.UpdateRun` at the same instant. Which goroutine runs first, which code decides that, and which context bounds the one that waits?

<details><summary>Answer</summary>Neither goroutine holds the runner's mutex during a progress save (`runner.go:246`, `runner.go:269`). Both call `db.BeginTx` in `runs.go:69`. Because `SetMaxOpenConns(1)` at `sqlite.go:59` allows one connection, `database/sql`'s pool hands it to whichever request arrives first and parks the other. The parked goroutine waits with the `saveCtx` that `saveRunUpdate` built from the runner's context plus five seconds (`runner.go:350`); if the first save takes longer than that, the second returns `context.DeadlineExceeded`, and the runner treats it as a failed progress save and stops that run's later steps (`runner.go:233-243`). SQLite itself never sees two of Patchbay's connections competing.</details>

6. `defer tx.Rollback()` at `run_interruptions.go:20` runs even after the `Commit` at L40 succeeded. Why is that not a bug, and why not call `Rollback` explicitly in each error branch instead?

<details><summary>Answer</summary>After `Commit`, the transaction is finished; `Rollback` returns `sql.ErrTxDone` and does nothing, and the function ignores that return value on purpose. Explicit `Rollback` calls in every `if err != nil` branch would be four copies of the same line, each one a chance to forget, and a panic between `BeginTx` and `Commit` would skip all of them, whereas a deferred call still runs. The same idiom appears at `runs.go:27`, `runs.go:73`, and `schema.go:61`.</details>
