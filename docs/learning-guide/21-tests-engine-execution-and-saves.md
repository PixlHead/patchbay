# 21. Tests: runner execution, persistence callbacks, and progress saves

Files: [internal/engine/runner_test.go](../../internal/engine/runner_test.go), [internal/engine/runner_persistence_test.go](../../internal/engine/runner_persistence_test.go), [internal/engine/runner_updates_test.go](../../internal/engine/runner_updates_test.go)

Revision: commit 1c4786e

## Role in the system

These three files are the proof behind the runner bullets of the "Execution and persistence rules" section (`AGENTS.md:78-99`). The production file they exercise is `internal/engine/runner.go` (Chapter 6). That file never touches the network or SQLite itself. It takes three functions as dependencies: `ExecuteStep` (`runner.go:51`) runs one step, `RecordNewRun` (`runner.go:55`) saves a new run, and `UpdateSavedRun` (`runner.go:60`) saves progress. In production `cmd/server/main.go:107-111` passes the real HTTP/TCP executor and the SQLite functions `store.CreateRun` (`internal/store/runs.go:17`) and `store.UpdateRun` (`internal/store/runs.go:68`). In these tests every one of those three functions is a small closure written inside the test. That is how the tests control failure and time without a database, a server, or a sleeping clock, which is what `AGENTS.md:134-137` asks for: "Use fake executors, temporary databases, local test servers, and controlled clocks/channels" and "Keep failure injection in tests."

Data comes in the same way it does from a browser click. The handler at `internal/httpapi/api.go:65` calls `runner.Start(definition)`; the tests call `runner.Start(example())` with the two-step definition built at `runner_test.go:14-19`. Data goes out two ways. First, through the public surface the HTTP layer also uses: `Start` returns a `Run`, and `Get` and `List` (`runner.go:159-174`) return copies of memory history, which `awaitRun` (`runner_test.go:21-40`) polls exactly as the frontend polls `GET /api/runs/{id}`. Second, through the fake callbacks, which capture every `Run` snapshot the runner hands to storage. Comparing the two tells you whether what SQLite would hold matches what the API would show.

The files split by subject. `runner_test.go` holds the shared helpers plus the basic execution rules: sequential steps, failure skipping later steps, shutdown cancellation, and the 100-run memory bound. `runner_persistence_test.go` covers the first save, the one made under the mutex before a run is accepted. `runner_updates_test.go` covers every later save: the per-step progress writes, the final save and its retries, and what shutdown does to a save in flight. Chapter 22 covers the remaining engine test files, which focus on concurrency limits, the queue, and shutdown ordering.

## Concepts you need

- **Internal test packages.** All three files declare `package engine`, not `package engine_test`. A test file in the same package can read unexported fields such as `runner.busyWorkflows` (`runner_updates_test.go:138`) and build a `Runner` with a struct literal instead of `New` (`runner_updates_test.go:298`). The price is that the tests are coupled to private names; the benefit is that they can check a slot was really released. [cmd/go: test packages](https://pkg.go.dev/cmd/go#hdr-Test_packages)
- **The `testing` package: `t.Fatal`, `t.Error`, `t.Helper`, `t.Run`.** `t.Fatal` records a failure and stops the test function immediately; `t.Error` records a failure and continues. `t.Fatal` may only be called from the goroutine running the test, which is why a callback running on the runner's goroutine uses `t.Error` (`runner_updates_test.go:214`). `t.Helper` makes a failure inside a helper report the caller's line. `t.Run` starts a named subtest with its own pass/fail result, so one table of cases gives one line per case in `go test -v`. [pkg.go.dev/testing](https://pkg.go.dev/testing)
- **Table-driven tests.** A slice of anonymous structs lists inputs and expected outputs; a loop runs the same body for each row inside `t.Run`. Adding a case is adding a row, not a function. `runner_updates_test.go:85-101` is the clearest example. [Go wiki: TableDrivenTests](https://go.dev/wiki/TableDrivenTests)
- **Closures as fakes.** A closure is a function value that can read and write variables from the surrounding function. Every fake executor and fake save callback here is a closure that counts calls, records arguments, or returns an error on the Nth call, with no mock framework. The runner only sees a function of the right type. [Tour: function closures](https://go.dev/tour/moretypes/25)
- **Goroutines and `go`.** `go f()` starts `f` on a new lightweight thread. The runner starts one goroutine per run (`runner.go:197`); the tests start their own to call `Close` or `Get` while something is blocked, so the test goroutine stays free to wait with a timeout. [Tour: goroutines](https://go.dev/tour/concurrency/1)
- **Channels, `close`, and `select`.** A channel passes a signal between goroutines. Receiving from a closed channel returns at once, so `close(ch)` is a broadcast that "this happened". `select` waits on several channel operations and takes the first that is ready; a `default` case makes it non-blocking. The tests pair a channel with `time.After` so a hang becomes a failure instead of a frozen test. [Tour: channels](https://go.dev/tour/concurrency/2), [Tour: select](https://go.dev/tour/concurrency/5)
- **`context` and cancellation.** A `context.Context` carries a cancel signal and an optional deadline. `ctx.Done()` is a channel closed on cancel, `ctx.Err()` says why, and `ctx.Deadline()` reports the time limit. `context.WithTimeout` derives a child that can only be shorter than its parent; `context.WithoutCancel` derives a child that ignores the parent's cancel. The fakes block on `ctx.Done()` to imitate a database that honors cancellation. [pkg.go.dev/context](https://pkg.go.dev/context)
- **`sync.WaitGroup` and `WaitGroup.Go`.** A wait group counts running goroutines so a caller can wait for all of them. `wg.Go(f)` (Go 1.25) adds one, runs `f` on a new goroutine, and marks it done when `f` returns. The runner uses a wait group so `Close` blocks until every run goroutine has exited (`runner.go:190`). [pkg.go.dev/sync#WaitGroup.Go](https://pkg.go.dev/sync#WaitGroup.Go)
- **`sync.Mutex`.** A mutex lets one goroutine at a time touch shared data. The last test protects a map with one because two final saves can call the fake at the same time (`runner_updates_test.go:362-364`). [pkg.go.dev/sync#Mutex](https://pkg.go.dev/sync#Mutex)
- **The Go memory model and happens-before.** Reading a variable one goroutine wrote is only safe if something orders the write before the read: a mutex handoff, a channel receive, or `WaitGroup.Wait` returning. Several tests call `runner.Close()` before reading a slice the callback appended to, precisely to get that ordering. `make test` runs with `-race` (`Makefile:16`), which reports any read and write that are not ordered. [The Go memory model](https://go.dev/ref/mem), [Race detector](https://go.dev/doc/articles/race_detector)
- **`defer` and last-in, first-out order.** A deferred call runs when the surrounding function returns, even on `t.Fatal`. When a function defers several calls they run in reverse order. `runner_updates_test.go:228-229` depends on that order to unblock a save before `Close` waits on it. [Spec: defer statements](https://go.dev/ref/spec#Defer_statements)
- **Error wrapping: `%w`, `errors.Is`, `errors.Join`.** `fmt.Errorf("%w: %w", a, b)` builds one error that reports both `a` and `b` as causes. `errors.Is(err, target)` walks that chain. `errors.Join` combines two errors the same way. The tests check wrapped sentinels such as `ErrRecordRun` and `context.DeadlineExceeded` with `errors.Is`, never with string comparison. [pkg.go.dev/errors](https://pkg.go.dev/errors)
- **`reflect.DeepEqual`.** Compares two values field by field, following pointers and slices. It is how the tests say "this snapshot is identical to that one", including nested `*CheckResult` outputs. [pkg.go.dev/reflect#DeepEqual](https://pkg.go.dev/reflect#DeepEqual)
- **Slices share backing arrays; `slices.Clone` separates them.** A slice is a small header pointing at an array. Copying the header, which is what passing a struct by value does, still shares the elements. The persistence test edits a step after `Start` returns to prove the runner cloned the slice (`runner.go:109`). [Go blog: slices](https://go.dev/blog/slices-intro), [pkg.go.dev/slices#Clone](https://pkg.go.dev/slices#Clone)
- **Pointers versus values; `nil` pointer fields.** `StartedAt`, `FinishedAt`, and `Output` on `StepRun` are pointers (`runner.go:28-30`) so that "not set" is `nil` and JSON can omit them. The tests check `== nil` and `!= nil` to say whether a timestamp or output was recorded. [Tour: pointers](https://go.dev/tour/moretypes/1)
- **Arrays versus slices for comparison.** `[3]string` is a fixed-size array value; two arrays are equal when their elements are equal, so a slice of them compares cleanly with `reflect.DeepEqual` (`runner_updates_test.go:45-61`). [Tour: arrays](https://go.dev/tour/moretypes/6)
- **`for range N` over an integer.** Since Go 1.22, `for i := range 101` counts from 0 to 100, and `for range 10` repeats ten times without a variable. [Spec: for statements with range clause](https://go.dev/ref/spec#For_range)
- **`time` helpers.** `time.After(d)` returns a channel that receives once after `d`; `time.NewTicker(d)` ticks repeatedly until `Stop`; `time.Since`, `time.Until`, `Sub`, `Equal`, and `Before` compare instants. [pkg.go.dev/time](https://pkg.go.dev/time)
- **`testing/synctest`: a fake clock for tests.** `synctest.Test(t, f)` runs `f` in a "bubble" where `time.Now`, timers, and context deadlines use a fake clock. Time advances only when every goroutine in the bubble is blocked, so a 5-second budget elapses instantly and `time.Since` returns exact values. `synctest.Wait()` blocks until all other goroutines in the bubble are blocked. The three final-save tests use it to check 100 ms, 200 ms, 50 ms, and 5 s budgets without sleeping. [pkg.go.dev/testing/synctest](https://pkg.go.dev/testing/synctest), [Go blog: synctest](https://go.dev/blog/synctest)
- **Composite literals.** `&Runner{updateSavedRun: f}` builds a struct with only the named fields set and takes its address. Two tests use it to call `finishRun` and `saveFinalRun` directly, skipping `New`, because those methods touch no other field. [Spec: composite literals](https://go.dev/ref/spec#Composite_literals)

## Walkthrough

### internal/engine/runner_test.go

**L1–L13** — `package engine` makes this an internal test file (see Concepts), and the imports name what the tests need: `context` for the `ctx` parameter every fake executor receives (`runner.go:51`); `errors` for `errors.New` in fakes and `errors.Is` at L104 and L122; `reflect` for `DeepEqual` at L57; `sync` for the reader wait group at L107; `testing`; `time` for the poll deadline and ticker in `awaitRun`; and `patchbay/internal/workflow` for `Definition`, `Step`, `CheckConfig`, and `CheckResult`. No `store`, `net/http`, or `httpapi` import appears: the engine is tested below those layers.

**L14–L20** — `example()` is the definition almost every engine test starts from, and `concurrentDefinition` (`runner_concurrency_test.go:272-279`) derives per-workflow variants from it. Every field is there to pass `workflow.Validate` (`internal/workflow/workflow.go:63-117`), which `Start` runs first (`runner.go:106-108`): `SchemaVersion: 1` (`workflow.go:64-66`), an ID matching the identifier pattern (`workflow.go:67-69`), one to twenty steps (`workflow.go:75-77`), an absolute `http` URL (`workflow.go:92-95`), an `ExpectedStatus` between 100 and 599 (`workflow.go:96-98`), and a `TimeoutMS` of at least 100 (`workflow.go:112-114`). `http://localhost` is never contacted; every test installs its own `ExecuteStep`, so the URL only has to be well formed. The function returns a fresh value on each call on purpose: `Steps` is a slice, and a test that edits a step (`runner_persistence_test.go:36`) must not change what another test sees.

**L21–L25** — `awaitRun` polls until a run leaves the `running` state. `t.Helper()` makes its two `t.Fatal` calls report the caller's line. `deadline` fires after two seconds so a run that never finishes fails the test instead of hanging it. The one-millisecond ticker paces the poll. `defer ticker.Stop()` stops it when the helper returns, as the `time` package asks; a helper that returned early through `t.Fatal` would otherwise leave a ticker firing until the collector reclaimed it. The helper watches `Get` rather than a private channel because the runner offers no completion signal to anyone: the browser polls `GET /api/runs/{id}` the same way, so the test proves the public surface shows completion.

**L26–L33** — Each pass takes a copy from `Get` (`runner.go:159-164`). A missing run is impossible for an accepted start (`Start` registers it at `runner.go:146-147` before returning), so `!ok` is a fatal. The loop returns as soon as `Status` is anything but `running`, which covers `succeeded`, `failed`, and `canceled`. Because the run goroutine publishes its terminal snapshot only at `runner.go:289`, after `finishRun` returns, a value returned here already has `FinishedAt` and its skipped steps filled in. No test in this chapter waits on a `queued` run; such a run would be returned immediately.

**L34–L41** — The `select` waits for whichever comes first: the deadline (fatal "run did not finish") or the next tick (loop again). Without the deadline case an executor that never returns would block the whole package's test run; without the ticker case the loop would spin a CPU core.

**L42–L47** — `TestSequentialChecksAndSnapshots` sets up a runner with two active slots, no queue, and both persistence callbacks `nil`, which `runner.go:89` documents as the in-memory mode for executor tests (`runner.go:136`, `runner.go:317`, and `runner.go:347` check for `nil`). The fake executor appends each step's ID to `called` and returns `Healthy: false, Reason: "maintenance"` with a `nil` error. That pairing is the point: an unhealthy service is a successful execution of the check step. `AGENTS.md:91` requires the runner to "Distinguish execution outcome, monitored-service health, and save failure", and `runner.go:257` stores the output as a succeeded step. `called` is written on the run goroutine and read at L57; that is safe because the runner's final publish under the mutex (`runner.go:287-289`) happens after the last executor call and before `Get` at L27 can return the finished status.

**L48–L51** — `New` validates its limits (`runner.go:91-96`), so its error is checked. `defer runner.Close()` guarantees that even a failing assertion leaves no run goroutine behind: `Close` cancels and then waits on the wait group (`runner.go:176-191`).

**L52–L56** — `Start` admits the run. With a free slot, `queued` is false at `runner.go:122`, so the returned `Run` is already `running` with `StartedAt` set (`runner.go:130-132`). `awaitRun` then blocks until it finishes.

**L57–L59** — Two facts in one condition. The status is `succeeded`: `status` starts as that at `runner.go:224` and nothing in the loop changes it when `err` is `nil`. And `called` is exactly `["one", "two"]`: the loop at `runner.go:225` is a plain `for` over `definition.Steps`, which is what `AGENTS.md:67` means by "steps within a run remain sequential".

**L60–L62** — Step two must not start before step one finished. `StartedAt` is set at `runner.go:231-232` before the step's progress save; `FinishedAt` at `runner.go:248-249` after `execute` returns. If the runner ever ran steps concurrently, the second start would precede the first finish. `FinishedAt` is a pointer (`runner.go:29`), hence the `*` to compare values.

**L63–L69** — The snapshot test. The test writes through `result.Steps[0].Output.Reason`, where `Output` is a `*workflow.CheckResult` (`runner.go:30`), then fetches the run again and expects the original `"maintenance"`. This passes only because `copyRun` (`runner.go:381-390`) both clones the `Steps` slice (L382) and allocates a new `CheckResult` for every non-nil `Output` (L384-387). Drop the inner copy and the two snapshots would share one `CheckResult`, so a caller of `Get` could corrupt history for every later reader. The comment at `runner.go:380` and the rule "Return copied snapshots" (`AGENTS.md:82`) are what this entry enforces.

**L70–L77** — `TestExecutionFailureSkipsLaterSteps` installs an executor that always fails with `"executor failed"` and a zero `CheckResult`, again with no persistence.

**L78–L82** — Start and wait as before.

**L83–L87** — The run is `failed` and step two is `skipped`. The path: `runner.go:250-255` sets `status` to `failed` and stores the error on step one; the runner context is not canceled, so `runner.go:262` does not break; the progress save at `runner.go:269` returns `nil` (nil callback); `runner.go:281` publishes; `runner.go:282-284` breaks on the error. `finishRun` (`runner.go:286`, body at `300-314`) turns the still-`pending` step two into `skipped` (`runner.go:303-307`). This is `AGENTS.md:86-88`: "A failed progress save stops later steps. Preserve completed outputs and skip steps that never ran", applied to an execution failure.

**L88–L94** — `TestBusyShutdownAndConcurrentReads` needs a run that is provably in progress. The executor closes `started` and then blocks on `ctx.Done()`, returning `ctx.Err()` once canceled. The `ctx` it receives is the runner's own context (`runner.go:247`), which only `Close` cancels (`runner.go:179`). `close` on an already closed channel panics, so this fake also asserts the executor runs once: after cancellation the loop breaks at `runner.go:262-267` and step two is never executed.

**L95–L98** — Constructor check and deferred `Close`.

**L99–L103** — After `Start`, `<-started` blocks until the executor is actually inside step one. Only then is the workflow guaranteed to be marked busy and executing.

**L104–L106** — A second `Start` of the same definition (same ID `"test"`) must return `ErrWorkflowBusy`. `Start` set the mark at `runner.go:148` and checks it at `runner.go:119-121` under the mutex. `errors.Is` is used because production callers wrap and inspect the same sentinel: `api.go:69-70` maps it to `409 Conflict`, and `scheduler.go:129-130` skips the occurrence.

**L107–L115** — Ten goroutines each call `Get` and `List` twenty times while the run goroutine is alive and while `Close` is running. `readers.Go` starts each and tracks it in the wait group. Nothing is asserted here; the race detector is the assertion. `make test` runs `go test -race` (`Makefile:16`), and the readers take the mutex (`runner.go:160`, `runner.go:167`) and receive copies, while the run goroutine mutates only its own working copy (`runner.go:218-219`). If `publishRun` stored a slice that aliased the goroutine's array, `-race` would report the writes at `runner.go:249` and `runner.go:255`, made while `Close` unblocks the step, against a read here.

**L116–L117** — `Close` while step one is blocked. It sets `closed`, cancels the context, finds no queue, and waits (`runner.go:176-191`). The executor returns `ctx.Err()`; the run goroutine marks step one `canceled` (`runner.go:250-255`), breaks at `runner.go:262-267`, and finishes. The deferred `Close` at L98 will run a second time later; that is harmless because `pending` is already `nil` and the wait group is at zero. `readers.Wait()` then makes sure every reader goroutine has exited before the test ends.

**L118–L121** — The run is `canceled` and step two is `skipped`, which is `README.md:175-176`: "If shutdown prevents remaining steps from executing, the run is Canceled and those steps are skipped."

**L122–L126** — A `Start` after `Close` returns `ErrClosed` (`runner.go:116-118`), which `api.go:73-74` maps to `503 Service Unavailable`. The check sits before any other admission logic because `Close` has already returned from `wg.Wait`; accepting work now would start a goroutine nobody waits for while `main.go:81` is about to close SQLite.

**L127–L139** — `TestInvalidDefinitionNeverRunsAndHistoryIsBounded` uses a healthy executor and a fake `UpdateSavedRun` that fails the first three saves whose status is `succeeded`. Progress saves arrive with status `running` (`runner.go:233`, `runner.go:269`) and return `nil`, so only final saves (`runner.go:338`) count. The comment at L134 explains the number three: `saveFinalRun` makes at most three attempts (`runner.go:325`), so the first run exhausts its retries and the second run's single attempt, the fourth call, succeeds.

**L140–L143** — Constructor check and deferred `Close`.

**L144–L148** — A definition with `Steps = nil` must be rejected. `Validate` fails at `workflow.go:75-77` ("workflow must contain 1–20 steps"), and `Start` returns that error at `runner.go:106-108` before taking the mutex, before any callback, and before any registration. The test name's "never runs" is this check: validation is the first gate, and an invalid definition reaches nothing behind it.

**L149–L162** — One hundred and one runs, started and awaited one after another. Each `awaitRun` returns only after the previous run published its terminal snapshot and, under the same lock acquisition, released its busy mark (`runner.go:289-290`), so the same workflow ID is accepted every time. `FinalSaveFailed` must be `true` only for `i == 0`: `finishRun` sets it at `runner.go:309-312` when `saveFinalRun` returns an error after its last attempt. The first run really waits through the 100 ms and 200 ms retry delays at `runner.go:327`; `awaitRun`'s two-second deadline absorbs that. The flag lives only on the in-memory `Run` (`runner.go:44-45`); the callback never receives it.

**L163–L169** — `List` must hold exactly 100 entries: `trimHistoryLocked` (`runner.go:366-378`) evicts the oldest finished run whenever `order` exceeds 100, and it runs from `Start` (`runner.go:149`) and from the end of every run (`runner.go:297`). `Get(first)` must fail: the first run, the one carrying the unsaved result, has been evicted. That is why `README.md:549-551` calls the warning temporary and why `AGENTS.md:94` says "Do not promise unsaved results survive eviction or process restart". The overlay at `api.go:145` stops finding it at the same moment.

### internal/engine/runner_persistence_test.go

**L1–L11** — Package clause and imports: `context`, `errors`, `reflect`, `testing`, and `workflow`. No `sync` or `time`: both tests are sequential and lean on `awaitRun` from `runner_test.go:21`.

**L12–L25** — `TestStartRecordsSnapshotBeforeExecution` keeps three recorders: `saved` (the `Run` the record callback received), `savedDefinition`, and `records` (how many times it was called). The fake executor turns ordering into an observable failure: if `saved.ID` is still empty when a step runs, the record callback has not run yet, and the step returns an error that would make the run `failed`. The fake `RecordNewRun` counts and stores both arguments. The runner calls it under the mutex at `runner.go:136-145` with `copyRun(run)` and its own copy of the definition.

**L26–L29** — Constructor check and deferred `Close`.

**L30–L36** — `definition := example()` is passed to `Start`, and then the caller edits it: `Name` at L35 and `Steps[0].Name` at L36. The two edits test different things. `Name` is a plain string field, copied when the struct was passed by value, so that edit can never reach the runner; it is a control. `Steps` is a slice header that still points at the caller's array unless the runner cloned it, which `runner.go:109` does with `slices.Clone`. Without that line the run goroutine, which reads `definition.Steps` at `runner.go:225` and uses `step.Name` in error messages at `runner.go:238` and `runner.go:276`, would see "Edited step", and so would the recorded snapshot.

**L37–L40** — The run must be `succeeded`, which means the executor saw `saved.ID` set, so the record call happened before the first step ran. That is `AGENTS.md:83`: "Save a new run and its workflow snapshot before acceptance". `records` must be exactly one: progress and final saves go to `UpdateSavedRun`, which is `nil` here, so `RecordNewRun` is called once per accepted run and never again.

**L41–L46** — The comment at L41 states the rule. `saved` must equal `started`: the callback's copy (`runner.go:140`) and `Start`'s return value (`runner.go:156`) are both `copyRun` of the same initial `run`, status `running` with pending steps and no `FinishedAt`. Finishing the run did not change either, because the run goroutine works on its own copy taken through `Get` (`runner.go:219`). `savedDefinition` must equal a fresh `example()`: the recorded definition kept the original step name despite L36. Together they prove the store receives the snapshot as of admission, which is what `store.CreateRun` (`runs.go:14-17`) writes.

**L47–L59** — `TestStartRejectsFailedSaveAndAllowsRetry` defines a sentinel `storageError`, counts `attempts` and `executed`, and installs a `RecordNewRun` that fails only on the first call.

**L60–L63** — Constructor check and deferred `Close`.

**L64–L67** — The rejected `Start` must return an error that `errors.Is` both `ErrRecordRun` and `storageError`. `runner.go:143` builds it with `fmt.Errorf("%w: %w", ErrRecordRun, err)`, two `%w` verbs, so the API can classify it and the log can show the cause. The returned `Run` must be the zero value: the runner hands back nothing half-registered. `api.go:75-78` maps this error to `500`, logs the raw cause, and sends the client "Could not save run. Check server logs." (`README.md:513-516`).

**L68–L70** — `List` must be empty. The registration lines `runner.go:146-147` come after the save at L140; a failed save returns at L143 before reaching them, so the run never enters `runs` or `order`.

**L71–L76** — A second `Start` of the same workflow must succeed. That proves two things about the failure path: the busy mark at `runner.go:148` was never set, and `launchLocked` at `runner.go:154` never took an active slot. This is `AGENTS.md:83-84`: "Failed initial saves must not execute actions or consume capacity." The test awaits the run and calls `Close` so the goroutine is finished before counters are read.

**L77–L80** — Final checks: the retried run `succeeded`; `attempts` is two (one failure, one success); `executed` equals the number of steps in `example()`, so only the accepted run executed anything; and `List` holds exactly one run.

### internal/engine/runner_updates_test.go

**L1–L14** — Imports add `sync` (the mutex in the last test), `testing/synctest` (the fake clock in the last three tests), and `time`.

**L15–L21** — `TestRunSavesProgressAndCompletion` loops over `[]bool{false, true}` and names the subtests `success` and `execution failure`. Each `t.Run` gets its own runner and its own pass/fail line; you can run one with `go test ./internal/engine -run 'TestRunSavesProgressAndCompletion/success'`.

**L22–L31** — `updates` collects every `Run` the fake `UpdateSavedRun` receives, in order. The executor fails with `"connection refused"` when `executionFails` is set, otherwise returns a healthy result with `StatusCode: 200`. Appending from the callback needs no mutex: one run means one goroutine calling it.

**L32–L35** — Constructor check and deferred `Close`.

**L36–L41** — Start, wait, then an explicit `runner.Close()`. The deferred `Close` at L35 would run too late for what follows: the test is about to read `updates`, which was written on the run goroutine. `Close` returns only after `wg.Wait` (`runner.go:190`), and the goroutine's deferred `wg.Done` (`runner.go:217`) runs after its last callback, so every append happens before the reads below.

2. In `TestSaveFailureStopsLaterStepsWithoutReplayingActions`, row "after last step" has both steps executed and succeeded, yet expects run status `failed`. Row "all final saves fail" also has both steps succeeded but expects `succeeded`. Which production lines make the difference?

<details><summary>Answer</summary>Row 4 fails the result save of step two, a progress save at `runner.go:269`. 3. In `TestShutdownSavesCancellationAndWaitsForFinalWrite`, why does the final-save branch use `t.Error` at L214 rather than `t.Fatal`, and why is `defer close(releaseFinal)` written after `defer runner.Close()`?

<details><summary>Answer</summary>The save callback runs on the run goroutine (`runner.go:338` is called from `finishRun`, which `run` calls at `runner.go:286`). The `testing` package requires `t.Fatal`, `t.FailNow`, and `t.SkipNow` to be called from the goroutine running the test function; from any other goroutine the test would not stop correctly. `t.Error` records the failure and lets the callback continue, so the test still ends through its normal path. The defers run last-in, first-out. Writing `close(releaseFinal)` second means it runs first, so a callback parked at L218-223 receives from the closed channel and returns `nil`. Then `runner.Close()` runs and its `wg.Wait` at `runner.go:190` returns because the run goroutine can finish. In the opposite order, a failed assertion between L234 and L265 would leave `Close` waiting on a save that nothing releases.</details>

4. `TestCloseBoundsActiveAndQueuedFinalSaves` expects `{"a": 1, "b": 1}` and no entry for `c`. Trace why `c`'s save callback is never called, and why `a` and `b` each get exactly one call.

<details><summary>Answer</summary>`Close` cancels the runner context (`runner.go:179`), moves `b` and `c` into a local slice, and calls `cancelQueued` on the calling goroutine (`runner.go:188`). `cancelQueued` creates one five-second context for the whole queue (`runner.go:203`). For `b`, `finishRun` calls `saveFinalRun`, whose `context.WithTimeout` at `runner.go:322` keeps the same deadline; the fake blocks on `ctx.Done()` until that deadline, returns `DeadlineExceeded`, and `runner.go:339` returns because `saveCtx.Err() != nil`, so there is no second attempt. By then the shared context has expired, so for `c` the check at `runner.go:335-336` returns `errors.Join(nil, DeadlineExceeded)` before the callback at `runner.go:338` is reached. Meanwhile `a`'s run goroutine, unblocked by the same cancel, calls `finishRun` with `context.WithoutCancel(r.ctx)` (`runner.go:286`) and its own five seconds; its single attempt also blocks for the whole budget and returns without retry. 5. `TestRunSavesProgressAndCompletion` already has `defer runner.Close()` at L35. Why does it call `runner.Close()` again at L41 before reading `updates`, and what would `go test -race` say if that line were removed?

<details><summary>Answer</summary>`updates` is appended on the run goroutine inside the save callback. The test goroutine reads it at L60-66. The Go memory model requires something to order those appends before the reads. `runner.Close()` provides it: `Close` returns only after `wg.Wait` (`runner.go:190`), and the run goroutine's `wg.Done` is deferred at `runner.go:217`, so it runs after the last callback. The deferred `Close` at L35 would run after the reads, too late. Removing L41 would not make `-race` report anything, because `awaitRun` already observes the ordering by a second route: the final callback at `runner.go:338` runs before the run goroutine takes the mutex and publishes at `runner.go:287-289`, and `awaitRun`'s `Get` takes that same mutex afterward. The explicit `Close` states the intent directly, does not depend on where the publish sits inside `run`, and guarantees the goroutine has exited before the subtest returns. The same call at `runner_updates_test.go:125` matters more, because L138 then reads `runner.busyWorkflows` with no lock at all; the delete at `runner.go:290` is in the same critical section as the publish, so the mutex route orders it too, but a finished goroutine is the plainer guarantee.</details>

6. The first run in `TestInvalidDefinitionNeverRunsAndHistoryIsBounded` takes roughly 300 ms longer than the other hundred. Where does that time go, and why does `TestFinalSaveRetriesUnchangedResult` not pay it even though it also makes three attempts?

<details><summary>Answer</summary>The first run's final save fails three times, so `saveFinalRun` waits on a real timer of 100 ms before the second attempt and 200 ms before the third (`runner.go:326-334`, with the duration computed at `runner.go:327`). That test uses the real clock, so the wait is real; `awaitRun`'s two-second deadline absorbs it. `TestFinalSaveRetriesUnchangedResult` runs under `synctest.Test` (`runner_updates_test.go:295`), where timers use a fake clock that jumps forward as soon as every goroutine in the bubble is blocked, so the same two timers fire instantly and the test can even assert the gaps are exactly 100 ms and 200 ms (`runner_updates_test.go:327`).</details>
