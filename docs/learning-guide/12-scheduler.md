# 12. The cron scheduler

Files: [internal/schedule/scheduler.go](../../internal/schedule/scheduler.go)

Revision: commit 1c4786e

## Role in the system

`internal/schedule/scheduler.go` is the whole `schedule` package. Its first two lines state its job and its limit: "Package schedule starts workflow runs at cron occurrences. It owns timing only: the runner still owns admission, overlap, capacity, and execution" (L1-L2). For every loaded workflow file that carries a `schedule` object (`README.md:345-364`), the scheduler runs one goroutine that sleeps until the next cron occurrence, asks the runner to start the workflow, and goes back to sleep until the occurrence after that. It never executes a step, never opens the database, and never serves HTTP. It is 145 lines long because everything hard about running a workflow already lives in the runner (chapter 6) and everything hard about cron arithmetic already lives in `workflow.Timetable` (chapter 5).

Three things come in. `New` (L53) receives the validated definitions that `workflow.Load` produced (`cmd/server/main.go:58`, `main.go:116`), a `StartRun` function, which in production is the runner's `Start` method passed as a value (`main.go:116`, `internal/engine/runner.go:105`), and a `Clock`, which in production is the real `time.Now` and `time.After` (L28-L30) and in tests is a fake that the test advances by hand (`internal/schedule/scheduler_test.go:26-63`). Three things go out. Each occurrence becomes one call to `start` (L125), which is the same call the HTTP handler makes for a manual run (`internal/httpapi/api.go:65`). Each start, skip, and schedule end becomes a structured log line (L89, L128, L130, L132, L144). And `NextRun` (L105) answers the question "when is this workflow's next occurrence?", which `GET /api/workflows` encodes as `nextRunAt` (`api.go:41-44`) and the page heading shows in the browser's zone (`web/src/format.ts:29-33`, `README.md:386-389`).

On the path from a browser click to a saved run, the scheduler is not on the path at all: a manual start goes from the handler to the runner without touching this package. For a scheduled run the scheduler stands in for the click. The loop goroutine at L125 is in the same position as the handler at `api.go:65`, and everything after that call is identical: the runner validates, checks overlap and capacity under its mutex, saves the run before accepting it, and executes the steps on its own goroutine under its own context (`runner.go:105-157`). The run then belongs to the runner, not to the scheduler. That is why shutdown stops the scheduler first and the runner second (`main.go:139-140`): once `Close` (L98) returns, no goroutine in this package can ask for more work, and the runner can drain what it already accepted.

## Concepts you need

- **Named function types and method values.** `type StartRun func(workflow.Definition) (engine.Run, error)` (L19) gives a name to a function signature; any function or closure with that exact shape can be stored in a field of that type. `runner.Start` without parentheses (`main.go:116`) is a method value: a function bound to that one runner, which fits `StartRun` because `Runner.Start` has the same signature (`runner.go:105`). Calling a nil function value panics, which is why L54 checks for nil. [Spec: Function types](https://go.dev/ref/spec#Function_types), [Spec: Method values](https://go.dev/ref/spec#Method_values)
- **A struct of functions as a test seam.** `Clock` (L23-L26) has two function-typed fields instead of being an interface. Production fills them with `time.Now` and `time.After` (L29); a test fills them with methods of a fake (`scheduler_test.go:41-43`) so it can decide exactly when a timer fires. This is the "fake clocks for scheduling" the roadmap asks for (`docs/roadmap.md:235`); without it a scheduler test would have to sleep for real minutes. [A Tour of Go: Function values](https://go.dev/tour/moretypes/24)
- **Receive-only channel types.** `<-chan time.Time` (L25) is a channel the holder can only receive from. `time.After` returns one, and the scheduler only ever waits on it (L119). The direction in the type stops the scheduler from sending on or closing a channel it does not own. [Spec: Channel types](https://go.dev/ref/spec#Channel_types)
- **`time.After` and timers.** `time.After(d)` returns a channel that delivers the current time once, after `d` has passed; a zero or negative `d` delivers at once. Since Go 1.23 an unreferenced timer is garbage collected even if it never fired, so a wait abandoned by `Close` does not leak. L119 uses it inside a `select` so the wait can be interrupted. [time.After](https://pkg.go.dev/time#After)
- **`time.Time`, zero values, and the two clocks.** A `time.Time` value is comparable with `Before`, `Equal`, and `IsZero`; its zero value (year 1) is the conventional "no time", which `Timetable.Next` uses to mean "no occurrence" (`internal/workflow/schedule.go:59`). `time.Now()` carries both a wall-clock reading and a monotonic reading; timers count with the monotonic clock, while a time built from a cron expression or passed through `In` carries only wall-clock time. `Sub` and `Before` between such values fall back to wall-clock arithmetic, which matters at L119 and L136. [time: Monotonic Clocks](https://pkg.go.dev/time#hdr-Monotonic_Clocks)
- **`select` and its random choice.** `select` blocks until one of its channel cases is ready and runs that case; an empty case body (L119) is legal and means "wake up and continue". When several cases are ready at the same moment, Go picks one at random, so code after a `select` cannot assume which case ran. L121 exists for exactly that reason. [A Tour of Go: Select](https://go.dev/tour/concurrency/5), [Spec: Select statements](https://go.dev/ref/spec#Select_statements)
- **`context.Context`: `WithCancel`, `Done`, and `Err`.** A context carries a cancellation signal. `context.WithCancel(parent)` returns a child and a `cancel` function; calling `cancel` closes the channel from `ctx.Done()` and makes `ctx.Err()` return `context.Canceled` forever after. The scheduler builds its own root context from `context.Background()` (L68) so that only `Close` can cancel it. [context](https://pkg.go.dev/context), [Go blog: Context](https://go.dev/blog/context)
- **Goroutines and `sync.WaitGroup`.** `go s.loop(e, occurrence)` (L92) starts `loop` on a new goroutine and returns at once. A `WaitGroup` counts goroutines in flight: `Add(1)` before the `go` statement, `Done()` when the goroutine ends (usually with `defer`), and `Wait()` blocks until the count is zero. The `Add` must run before the `Wait` it is meant to delay, which is why L91 runs in the launching goroutine, not inside `loop`. [A Tour of Go: Goroutines](https://go.dev/tour/concurrency/1), [sync.WaitGroup](https://pkg.go.dev/sync#WaitGroup)
- **`sync.Mutex` and `defer Unlock`.** A mutex lets one goroutine at a time hold a lock; others block in `Lock()` until `Unlock()`. `defer s.mu.Unlock()` right after `Lock()` releases the lock on every return path (L79-L80, L106-L107). Inside a loop (L140-L142) the unlock is written out explicitly, because a `defer` would only run when the function returns, and the next iteration would deadlock trying to lock again. Go mutexes are not re-entrant. [sync.Mutex](https://pkg.go.dev/sync#Mutex)
- **Maps and the comma-ok form.** `next, ok := s.next[workflowID]` (L108) reads a map and reports whether the key exists; a missing key yields the value type's zero value plus `false`. A map must be created with `make` before writing (L71); writing to a nil map panics, and reading or writing one map from two goroutines without a lock is a data race that can crash the process. [A Tour of Go: Maps](https://go.dev/tour/moretypes/19)
- **`errors.Is` and `%w` wrapping.** `fmt.Errorf("workflow %q: %w", ...)` (L64) builds a new message that still wraps the original error, and `errors.Is(err, target)` (L129) finds a sentinel such as `engine.ErrWorkflowBusy` (`runner.go:18`) through any number of wrappers. Comparing with `==` would stop working the moment someone wrapped the error. [errors.Is](https://pkg.go.dev/errors#Is), [fmt.Errorf](https://pkg.go.dev/fmt#Errorf)
- **A `switch` with no expression.** `switch { case cond: ... }` (L126) is a cleaner `if`/`else if` chain: the first case whose condition is true runs, and there is no fall-through. L126-L133 uses it to pick one of three log lines. [A Tour of Go: Switch with no condition](https://go.dev/tour/flowcontrol/11)
- **`for` with only a condition.** `for !occurrence.IsZero() { ... }` (L115) is Go's `while` loop: it tests the condition before every iteration and stops when it is false. [A Tour of Go: For continued](https://go.dev/tour/flowcontrol/3)
- **Value copies versus pointers.** Passing a struct, or assigning it, copies it; a pointer refers to one shared value. `*definition.Schedule` (L62) dereferences a pointer to copy the `Schedule` struct into a call; `e entry` (L112) is a copy that each loop goroutine owns outright. `Definition` holds a slice and a pointer, so a copy shares what they point to, which is safe here only because nobody writes to a loaded definition. [A Tour of Go: Pointers](https://go.dev/tour/moretypes/1)
- **Exported and unexported names.** A name that starts with a capital letter (`Scheduler`, `New`, `NextRun`) is visible outside the package; a lowercase name (`entry`, `loop`, `mu`, `next`) is private to it. The public surface of this package is exactly `StartRun`, `Clock`, `SystemClock`, `Scheduler`, `New`, `Start`, `Close`, and `NextRun`. [A Tour of Go: Exported names](https://go.dev/tour/basics/3)
- **Pointer receivers.** `func (s *Scheduler) Start()` (L78) declares a method on `*Scheduler`; `s` points to the one shared scheduler rather than a copy. Every method here uses a pointer receiver because the struct holds a mutex and a wait group, which must never be copied. [A Tour of Go: Pointer receivers](https://go.dev/tour/methods/4)
- **Implicit interfaces.** `httpapi.NextRunSource` (`api.go:21-23`) is an interface with one method, `NextRun(string) (time.Time, bool)`. `*Scheduler` satisfies it just by having that method (L105); there is no `implements` keyword, and this file does not import `httpapi`. [A Tour of Go: Interfaces are implemented implicitly](https://go.dev/tour/methods/10)
- **Keyed struct literals and `&T{}`.** `&Scheduler{start: start, ...}` (L69-L72) builds a struct with named fields and returns a pointer to it; fields not named keep their zero values (`started` is `false`, `wg` is an empty wait group). [A Tour of Go: Struct literals](https://go.dev/tour/moretypes/5)
- **Structured logging with `log/slog`.** `slog.Info("msg", "key", value, ...)` writes a message plus key-value pairs. The scheduler logs `workflow_id`, `occurrence`, and `run_id` so an operator can match a scheduled start to the run it created. `Info` is for expected events, `Warn` for events that need a look. [log/slog](https://pkg.go.dev/log/slog)

The signature is copied from `Runner.Start` (`runner.go:105`), so `main.go:116` passes `runner.Start` as a method value with no adapter. Taking a function rather than a `*engine.Runner` means the scheduler depends on one capability only. This is how `AGENTS.md:100`, "Scheduled starts call `Runner.Start` exactly as the API does", is kept true: there is no second admission path to drift.

The scheduler needs only to read the time and to wait, so two functions are enough; an interface would add nothing. The test fake (`scheduler_test.go:26-63`) hands every wait to the test over a channel so the test can say "the timer fired at 10:23" (`scheduler_test.go:134`) without sleeping. Without this seam, `TestStartsRunsAtOccurrencesAndSkipsMissedOnes` would take twenty real minutes.

**L45–L49** — A blank line, `ctx`, `cancel`, `wg`, and the closing brace. `ctx` is the scheduler's own lifetime, `cancel` ends it (L99), and `wg` counts loop goroutines so `Close` can wait for them (L100). The context is deliberately not derived from the signal context at `main.go:38`; chapter 3 explains that the main goroutine cancels the scheduler and then the runner in a fixed order (`main.go:139-140`) rather than letting one signal cancel everything at once.

The `*` dereferences the pointer and copies the `Schedule` struct into the call. `NewTimetable` (`schedule.go:29-56`) parses the cron expression, loads the zone, and enforces the five-year and once-a-minute limits; this is the second time it runs for each file, because `Validate` throws its result away (`workflow.go:71`) and `New` needs the `Timetable` value. **L68–L68** — `ctx, cancel := context.WithCancel(context.Background())`. The scheduler's root context. It has no deadline and no parent that could cancel it; the only way it ends is `Close` calling `cancel` (L99). Every loop goroutine watches it (L117, L121).

**L69–L73** — Return `&Scheduler{...}` with keyed fields, including `next: make(map[string]time.Time)`. The map must be made here, because L88 writes to it and writing to a nil map panics. `started` is left `false` and `wg` at zero. `New` starts no goroutine, so a scheduler that is created but never started, which happens when `runServer` fails after `main.go:116`, closes cleanly: `Close` cancels a context nobody is watching and waits on a zero count.

**L74–L74** — Blank line.

**L75–L78** — The doc comment and signature of `Start`. "NextRun reports those occurrences as soon as Start returns" is the promise that lets `main.go:130` call `Start` after the HTTP listener is already serving (`main.go:129`): the first `GET /api/workflows` after `Start` returns sees a `nextRunAt`. "A second call, or a call after Close, does nothing" is the promise behind L81; the call-after-`Close` half is tested at `scheduler_test.go:229-235`, and no test calls `Start` twice.

**L79–L80** — Lock `s.mu` and defer the unlock. The lock is held for the entire method, including the goroutine launches, so two concurrent `Start` calls cannot both pass the guard on the next line, and no `NextRun` can observe a half-filled `next` map.

**L81–L83** — Return early if `s.started` is already true or `s.ctx.Err()` is non-nil, meaning `Close` already ran. The first condition stops a second `Start` from launching a second goroutine per entry, which would double-start every occurrence. The second stops a `Start` after `Close` from logging `schedule active` and launching goroutines that nobody will wait for. `main` only calls `Start` once (`main.go:130`); the guard makes the method safe anyway.

**L84–L84** — `s.started = true`, written under the lock taken at L79.

**L85–L85** — `now := s.clock.Now()`, read once so every entry's first occurrence is measured from the same instant. This line implements "the first occurrence after startup is computed from the current time" (`README.md:377-378`) and therefore `AGENTS.md:101-102`, "never replays occurrences missed during downtime": an occurrence earlier than `now` is never computed, so it can never be started. With the fake clock at 10:03, the first occurrence of `*/5 * * * *` is 10:05, not the 10:00 that passed (`scheduler_test.go:103-106`).

**L86–L88** — For each entry, compute `occurrence := e.timetable.Next(now)` and store it in `s.next` under the entry's workflow id. `Next` (`schedule.go:60-62`) returns the first occurrence strictly after `now`, expressed in the schedule's zone, or the zero time if there is none within five years. Storing before launching the goroutine is what makes the "as soon as Start returns" promise at L76 true.

**L89–L90** — `slog.Info("schedule active", ...)` with the id, cron expression, time zone, and first occurrence. Dereferencing `e.definition.Schedule` is safe because L59 kept only entries with a non-nil schedule. This is the line an operator reads at startup to confirm a schedule was loaded and when it fires first; chapter 5's last experiment watches it.

**L91–L92** — `s.wg.Add(1)` and then `go s.loop(e, occurrence)`. The `Add` runs here, in the launching goroutine and under `s.mu`, before the `go` statement; if it were inside `loop`, `Close` could call `Wait` on a zero count while a loop was still about to start, and return before that loop was stopped. `e` and `occurrence` are passed as arguments, so each goroutine owns its own copies and no closure captures a loop variable. Go 1.22 made loop variables per-iteration anyway, but arguments make the ownership visible.

**L93–L94** — The closing braces of the loop and the method. The deferred unlock from L80 runs here, after every goroutine has been launched.

**L95–L95** — Blank line.

**L96–L98** — The doc comment and signature of `Close`. "Runs that already started belong to the runner and continue there." `Close` does not touch the runner, cancel runs, or wait for them; that is `runner.Close`'s job (`runner.go:176-191`). This upholds `AGENTS.md:84-85`: "Accepted runs belong to the runner's context, not the originating HTTP request", and not the scheduler either. `main` calls `Close` at `main.go:139` on a signal and again through the `defer` at `main.go:121`; both calls are safe.

**L99–L99** — `s.cancel()`. Closes the channel behind `s.ctx.Done()`, which wakes every loop blocked in the `select` at L116-L120 and makes `s.ctx.Err()` non-nil for the checks at L81 and L121. A second call is a no-op, which is why the double `Close` in `main` is harmless.

**L100–L101** — `s.wg.Wait()` and the closing brace. Returns only when every loop goroutine has run its deferred `Done` (L113). After this line no goroutine in this package can call `s.start`, so `runner.Close` at `main.go:140` can proceed knowing no scheduled admission will arrive during its drain. This is what makes "Stop the scheduler before the runner" (`AGENTS.md:102`) more than a line order: a loop that is inside `s.start` at the moment of the cancel finishes that call, then exits at its next `select`, and `Wait` covers that case too. `scheduler_test.go:216-228` checks that `Close` returns while a wait is pending and that no run started.

**L102–L102** — Blank line.

**L103–L105** — The doc comment and signature of `NextRun`. "It reports false for an unscheduled workflow or a schedule with no occurrence left." This method is what makes `*Scheduler` satisfy `httpapi.NextRunSource` (`api.go:21-23`), and `main.go:123` passes the scheduler to `httpapi.New` for that reason. It is called once per workflow on every `GET /api/workflows` (`api.go:42`), from HTTP handler goroutines, which is why the next two lines lock.

**L106–L107** — Lock and deferred unlock around the map read. A read of `next` without the lock would race the writes at L88 and L141.

**L108–L110** — `next, ok := s.next[workflowID]`, then `return next, ok && !next.IsZero()`. Two different "no next run" cases collapse into one `false`: an id that was never scheduled (or does not exist), and a schedule whose loop stored a zero time at L141 because `Next` ran out of occurrences. The API then leaves `nextRunAt` out of the JSON (`api.go:42-44`, `omitempty` at `api.go:27`), and the heading shows the cron summary without a next time (`web/src/format.ts:32`). `time.Time` is a value, so the caller receives a copy and cannot change the map entry.

**L111–L111** — Blank line.

**L112–L114** — The signature of `loop`, `defer s.wg.Done()`, and `id := e.definition.ID`. One `loop` goroutine runs per entry, launched at L92. The `defer` guarantees that `Close`'s `Wait` is released on every exit path: cancel at L118, the post-timer check at L123, and the natural end at L145. `id` is just a shorter name for the four log calls in this method (L128, L130, L132, L144) and the map write at L141. The method is unexported; only `Start` launches it.

**L115–L115** — `for !occurrence.IsZero()`. Keep going while the timetable still has a next occurrence. `NewTimetable` already rejects a schedule whose first occurrence is zero (`schedule.go:48-51`), and a five-field cron expression that has one occurrence almost always has another within the five-year window, so in today's code the loop ends only through `return`. The condition is still necessary: if a zero time ever reached L119, `occurrence.Sub(now)` would be a huge negative duration, `After` would fire immediately, and the loop would call `start` on every iteration without pause.

**L116–L120** — The `select`. Either `s.ctx.Done()` is ready and the loop returns, or the clock's channel for `occurrence.Sub(s.clock.Now())` delivers and the empty case body falls through. `Now` is read again here, not reused from L85, so the wait is measured from this moment. The duration may be negative when the occurrence already passed, for example because the previous `start` call took a while; `time.After` then fires at once, which is the intended "start late, once" behavior (`README.md:379-380`). A plain `time.Sleep` would do the same arithmetic but could not be interrupted by `Close`. The fake clock receives the duration on this line (`scheduler_test.go:51-55`), which is how the tests assert "want a two-minute wait" (`scheduler_test.go:111`).

**L121–L124** — After waking, check `s.ctx.Err()` again. The comment explains: "Close raced with the timer; shutdown must not admit new work." Because `select` picks at random among ready cases, a timer and a cancel that are ready at the same instant may be resolved in favor of the timer. Without this check, a run could be admitted after `main.go:139` believed no scheduled start was possible; the runner would then cancel it immediately, or, if `runner.Close` had already finished, answer `ErrClosed`. Either outcome would be a spurious run or a spurious warning during shutdown, and the first would violate "shutdown must not admit new work".

**L125–L125** — `run, err := s.start(e.definition)`. The one line where the scheduler asks for work, and the reason the package exists. In production this is `Runner.Start` (`runner.go:105-157`): validate, clone the definition, take `r.mu`, reject if the workflow is busy (`runner.go:119-120`) or capacity is exhausted (`runner.go:122-125`), save the run before accepting it (`runner.go:136-145`), then launch or queue it. The scheduler holds no lock here, so `s.mu` and `r.mu` are never held together. The call blocks until the save completes, up to five seconds (`runner.go:139`); during that time this loop is not waiting on a timer, which is the "slow start" that L134 mentions.

**L126–L133** — A `switch` with no expression picks one of three log lines and never retries. `err == nil`: `scheduled run started` with the run id, so the log can be matched to `GET /api/runs/{id}`. `errors.Is(err, engine.ErrWorkflowBusy)`: `scheduled run skipped while the previous run is active` at `Info` level, because a run that outlasts its interval is expected and the skip is the policy the roadmap chose, "by default, skip a scheduled occurrence if the same workflow is already queued or running" (`docs/roadmap.md:113`). Any other error (`ErrCapacity`, `ErrClosed`, `ErrRecordRun`, or a validation error) is a `Warn` with the error text. No branch loops back or sleeps and tries again: `AGENTS.md:101`, "never retries a rejected occurrence", and `README.md:374-377`. `scheduler_test.go:177-185` drives the busy branch with a real runner whose executor is blocked. `errors.Is` is used rather than `==` because the API does the same (`api.go:69`) and because a future wrap must not silently turn a busy skip into a warning.

**L134–L138** — The comment "Occurrences that passed during a long wait or a slow start are skipped, not replayed", then `from := s.clock.Now()`, clamped up to `occurrence` if the clock reads earlier. Using the current time as the base is the skip rule: after a host sleep that let several occurrences go by, `Next(now)` is the next future one, so the 10:15 and 10:20 occurrences in `scheduler_test.go:132-145` are never started. The clamp handles the opposite surprise. The timer at L119 counts on the monotonic clock while `occurrence` is wall-clock only (`In` at `schedule.go:61` strips the monotonic reading), so after a backward wall-clock adjustment `Now()` can read earlier than the occurrence that just fired. `Next` of such a time would return the same occurrence again, and the loop would start it twice. Clamping guarantees the next occurrence is strictly later than the one just handled.

**L139–L139** — `occurrence = e.timetable.Next(from)`. The next occurrence in the schedule's zone, or the zero time, which ends the loop at L115.

**L140–L142** — Lock, publish `s.next[id] = occurrence`, unlock. The unlock is explicit rather than deferred because this is inside a loop: a `defer` would hold the lock until the goroutine ended, and the next iteration's `Lock` would deadlock. The new value is published after the `start` call, so while a start is in progress `NextRun` still reports the occurrence being started. The tests read this value through `NextRun` at `scheduler_test.go:128`, `scheduler_test.go:140`, and `scheduler_test.go:183`, each time after `nextWait` has confirmed the loop reached its next `select`.

**L143–L143** — The closing brace of the `for` loop; control returns to the condition at L115.

**L144–L145** — `slog.Warn("schedule has no further occurrences", ...)` and the closing brace. Reached only when `Next` returned the zero time. The deferred `Done` from L113 runs here. From now on `NextRun` answers `false` for this id (L109), the API omits `nextRunAt`, and nothing restarts the loop; the schedule is inactive until the process restarts.

## State, concurrency, and cancellation

**Goroutines and what each owns.** The main goroutine calls `New` (L53), `Start` (L78), and `Close` (L98), in that order, from `runServer` (`main.go:116`, `main.go:130`, `main.go:139`). It is the only writer of `start`, `clock`, and `entries`, and it writes them once. Each scheduled workflow gets one `loop` goroutine (L92), which owns its `e` copy and its `occurrence` local and touches shared state only at L141. HTTP handler goroutines call `NextRun` (L105) for every `GET /api/workflows`. The runner's goroutines never touch scheduler state; the scheduler reaches the runner only through the `start` function.

**The mutex.** `s.mu` (L42) protects `next` and `started`, nothing else. It is taken at L79 (`Start`, held through the goroutine launches), L106 (`NextRun`), and L140 (`loop`, for one map write). It is never held while calling `s.start` (L125) or `s.clock.After` (L119). Two consequences: there is no lock ordering to remember, because `s.mu` and the runner's `r.mu` (`runner.go:63`) are never held at the same time; and a five-second initial save inside `Runner.Start` never blocks `NextRun`, so the API keeps answering during a slow save. `Start` does call `timetable.Next` under the lock (L87), which is fine because `Next` is a pure computation on immutable data (chapter 5).

**Contexts.** The scheduler has one context, `s.ctx`, created from `context.Background()` at L68 and canceled only by `Close` at L99. It is checked at L81 (refuse `Start` after `Close`), waited on at L117, and rechecked at L121. It is not derived from the signal context at `main.go:38`, so a signal does not cancel timers directly; the main goroutine cancels the scheduler first and then the runner (`main.go:139-140`). The scheduler passes no context into `start`; `Runner.Start` uses the runner's own context with a five-second timeout for the initial save (`runner.go:139`), so a scheduled run belongs to the runner from the moment it is saved.

**Failure paths, in the order the code can hit them.**

| Where | What happened | Result |
| --- | --- | --- |
| L54-L56 | nil `start` or incomplete clock | `New` fails; `main.go:117-118` returns `create scheduler: ...`; process exits 1 |
| L62-L65 | a schedule fails `NewTimetable` | same exit, with the workflow id in the message |
| L117-L118 | `Close` canceled the context during a wait | loop returns without starting anything |
| L121-L124 | timer and cancel ready together | loop returns; no admission during shutdown |
| L129-L130 | runner answered `ErrWorkflowBusy` | `Info` log; occurrence skipped; next one computed |
| L131-L132 | runner answered `ErrCapacity`, `ErrClosed`, `ErrRecordRun`, or a validation error | `Warn` log; occurrence skipped; next one computed |
| L119, L135 | timer fired late (host sleep) | that one occurrence starts late; occurrences that passed are skipped |
| L136-L138 | wall clock stepped backward | clamp prevents the same occurrence from starting twice |
| L115, L144 | `Next` returned the zero time | loop ends with a `Warn`; `NextRun` reports `false`; schedule inactive until restart |

A scheduled run that was admitted and then interrupted by shutdown follows the runner's rules (`README.md:172-180`); on the next startup its record is marked interrupted and the occurrence is not replayed, which is `AGENTS.md:98-99`, "Startup marks leftover queued/running records interrupted; it does not resume actions."

**Rules from AGENTS.md this file implements.**

- "Scheduled starts call `Runner.Start` exactly as the API does. The scheduler never executes steps, never retries a rejected occurrence, and never replays occurrences missed during downtime. Stop the scheduler before the runner." (`AGENTS.md:100-102`) L19 and L125 make the start call identical to `api.go:65`; the package imports no executor; L126-L133 has no retry branch; L85 and L135-L139 compute only future occurrences; L99-L100 let `main.go:139-140` stop the scheduler first and know it has stopped.
- "Keep admission, capacity, queue promotion, and same-workflow overlap checks under the runner's mutex." (`AGENTS.md:78-79`) The scheduler keeps no "is this workflow running" flag of its own. It learns that a workflow is busy only from the runner's answer at L129, so there is exactly one overlap check in the program, at `runner.go:119-120`.
- "Accepted runs belong to the runner's context, not the originating HTTP request." (`AGENTS.md:84-85`) `Close` (L98-L101) stops waiting goroutines and nothing else; a run already admitted at L125 is untouched.

**A design assumption worth stating.** `Start` and `Close` are written to be called in sequence from one goroutine, which is how `main` uses them. The `Add` at L91 runs under `s.mu`, but `Close`'s `Wait` at L100 does not take `s.mu`, so a `Start` and a `Close` running at the same instant on two goroutines could let `Wait` return before a just-launched loop exits. The L81 check covers the sequential case, `Close` then `Start`, which the tests exercise; the concurrent case does not occur in this program.

## Check yourself

1. Two goroutines could each decide that `scheduled-health` should start: the HTTP handler for a manual click and this workflow's `loop`. Where is the one check that prevents two runs of the same workflow, and why does the scheduler not keep its own flag?

<details><summary>Answer</summary>The check is in <code>Runner.Start</code> at <code>runner.go:119-120</code>, under <code>r.mu</code>, where <code>busyWorkflows</code> is consulted. Both callers reach it through the same function: the handler at <code>api.go:65</code> and the loop at L125. The scheduler keeps no flag because <code>AGENTS.md:78-79</code> puts the overlap check under the runner's mutex; a second flag in the scheduler could disagree with the runner's and would not see manual starts. The scheduler only reacts to the answer, at L129-L130.</details>

2. The schedule is `*/5 * * * *` in UTC. At 10:09 the loop is waiting for 10:10 and the laptop lid closes; the timer fires at 10:23. Which occurrences start, and what does `NextRun` report afterward? Name the lines.

<details><summary>Answer</summary>Only the 10:10 occurrence starts, late, at 10:23: the timer at L119 delivers once and L125 runs once. Then L135 reads the clock (10:23), L136 does not clamp because 10:23 is after 10:10, and L139 computes <code>Next(10:23)</code>, which is 10:25. The 10:15 and 10:20 occurrences are never computed, so they cannot start. L141 publishes 10:25 and <code>NextRun</code> reports it. This is <code>scheduler_test.go:132-145</code>, and the rule at <code>AGENTS.md:101-102</code>.</details>

3. Ctrl+C arrives in the same microsecond that a timer fires. Trace what stops a new run from being admitted, and what would go wrong if L121-L124 were deleted.

<details><summary>Answer</summary>The signal wakes <code>runServer</code> at <code>main.go:137</code>, which calls <code>scheduler.Close</code> (L99 cancels the context). In the loop, the <code>select</code> at L116 may have both cases ready and may pick the timer case at random. L121 then sees <code>s.ctx.Err() != nil</code> and returns, so <code>s.start</code> is never called; the deferred <code>Done</code> at L113 lets <code>Close</code>'s <code>Wait</code> at L100 return, and only then does <code>main.go:140</code> close the runner. Without L121-L124, the loop would call <code>s.start</code> after the scheduler was told to stop; the runner, still open, would save and admit a run that shutdown then cancels moments later, leaving a spurious canceled run in history.</details>

4. Why does L136-L138 compare `from` with `occurrence` instead of simply using `s.clock.Now()`? What exactly would go wrong, and why can the two values disagree at all?

<details><summary>Answer</summary>If <code>Now()</code> reads earlier than the occurrence that just fired, <code>Next(now)</code> at L139 returns that same occurrence, the loop waits a moment, and L125 starts the workflow a second time for one occurrence. The values can disagree because the timer at L119 counts with the monotonic clock while <code>occurrence</code> carries only wall-clock time (<code>schedule.go:61</code> uses <code>In</code>, which strips the monotonic reading); a backward wall-clock adjustment during the wait, or a timer that delivers a hair early, makes <code>Now()</code> precede the occurrence. Clamping to <code>occurrence</code> makes the next value strictly later.</details>

5. `NextRun("scheduled-health")` returns `false`. List every way that can happen and what the API response looks like.

<details><summary>Answer</summary>Three ways. The id has no entry in <code>next</code>: the workflow has no <code>schedule</code> (skipped at L59-L60) or the id is unknown. The entry exists but is the zero time: <code>Next</code> at L139 found no occurrence in the next five years and stored zero at L141, after which the loop ended at L144. Or <code>Start</code> has not been called yet, so the map is empty; <code>main.go:130</code> calls it right after the listener starts, so this window is tiny. In every case L109 returns <code>false</code>, <code>api.go:42-44</code> leaves <code>NextRunAt</code> nil, <code>omitempty</code> at <code>api.go:27</code> drops the field, and the heading shows only the cron summary (<code>web/src/format.ts:32</code>).</details>

6. Which goroutine owns the `e` value inside `loop`, and why can L125 and L139 read `e.definition` and `e.timetable` without taking `s.mu`?

<details><summary>Answer</summary>The loop goroutine owns it. L92 passes <code>e</code> by value, so each goroutine has its own copy of the <code>entry</code> struct. The data the copy still shares with others, the <code>Steps</code> backing array, the <code>Schedule</code> pointee, and the <code>Timetable</code>'s parsed schedule and <code>*time.Location</code>, is never written after <code>Load</code> and <code>New</code> finish, so concurrent reads are safe. <code>s.mu</code> exists only for <code>next</code> and <code>started</code>, which other goroutines do write.</details>
