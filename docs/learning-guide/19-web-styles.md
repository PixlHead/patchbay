# 19. The stylesheet: Tailwind theme tokens and React Flow bindings

## Role in the system

`web/src/index.css` is the only stylesheet in the project. `AGENTS.md:61` describes it as the Tailwind entry, the React Flow import, the `@theme` tokens, the base element rules, and the React Flow variable bindings; `README.md:409` gives the shorter form, "Tailwind entry, theme tokens, base rules". Every colour, font, shadow, and font size that a component names in a `className` string is defined here, and nowhere else. The file has no selectors for the app's own components. Components style themselves with utility classes such as `bg-surface` and `text-text-muted`, and this file is what makes those class names mean something.

Data flows through this file at build time, not at run time. `web/src/main.tsx:7` imports it, so Vite treats it as part of the bundle. The Tailwind Vite plugin registered at `web/vite.config.ts:3,6` compiles it: it expands `@import 'tailwindcss'`, reads the `@theme` block, scans every file under `web/src` for class names, and writes one CSS file into `web/dist/assets/`. The Go server serves that directory from `internal/httpapi/api.go:122`, and the browser loads the CSS once with `index.html`. After that the browser does the work: each time React changes a `className`, a `disabled` attribute, or an `aria-pressed` value, the browser re-matches the rules this file produced and repaints.

On the path from a browser click to a saved run, this file decides what the click target looks like and what the saved result looks like when it comes back. The Run button at `web/src/pages/WorkflowsPage.tsx:177` is green because of `--color-accent` at L42, turns translucent with a wait cursor while the POST is in flight because of L118-121, and the status badge that the one-second poll brings back is amber, blue, green, or red because `web/src/components/Badge.tsx:13-18` maps each run status onto the `--color-status-*` pairs at L51-58. The canvas on the Canvas view is coloured by the `.react-flow` block at L135-143. Nothing in this file touches the API, the router, or React state, but every pixel the reader sees passes through it.

## Concepts you need

- **Importing CSS from JavaScript.** `import './index.css'` in `web/src/main.tsx:7` is not a browser feature; Vite sees the import and bundles the stylesheet with the app. In development Vite injects it as a `<style>` tag so edits apply without a reload; in a production build it writes a hashed `.css` file and adds a `<link>` to `index.html`. [Vite: CSS](https://vite.dev/guide/features#css)
- **Tailwind CSS v4, configured in CSS.** Tailwind generates small single-purpose classes (`bg-surface`, `px-4`, `text-xs`) from the class names it finds in your source files. Version 4 has no `tailwind.config.js`; the whole configuration is this file: one `@import 'tailwindcss'` line and a `@theme` block. The Vite plugin in `web/vite.config.ts:6` runs the compiler. [Tailwind: Installing with Vite](https://tailwindcss.com/docs/installation/using-vite), [Tailwind: Theme variables](https://tailwindcss.com/docs/theme)
- **What `@import 'tailwindcss'` expands to.** It is equivalent to `@layer theme, base, components, utilities;` followed by three imports: Tailwind's theme into the `theme` layer, Preflight into `base`, and the utilities into `utilities`. That first line fixes the order of the four cascade layers for the whole stylesheet. [Tailwind: Preflight](https://tailwindcss.com/docs/preflight)
- **Cascade layers.** `@layer` groups rules into named layers, and the order in which layers are first declared decides which wins: a rule in a later layer beats a rule in an earlier layer regardless of selector specificity. Rules that are in no layer at all beat every layered rule. `@import url layer(name)` puts an imported file's rules into a layer. [MDN: @layer](https://developer.mozilla.org/en-US/docs/Web/CSS/@layer), [MDN: @import](https://developer.mozilla.org/en-US/docs/Web/CSS/@import)
- **Preflight.** Tailwind's base reset. It removes margins, makes headings inherit their size and weight, makes links inherit colour and decoration, gives `html` a line height of 1.5 and the `--default-font-family` font, sets `code` to the mono font at `1em`, and leaves buttons with the browser's default cursor. Everything in this file's `@layer base` block exists to put back a specific default that Preflight took away. [Tailwind: Preflight](https://tailwindcss.com/docs/preflight), [Tailwind: Upgrade guide, buttons use the default cursor](https://tailwindcss.com/docs/upgrade-guide#buttons-use-the-default-cursor)
- **`@theme` and theme variable namespaces.** A custom property declared inside `@theme` becomes a theme variable: Tailwind emits it on `:root` and generates utilities from it according to its prefix. `--color-accent` gives `bg-accent`, `text-accent`, `border-accent`, `outline-accent`; `--font-mono` gives `font-mono`; `--text-2xs` gives `text-2xs`; `--shadow-node` gives `shadow-node`. A plain `:root { --color-accent: ... }` block would give you `var(--color-accent)` but no class. [Tailwind: Theme variable namespaces](https://tailwindcss.com/docs/theme#theme-variable-namespaces)
- **Overriding and removing default theme values.** Redeclaring a default name such as `--font-sans` replaces it. Writing `--color-*: initial` removes every default colour in that namespace, so `bg-red-500` no longer exists until you define `--color-red-500` yourself. Order inside `@theme` matters: a later declaration wins. [Tailwind: Overriding the default theme](https://tailwindcss.com/docs/theme#overriding-the-default-theme)
- **Which variables reach the output.** By default Tailwind writes only the theme variables that something uses, either as a generated utility or through `var()` in CSS. `@theme static` would emit all of them. This is why a token can be declared and still be absent from `web/dist` until a component names it. [Tailwind: Generating all CSS variables](https://tailwindcss.com/docs/theme#generating-all-css-variables)
- **CSS custom properties and inheritance.** `--name: value` defines a variable on an element; `var(--name)` reads it. Custom properties inherit, so a variable set on `:root` is visible everywhere, and one set on `.react-flow` is visible to every element inside the canvas but nowhere else. The `color` property inherits too, which is why setting it once on `body` colours all text. [MDN: Using CSS custom properties](https://developer.mozilla.org/en-US/docs/Web/CSS/Using_CSS_custom_properties), [MDN: Inheritance](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_cascade/Inheritance)
- **Class detection and the Prettier sorter.** Tailwind generates a class only when it finds the complete name as a string in a source file; a name assembled at run time produces nothing, and an unknown name produces nothing and no error. The Prettier plugin named in `web/.prettierrc.json:4` sorts `className` strings and reads this stylesheet (`web/.prettierrc.json:5`) so it recognises the project's own tokens. [Tailwind: Detecting classes in source files](https://tailwindcss.com/docs/detecting-classes-in-source-files), [prettier-plugin-tailwindcss](https://github.com/tailwindlabs/prettier-plugin-tailwindcss)
- **`@layer base` and `@layer components` in your own CSS.** Tailwind lets you add rules to its layers. Base rules are for bare elements (`body`, `h1`, `button`) and lose to any utility class. Component rules are for reusable classes and also lose to utilities, so `className="font-medium"` on an `<h3>` always beats `h3 { font-weight: 700 }` here. [Tailwind: Adding base styles](https://tailwindcss.com/docs/adding-custom-styles#adding-base-styles), [Tailwind: Adding component classes](https://tailwindcss.com/docs/adding-custom-styles#adding-component-classes)
- **Font size tokens and paired line heights.** A `--text-<name>` variable creates a `text-<name>` utility. If a companion `--text-<name>--line-height` exists, the utility sets both `font-size` and `line-height`; without it, the utility sets only `font-size` and the element inherits its line height. L9 deliberately has no companion. [Tailwind: Font size, customizing your theme](https://tailwindcss.com/docs/font-size#customizing-your-theme)
- **`rem` and eight-digit hex colours.** `1rem` is the root font size, 16px in every browser unless the user changes it, so `0.625rem` is 10px and `0.875rem` is 14px. A hex colour with eight digits carries alpha in the last two: `#17352612` is the colour `#173526` at `0x12 / 255`, about 7 percent opacity. [MDN: length](https://developer.mozilla.org/en-US/docs/Web/CSS/length), [MDN: hex-color](https://developer.mozilla.org/en-US/docs/Web/CSS/hex-color)
- **`:disabled`, `:focus-visible`, `outline-offset`.** `:disabled` matches a form control with the `disabled` attribute, which React sets from `disabled={...}`. `:focus-visible` matches an element that has focus and that the browser thinks should show it, in practice keyboard focus but not a mouse click. `outline-offset` pushes the outline away from the border so a ring does not sit on top of the element's own edge. [MDN: :focus-visible](https://developer.mozilla.org/en-US/docs/Web/CSS/:focus-visible), [MDN: outline-offset](https://developer.mozilla.org/en-US/docs/Web/CSS/outline-offset)
- **Text rendering properties.** `font-synthesis: none` stops the browser from faking bold or italic when a font lacks that face. `text-rendering: optimizeLegibility` turns on kerning and ligatures. `-webkit-font-smoothing: antialiased` selects greyscale smoothing in WebKit and Blink on macOS. `-webkit-tap-highlight-color` is the grey flash a mobile browser paints over a tapped element. [MDN: font-synthesis](https://developer.mozilla.org/en-US/docs/Web/CSS/font-synthesis), [MDN: text-rendering](https://developer.mozilla.org/en-US/docs/Web/CSS/text-rendering), [MDN: -webkit-tap-highlight-color](https://developer.mozilla.org/en-US/docs/Web/CSS/-webkit-tap-highlight-color)
- **React Flow theming with `--xy-*` variables.** React Flow ships one stylesheet, `@xyflow/react/dist/style.css`, that the app must import for the canvas, handles, background, and controls to render. Its rules read colours through CSS variables named `--xy-…`, each falling back to a `--xy-…-default` value the library sets on `.react-flow`. Declaring the plain variable on `.react-flow` is the supported way to recolour the canvas without touching the library. [React Flow: Theming](https://reactflow.dev/learn/customization/theming), [React Flow: Background](https://reactflow.dev/api-reference/components/background), [React Flow: Controls](https://reactflow.dev/api-reference/components/controls), [React Flow: Handle](https://reactflow.dev/api-reference/components/handle)

## Walkthrough

### web/src/index.css

**L1–L1** — `@import 'tailwindcss';` brings in the framework. The Tailwind Vite plugin (`web/vite.config.ts:3,6`) resolves this at build time; the browser never sees an `@import`. It expands to a layer-order declaration, `@layer theme, base, components, utilities;`, and three layered imports: the default theme, Preflight, and the utilities. It must be the first statement because CSS requires `@import` before other rules and because the layer order it declares governs everything below. Without this line the `@theme` block at L5 would be ordinary CSS with no effect, no utility class in `web/src` would exist, and `var(--color-canvas)` at L82 would resolve to nothing. `web/src/main.tsx:7` is the only importer of this file; `README.md:409` calls it "The only stylesheet".

**L2–L2** — The comment states the one cascade fact that justifies L3: React Flow's stylesheet declares no `@layer`, and unlayered rules beat every layered rule. Tailwind's base, components, and utilities are all layered, so without intervention the library would win every argument.

**L3–L3** — `@import '@xyflow/react/dist/style.css' layer(base);` imports React Flow's default styles, which the canvas needs (`README.md:184` points at React Flow; the package is `web/package.json:17`), and files them into Tailwind's `base` layer. Inside a layer, source order decides, so these rules sit after Preflight and before this file's own `@layer base` block at L73. The practical effect is on handles: React Flow's `.react-flow__handle` rule sets a 6px size, a background, and a 1px border, and `web/src/components/CanvasNode.tsx:6` overrides all three with the utilities `size-2 border-2 border-white bg-node-handle`. Utilities win only because React Flow is now in an earlier layer. Remove `layer(base)` and the handles revert to the library's small 6px dots (still filled with `--color-node-handle`, because L138 keeps feeding the library's own rule) while every class on them is silently ignored. Vite resolves the bare package path through `web/node_modules`, and the merged output lands in `web/dist/assets/` for `internal/httpapi/api.go:122` to serve.

Components that want a specific value say so: `leading-tight` at `Badge.tsx:28`, `leading-normal` at `Sidebar.tsx:24`, `leading-[1.6]` at `WorkflowCanvas.tsx:134`.

**L81–L85** — The `body` rule is where three tokens enter the page. `background-color: var(--color-canvas)` paints the page (the only consumer of L18). `color: var(--color-ink)` sets the default text colour (the only consumer of L33); every component inherits it and only overrides where it wants a grey from L36-40 or a status colour. `font-size: 0.875rem` makes 14px the base size, the same value `text-sm` would give, so components only need a size class when they differ. Without this rule the page would be white, black, and 16px, and every spacing value in the components would be out of proportion.

**L86–L89** — Preflight makes links inherit their colour and decoration so they look like the surrounding text. This rule restores the two cues a reader expects, accent colour and underline, for plain links such as the ones in `web/src/pages/ErrorPage.tsx:24` and `web/src/pages/NotFoundPage.tsx:16`. The nav links are styled as tabs instead, so `web/src/components/AppHeader.tsx:10` cancels the underline with `no-underline`; that utility beats this base rule because of layer order.

**L90–L90** — The comment names the Preflight behaviour the next rule undoes: "Preflight makes headings inherit weight; the page design keeps them bold."

**L91–L95** — `h1`, `h2`, and `h3` get weight 700. Preflight sets headings to `font-weight: inherit`, so without this rule the page title at `web/src/components/PageHeading.tsx:17`, the panel headings at `web/src/components/StepList.tsx:10` and `web/src/components/ExecutionHistory.tsx:20`, and the run and step headings at `web/src/components/RunDetails.tsx:15`, `StepList.tsx:23`, and `ExecutionHistory.tsx:35` would all render at the body's normal weight. `StepList.tsx:23` and `ExecutionHistory.tsx:35` opt down to `font-medium`, which works only because utilities outrank this layer.

**L96–L100** — `h1` is 30px, with letter spacing pulled in by 1px and a line height of 1.25. Preflight gives headings `font-size: inherit`, so this is the default for a bare `<h1>`, but neither `<h1>` in the app takes its size from here. The page title at `web/src/components/PageHeading.tsx:17` sets `text-2xl lg:text-3xl` (24px, and 30px from the `lg` breakpoint, where it happens to match this value; those utilities also set their own line height), so what it keeps from this rule is the `-1px` letter spacing and the weight from L94. Preflight sets `code` to the mono font at `font-size: 1em`, which would be the surrounding 14px; this shrinks it so the endpoint line at `web/src/components/StepList.tsx:28` and the check output at `web/src/components/RunDetails.tsx:71` read as code without dominating the row.

The app has many bare `<button>` elements that must read as clickable: the sidebar items at `web/src/components/Sidebar.tsx:32`, the run rows at `web/src/components/ExecutionHistory.tsx:48`, the view tabs, the Run button at `web/src/pages/WorkflowsPage.tsx:176`, and the canvas tools at `web/src/components/WorkflowCanvas.tsx:94,97`. **L126–L130** — The keyboard focus ring for buttons and summaries: a 3px outline in `--color-focus`, offset 4px from the edge. `:focus-visible` limits it to keyboard focus so a mouse click does not leave a ring behind. Links and inputs are not covered here; they attach `focusRingClass` (`web/src/components/classes.ts:7-8`, offset 3px) at the call site, for example `web/src/components/AppHeader.tsx:10` and the input class at `classes.ts:12`. ## State and rendering

This file holds no JavaScript state, but it defines where visual state lives. The design tokens live as CSS custom properties on `:root`, emitted by Tailwind from the `@theme` block at L5-71 into the `theme` layer; any rule or utility anywhere in the app can read them with `var()`. The React Flow variables at L136-142 live on the `.react-flow` element and are visible only inside the canvas subtree. Nothing in the app changes a custom property at run time; the palette is fixed at build time, and `web/dist/assets/` contains the compiled result that `internal/httpapi/api.go:122` serves.

What changes at run time is the DOM, and the browser re-matches these rules whenever React commits a change. Four attributes carry the state this stylesheet reacts to. The `disabled` attribute that `web/src/pages/WorkflowsPage.tsx:178` sets from `starting || !!connectionError` triggers L118-121. The `aria-current="page"` that `web/src/components/Sidebar.tsx:35` sets from `selectedId` and that `Link` sets on the active nav item triggers the `aria-[current=page]:` utilities that use `surface-selected` and `ink-selected`. The `aria-pressed` that `web/src/components/ExecutionHistory.tsx:51` sets from `inspectedRun` triggers `surface-active` and the `accent-bar` inset shadow. The `selected` prop that React Flow passes to `CanvasNode` (`web/src/components/CanvasNode.tsx:8,13`) adds the `outline-node-http` class. Keyboard focus triggers L126-130 with no React involvement at all.

The data path from the API to a colour is short. TanStack Query fetches `GET /api/runs`, the `Run` object's `status` string reaches `StatusBadge`, `badgeTone` at `web/src/components/Badge.tsx:21-23` picks one of the literal class strings at `Badge.tsx:7-19`, Tailwind compiled that string into a rule that reads `--color-status-failed` and `--color-status-failed-bg` from L57-58, and the badge turns red. A poll every second (`web/src/pages/WorkflowsPage.tsx:45,50`, chapter 15) re-renders the component, but the browser repaints only when the class string actually changes.

Errors reach the user through three token groups. A failed request renders `ErrorBanner`, which is the danger trio at L63-65 and the app's only `role="alert"`. A failed workflows query flips the header dot to `offline` (L49) through `web/src/components/AppHeader.tsx:43`. A run whose final save failed keeps its real status badge and adds the amber `text-status-queued` note at `web/src/components/ExecutionHistory.tsx:67`, which is the stylesheet's expression of the `AGENTS.md` rule that `finalSaveFailed` "is a memory-only warning, not a new execution status". Nothing in the Playwright suite under `web/tests/` asserts a computed style, so a wrong colour here is caught by eyes, not by `make e2e`.

## Check yourself

1. The reader deletes `layer(base)` from L3 and nothing else. Which elements change, and why does no Tailwind class on them help?

<details><summary>Answer</summary>React Flow's stylesheet becomes unlayered, and unlayered rules beat every layered rule regardless of specificity. The elements React Flow styles directly are affected: the handles revert to the library's 6px size and 1px border (the fill stays the same colour, because L138 still feeds the library's rule), and the controls and background keep their library defaults except where the <code>--xy-*</code> variables at L136-142 still apply (those still work, because they are variables, not competing declarations). The utilities <code>size-2 border-2 border-white bg-node-handle</code> at <code>web/src/components/CanvasNode.tsx:6</code> live in the <code>utilities</code> layer, which is layered, so they lose. The comment at L2 exists to stop exactly this edit.</details>

2. Why must `--color-*: initial` at L15 come before `--color-white` at L16 rather than after L70, and what does a component get if it writes `bg-red-500` today?

<details><summary>Answer</summary>Inside <code>@theme</code> the later declaration wins. Placed after L70, the wipe would remove the project's own colours as well as Tailwind's, and every <code>bg-surface</code> and <code>text-text-muted</code> in the app would generate nothing. Placed first, it clears the defaults and L16-70 then define the only palette. A component that writes <code>bg-red-500</code> today gets no CSS and no error: Tailwind generates nothing for an unknown class, <code>npm --prefix web run typecheck</code> does not check class names, and the element simply has no background. The comment at L14 states the intent: "Only the project palette exists as utilities."</details>

3. No component anywhere uses `text-ink` or `bg-canvas`. How do `--color-ink` and `--color-canvas` reach the screen, and what does a component do when it wants a different text colour?

<details><summary>Answer</summary>They are applied once, on <code>body</code> at L82-83. <code>background-color</code> paints the page; <code>color</code> is an inherited property, so every element below <code>body</code> gets <code>--color-ink</code> without naming it. A component that wants a grey adds a utility such as <code>text-text-muted</code>, which sets <code>color</code> on that element and on everything it contains; the utility wins over inheritance because it is a declaration on the element itself, and it would also win over any base rule because the <code>utilities</code> layer is last.</details>

4. `web/src/components/StepList.tsx:23` renders `<h3 className="font-medium">`. L91-95 says `h3 { font-weight: 700 }` and a bare element selector has lower specificity than a class, so which rule wins and would the answer change if the specificities were reversed?

<details><summary>Answer</summary>The utility wins, and it would win even if the base rule had the higher specificity. Layer order is decided before specificity: L1 declares <code>theme, base, components, utilities</code>, the <code>h3</code> rule is in <code>base</code>, and <code>font-medium</code> is in <code>utilities</code>. A later layer beats an earlier one no matter how the selectors compare. Specificity only breaks ties within the same layer, which is also why this file's <code>@layer base</code> block overrides Preflight: same layer, later in source order.</details>

5. A run is marked `interrupted` by startup cleanup, and another run finished but its final save failed. Which colours does each get, which file decides, and why are they not the same colour?

<details><summary>Answer</summary><code>web/src/components/Badge.tsx:18</code> maps <code>interrupted</code> to <code>bg-status-failed-bg text-status-failed</code>, the red pair at L57-58, because from the user's side the run did not complete. The run with a failed final save keeps whatever status it reached (for example the green pair at L51-52 for <code>succeeded</code>) and <code>web/src/components/ExecutionHistory.tsx:67</code> adds a note in <code>text-status-queued</code>, the amber at L53. They differ because <code>AGENTS.md</code> requires distinguishing execution outcome from save failure: <code>finalSaveFailed</code> is a memory-only warning, not a status, so it borrows the warning colour rather than the failed one.</details>

6. The reader adds `--text-2xs--line-height: 1rem;` under L9. What changes on the page, and which comment in this file becomes wrong?

<details><summary>Answer</summary>The <code>text-2xs</code> utility now sets <code>line-height: 1rem</code> as well as <code>font-size</code>, so every 10px label stops inheriting the <code>normal</code> line height from L79 and gets a 16px line box instead. Sidebar rows, badges, and the history list grow by the difference, and the fixed sizes measured in the components (such as <code>lg:max-h-[462px]</code> at <code>web/src/components/ExecutionHistory.tsx:44</code>) show fewer rows. The comment at L78, "text-2xs elements inherit this line height", becomes false, and <code>leading-tight</code> at <code>Badge.tsx:28</code> would now be overriding a value the token set instead of an inherited one.</details>
