## Role in the system

These three files test the `Runner` in `internal/engine/runner.go`, which chapter 6 walked through. The runner is the part of the server that decides whether a start request is admitted, queued, or refused; that runs each admitted workflow on its own goroutine with steps in order; that holds a slot until the final save has returned; and that cancels everything on shutdown without repeating an action. The eleven tests here feed the runner hand-built definitions and three fake dependencies, the executor and the two save callbacks (`runner.go:51`, `:55`, `:60`), and read back snapshots through `Get` and `List` (`runner.go:159`, `:166`) plus the arguments the fakes receive. No test opens a socket, a file, or a database. The URL `http://localhost` inside the shared fixture (`internal/engine/runner_test.go:16-17`) is never fetched, because every test replaces the executor with a closure. That is the AGENTS.md:134-137 rule: "Use fake executors, temporary databases, local test servers, and controlled clocks/channels; routine tests must not depend on live homelab services."

On the real path from a browser click to a saved run, the runner sits in the middle. `POST /api/workflows/{id}/runs` (`internal/httpapi/api.go:50`) calls `runner.Start(definition)` (`api.go:65`); `Start` saves the new run through the `RecordNewRun` callback, which in production is `store.CreateRun` (`cmd/server/main.go:107-108`, `internal/store/runs.go:17`); the handler answers `202` with the snapshot (`api.go:83-84`). The run's goroutine (`runner.go:197`, `:216`) calls the executor and the `UpdateSavedRun` callback, which is `store.UpdateRun` (`main.go:109-110`, `runs.go:68`). The scheduler starts runs through the same `Start` (`internal/schedule/scheduler.go:125`). On SIGTERM, `main.go:138-140` closes the scheduler and then the runner before SQLite is closed by the deferred cleanup. The tests in this chapter replace both ends of that path, the store and the executor, with closures, so they can make a save fail, block an executor, or hold a final save open at exactly the moment a rule is supposed to hold.

What the three files divide between them: `runner_concurrency_test.go` proves the limits and the ownership of slots and guards under simultaneous starts, and the 100-entry memory bound; `runner_queue_test.go` proves the FIFO queue, that a failed save never blocks later work, and that every concurrent `Close` waits for the queued-run cleanup; `runner_shutdown_test.go` proves, under a fake clock, which execution outcomes survive shutdown and how the bounded final-save retry behaves. Together they cover the rules in AGENTS.md:78-99 that the roadmap set for M1: "run limits, queue limits, and same-workflow overlap rules hold under simultaneous start requests" and "Verify concurrent admission, history reads, and shutdown with Go's race detector" (`docs/roadmap.md:176`). `make test` runs them with `-race` (`Makefile:16`).

## Concepts you need

- **Same-package test files and `testing.T`.** A `_test.go` file that declares `package engine` compiles into the test binary with the package itself, so it can call unexported helpers and read unexported fields such as `runner.activeRuns` (`runner_concurrency_test.go:299`). `t.Fatal` and `t.Fatalf` stop the current test at once; `t.Error` and `t.Errorf` record a failure and continue. `Fatal` may only be called from the goroutine running the test; a fake that runs on another goroutine must use `Error`. `t.Helper()` makes a failure inside a helper report the caller's line. [testing](https://pkg.go.dev/testing)
- **Table-driven tests and subtests.** A slice of case structs plus `t.Run(name, func(t *testing.T) {...})` gives each case its own name, so `go test -run 'TestName/case_name'` runs one of them, and a failure names the case. Inside the closure the parameter `t` is the subtest's `T`, which shadows the outer one. [testing: Subtests](https://pkg.go.dev/testing#hdr-Subtests_and_Sub_benchmarks)
- **Fakes through function-typed dependencies.** The runner takes three functions (`runner.go:51-60`) instead of an interface. A test passes a closure for each, so "the save fails once" or "the executor blocks until canceled" is written in a few lines. The closures capture test variables such as channels, which is how the test and the runner talk to each other. [A Tour of Go: Function closures](https://go.dev/tour/moretypes/25)
- **Goroutines and channels.** `go f()` starts `f` on a new goroutine. A channel moves values between goroutines: an unbuffered channel blocks the sender until a receiver is ready; a buffered channel (`make(chan string, 8)`) holds that many values first. `chan struct{}` carries no data, only the event. A receive-only type `<-chan T` stops a function from sending by mistake. [A Tour of Go: Channels](https://go.dev/tour/concurrency/2), [Buffered channels](https://go.dev/tour/concurrency/3)
- **Closing a channel as a broadcast.** `close(ch)` makes every current and future receive on `ch` return at once with the zero value. The tests use it as a release signal that wakes every waiter and stays "released" forever. Closing a channel twice panics, so a channel that may already be closed is closed through a guard (`select` with `default`) or a `sync.Once`. [Spec: Close](https://go.dev/ref/spec#Close)
- **`select`, timeouts, and the non-blocking `default`.** `select` waits on several channel operations and runs the first one ready. Pairing a receive with `case <-time.After(2 * time.Second)` turns "wait for the runner" into "wait at most two seconds, then fail". A `select` with a `default` branch never blocks: it checks whether something is ready right now, which is how a test asserts that nothing has happened yet. [A Tour of Go: Select](https://go.dev/tour/concurrency/5), [Default selection](https://go.dev/tour/concurrency/6)
- **`sync.Once` and `sync/atomic`.** `once.Do(f)` runs `f` the first time only, even when called from several goroutines. `atomic.Int32` is a counter that many goroutines can `Add` and `Load` without a mutex. Both let a fake keep bookkeeping that is safe under `go test -race` without depending on the runner's own lock. [sync.Once](https://pkg.go.dev/sync#Once), [sync/atomic](https://pkg.go.dev/sync/atomic)
- **`defer` runs last-in, first-out.** Several `defer` statements run in reverse order when the function returns, including on `t.Fatal`, which exits the test function through `runtime.Goexit`. The tests register `defer runner.Close()` first and a "release the blocked save" defer second, so the release runs before `Close` waits. [A Tour of Go: Defer](https://go.dev/tour/flowcontrol/12), [Effective Go: Defer](https://go.dev/doc/effective_go#defer)
- **Context cancellation inside a fake.** An executor or save callback receives a `context.Context`. `<-ctx.Done()` blocks until that context is canceled; `ctx.Err()` is then `context.Canceled` or `context.DeadlineExceeded`; `ctx.Deadline()` reports whether and when a timeout will fire. A fake that waits on `ctx.Done()` behaves like a real network call that honors cancellation, and it also guarantees the goroutine exits when the runner shuts down. [context](https://pkg.go.dev/context)
- **`errors.Is` and wrapped sentinels.** The runner returns fixed error values (`runner.go:17-22`), sometimes wrapped with `fmt.Errorf("%w ...")` to add detail (`runner.go:124`, `:143`). `errors.Is(err, ErrCapacity)` finds the sentinel inside the wrapper; comparing with `==` would fail on the wrapped ones. [errors.Is](https://pkg.go.dev/errors#Is)
- **Range over an integer and per-iteration loop variables.** Since Go 1.22, `for range 24 { ... }` loops 24 times and `for i := range 24` counts from 0 to 23. Each iteration gets a fresh `i`, so a goroutine closure that captures `i` (`runner_concurrency_test.go:124-126`) sees its own value. Before 1.22 that was a classic bug. [Go 1.22 release notes: for loops](https://go.dev/doc/go1.22#language)
- **`testing/synctest` and the fake clock.** `synctest.Test(t, f)` (Go 1.25) runs `f` in a "bubble" whose clock starts at 2000-01-01 00:00 UTC and advances only when every goroutine in the bubble is durably blocked: on a channel created in the bubble, a `select` over such channels, `sync.WaitGroup.Wait` whose `Add` happened in the bubble, or `time.Sleep`. Timers, `time.After`, and `context.WithTimeout` created inside use the fake clock, so a 100 ms retry delay passes with no real wait. When `f` returns, every goroutine in the bubble must have exited, or the test fails as a deadlock. [testing/synctest](https://pkg.go.dev/testing/synctest)
- **The race detector and happens-before.** `go test -race` reports two goroutines touching the same memory without synchronization. A channel send that completes before the matching receive, a mutex unlock before the next lock, and `WaitGroup.Done` before `Wait` returns each establish an order the detector accepts. These tests read slices that the run goroutine appended to only after `runner.Close()` returned, because `Close` ends with `wg.Wait()` (`runner.go:190`). [Race detector](https://go.dev/doc/articles/race_detector), [The Go Memory Model](https://go.dev/ref/mem)
- **`reflect.DeepEqual`.** Compares two values recursively: slices element by element, structs field by field, and pointers by the values they point to. The tests use it to compare lists of step ids and whole `Run` snapshots, including `*CheckResult` outputs. [reflect.DeepEqual](https://pkg.go.dev/reflect#DeepEqual)
- **`encoding/json` and `omitzero`.** `json.Marshal` turns a struct into JSON text using its struct tags. `omitzero` (Go 1.24) drops a field whose value is its type's zero value, calling `IsZero` for `time.Time`; `omitempty` would not drop a zero `time.Time` because a struct is never "empty". The queue test marshals a queued run and searches the bytes for `startedAt` to prove the tag works. [encoding/json Marshal](https://pkg.go.dev/encoding/json#Marshal)
- **Slicing a slice literal.** `[]string{"one", "two"}[:n]` builds a slice and keeps its first `n` elements, so one expression gives `[]`, `["one"]`, or `["one","two"]` for `n` of 0, 1, or 2. [A Tour of Go: Slices of slices](https://go.dev/tour/moretypes/9)

## Check yourself

1. In `TestRunKeepsItsSlotUntilFinalSaveReturns`, why does starting `a` fail with `ErrWorkflowBusy` while starting `b` fails with `ErrCapacity`, and which production lines are responsible for both answers?

<details><summary>Answer</summary>
Both starts happen while <code>a</code>'s goroutine is blocked inside the final save, which <code>finishRun</code> calls at <code>runner.go:309</code> from <code>runner.go:286</code>. The guard delete (<code>runner.go:290</code>) and <code>activeRuns--</code> (<code>runner.go:291</code>) come after that call returns, so <code>busyWorkflows</code> still contains <code>a</code> (<code>runner.go:119-121</code> returns <code>ErrWorkflowBusy</code>) and <code>activeRuns</code> is still 1 with a queue limit of 0 (<code>runner.go:122-124</code> returns <code>ErrCapacity</code>). The test uses two different ids on purpose: the same id would always hit the busy check first and never reach the capacity check.
</details>

2. The save fake in `TestCloseWaitsForQueuedCancellationSave` uses `t.Errorf` and `t.Error` (L206, L209), while the rest of the file uses `t.Fatal`. Why, and what would go wrong with `Fatal` there?

<details><summary>Answer</summary>
The fake runs on the goroutine that called <code>Close</code>, inside <code>cancelQueued</code> (<code>runner.go:200-214</code>), not on the test goroutine. <code>Fatal</code> calls <code>FailNow</code>, which the <code>testing</code> docs say must be called from the goroutine running the test. Called elsewhere it marks the test failed but does not stop the test function, and it ends the calling goroutine with <code>runtime.Goexit</code>. Deferred calls still run, so <code>wg.Done</code> at <code>runner.go:201</code> would fire, but the loop would skip every remaining queued entry: no snapshot published, no guard deleted, and the test's later assertions would be checking a runner the production code never produces. If the test function had already returned, the call would panic instead. <code>Error</code> records the failure, lets the cleanup finish, and the test fails at the end. The same reasoning applies to <code>t.Error</code> at <code>runner_shutdown_test.go:77</code>, which runs on the run goroutine.
</details>

3. In `TestShutdownKeepsCompletedExecutionOutcome`, the cases "final executor succeeds" and "earlier executor succeeds" both have an executor that returns a healthy result after cancellation. Why is one run `succeeded` and the other `canceled`?

<details><summary>Answer</summary>
<code>allStepsSucceeded := err == nil && i == len(definition.Steps)-1</code> at <code>runner.go:261</code>. When step two, the last step, returns without error, the flag is true, and the cancellation branch at <code>runner.go:262-268</code> breaks out without changing the status from <code>succeeded</code>. When step one returns without error, <code>i</code> is not the last index, the flag is false, and <code>runner.go:264-266</code> sets <code>canceled</code> because step two can never run; <code>finishRun</code> then marks step two <code>skipped</code>. <code>README.md:173-176</code> states both outcomes: a run whose final step returned successfully stays Completed; a run that shutdown stopped before its remaining steps is Canceled.
</details>

4. `TestQueueIsFIFOAndWaitsForFinalSave` edits `definition.Steps[0].Name` after `Start` has returned (L71). What would happen in production without `slices.Clone` at `runner.go:109`, given how the API handler calls `Start`?

<details><summary>Answer</summary>
A slice value is a header pointing at a shared backing array. The handler passes the same loaded <code>definition</code> value on every request (<code>api.go:65</code>), and the scheduler passes its own copy of the same loaded definitions (<code>scheduler.go:125</code>). Without the clone, every queued entry's <code>Steps</code> would point at that one shared array, so any in-place edit, including a future workflow reload or editor feature, would change work that was already admitted and saved with a different snapshot. The test proves the clone by checking that <code>b</code>'s step one output still reads <code>One</code> (L117).
</details>

5. `TestSimultaneousStartsRespectCapacityAndWorkflowOverlap` requires `recorded` to equal the number of accepted runs. What does that prove about rejected starts, and which order of statements in `Start` makes it true?

<details><summary>Answer</summary>
Rejected starts are never saved. In <code>Start</code>, the closed, busy, and capacity checks at <code>runner.go:116-125</code> return before the <code>recordNewRun</code> call at <code>runner.go:136-145</code>, and only a successful save reaches the state changes at <code>runner.go:146-155</code>. So the saved count, the accepted count, and <code>len(List())</code> all equal the number of starts that passed every check. <code>README.md:165</code> states it as "rejected starts are not saved as executions", and AGENTS.md:83-84 adds that a failed save must consume no capacity, which <code>TestQueueSaveFailuresDoNotBlockFollowingWork</code> covers from the other side.
</details>

6. Why does `failedAdmission` in `runner_queue_test.go:129` get to be a plain `bool`, while `recorded` in `runner_concurrency_test.go:103` is an `atomic.Int32`?

<details><summary>Answer</summary>
<code>failedAdmission</code> is read and written only inside the <code>RecordNewRun</code> fake, which <code>Start</code> calls while holding the runner's mutex (<code>runner.go:114</code>, <code>:140</code>), and that test calls <code>Start</code> from one goroutine in sequence, so no two accesses can ever overlap. <code>recorded</code> is written by 24 goroutines calling <code>Start</code> at once and then read by the test goroutine. The runner's mutex would in fact serialize those writes today, but AGENTS.md:81-82 describes holding the lock during the initial save as the current choice, not a promise. An atomic keeps the test's own bookkeeping correct under <code>-race</code> no matter how the runner locks.
</details>
