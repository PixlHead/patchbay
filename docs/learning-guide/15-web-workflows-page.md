# 15. The Workflows page: polling, starting runs, selection

Files: [web/src/pages/WorkflowsPage.tsx](../../web/src/pages/WorkflowsPage.tsx)

Revision: commit 1c4786e

## Role in the system

`WorkflowsPage.tsx` is the runner's screen. It is the only file in the frontend that talks to the Go server: the three `request` calls at L44, L49, and L56 are the only callers of `request` in `web/src/api.ts:65`. Two of them are polls. Every second while the page is mounted, it asks `GET /api/workflows` (`internal/httpapi/api.go:37`) for the loaded definitions and `GET /api/runs` (`api.go:89`) for the newest 100 runs. The third is the one write the frontend can make: a `POST /api/workflows/{id}/runs` (`api.go:50`) when the user clicks Run workflow. `AGENTS.md:58` names the file's three jobs in the code map, "polled queries, run start, selection", and this chapter follows that order.

Data comes in from four places. The two lists arrive through TanStack Query (chapter 14 covers the request helper and the client defaults). The selected workflow id, the local drafts, and the per-workflow canvas layouts come from the workspace context that `App.tsx` owns (chapter 13). The open view, `canvas` or `details`, comes from the URL search params that `router.tsx:28-32` validates. The run the user wants to inspect is the one piece of state this page keeps for itself (L36). From these the page derives everything it draws: which workflow is selected, whether it is a saved workflow or a local draft, which runs belong to it, and which run to show in detail. What goes out is the POST, a patch to the query cache (L62-65), updates to the context (L86, L138-141), a URL change (L97), and the rendered tree of components that chapter 16 and the canvas chapter cover one by one.

On the path from a click to a saved run, this file is the first and the last stop in the browser. The click lands on L179, `startRun` (L91) calls `startMutation.mutate` (L93), the mutation function (L55-59) posts through `request`, the Vite proxy (`web/vite.config.ts:11`) or the Go file server passes it to `api.go:50`, and `Runner.Start` at `internal/engine/runner.go:105` checks admission under its mutex and saves the run before accepting it (`runner.go:136-145`). The 202 response (`api.go:84`) comes back into `onSuccess` (L60), which shows the run at once (L62-66). From then on the page no longer owns anything: the run belongs to the runner's context, not the request (`runner.go:138-139`, `README.md:451`), and the page just keeps polling until the saved status changes. `docs/roadmap.md:209` ends with the rule this page upholds by design: "The browser must never execute workflow nodes itself."

## Concepts you need

- **Function components and the rules of hooks.** A React component is a function that runs on every render and returns elements. Hooks are the functions whose names start with `use`; they attach state or subscriptions to the component. Every hook must be called at the top level of the component, in the same order on every render, never inside an `if` or a loop. L33-L38 and L42-L68 call eight hooks in a fixed order before any condition. [React: Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks)
- **`useState`.** `const [runId, setRunId] = useState('')` gives the component one value that survives re-renders and a setter that schedules a re-render. The variable does not change until the next render. This page has exactly one such value (L36); everything else is either read from elsewhere or computed on the spot. [React: useState](https://react.dev/reference/react/useState)
- **Derived values instead of state.** When a value can be computed from props, context, or other state, compute it during render instead of storing it. L70-L83 compute thirteen values this way. The gain is that they can never go stale: if the poll brings a new list, the next render recomputes `selected`, `history`, and `inspectedRun` from it. Storing them would need extra code to keep them in sync. [React: Avoid redundant state](https://react.dev/learn/choosing-the-state-structure#avoid-redundant-state)
- **Context through a custom hook.** `useWorkspace()` (L33-34) is a custom hook around `useContext` (`web/src/workspace.ts:18-22`). It returns the object that `App.tsx:36-47` provides. Reading it here means the page shares the selection and drafts with the New workflow page without either page passing props to the other. [React: useContext](https://react.dev/reference/react/useContext)
- **Conditional rendering with `&&`, ternaries, and fragments.** In JSX, `{cond && <X />}` draws `X` only when `cond` is truthy, `{a ? <X /> : <Y />}` picks one branch, and `<>...</>` groups several elements without adding a DOM node. L114, L133, L147, L150, L175, and L190 are all branches of this kind. One trap: `{0 && <X />}` draws the `0`, so conditions should be booleans or strings, never counts. [React: Conditional rendering](https://react.dev/learn/conditional-rendering), [React: Fragment](https://react.dev/reference/react/Fragment)
- **The `key` prop as a reset switch.** React reuses a component instance across renders when its type and position stay the same. Giving it a `key` that changes tells React to throw the old instance away and mount a fresh one, which resets all of its internal state. L135 uses this so the canvas starts over for each workflow. [React: Resetting state with a key](https://react.dev/learn/preserving-and-resetting-state#resetting-a-form-with-a-key)
- **Passing functions down.** A parent gives a child a function to call when something happens: `onSelect={chooseWorkflow}` (L109), `onChange={showView}` (L113), `onClick={startRun}` (L179), `onInspect={setRunId}` (L196). The child calls it; the parent decides what changes. A state setter can be passed directly when its signature fits. [React: Responding to events](https://react.dev/learn/responding-to-events)
- **TanStack Query: `useQuery`, query keys, and status flags.** `useQuery({ queryKey, queryFn })` runs `queryFn`, caches the result under `queryKey`, and returns an object whose `data`, `isPending`, and `error` fields describe the current state. `isPending` is true only until the first attempt settles, with data or with an error; `error` is set when the latest fetch failed, and `data` keeps the last successful result even then. The key is an array (`['workflows']`) so related keys can be grouped later. [TanStack Query: useQuery](https://tanstack.com/query/v5/docs/framework/react/reference/useQuery), [TanStack Query: Query keys](https://tanstack.com/query/v5/docs/framework/react/guides/query-keys)
- **TanStack Query: polling with `refetchInterval`.** Setting `refetchInterval: 1000` makes the query refetch every second while a component using it is mounted. If a fetch is still in flight when the next tick arrives, the library reuses that fetch instead of starting another, so requests never pile up. The interval keeps running after an error, which is why L117 can promise "Retrying automatically". [TanStack Query: Important defaults](https://tanstack.com/query/v5/docs/framework/react/guides/important-defaults)
- **TanStack Query: cancellation with `AbortSignal`.** `queryFn` receives a `signal`. If the function hands it to `fetch`, the library knows the request can be aborted and does so when the query is cancelled, for example when the page unmounts mid-request. If the function ignores the signal, the request runs to completion in the background. [TanStack Query: Query cancellation](https://tanstack.com/query/v5/docs/framework/react/guides/query-cancellation), [MDN: AbortSignal](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal)
- **TanStack Query: `useMutation`.** A mutation is a write. `useMutation({ mutationFn, onSuccess })` returns `mutate` to start it, `isPending` while it runs, `error` if it failed, and `reset` to clear that error. `mutate` never throws; failures land in `error`. Mutations do not retry or poll on their own. [TanStack Query: Mutations](https://tanstack.com/query/v5/docs/framework/react/guides/mutations), [TanStack Query: useMutation](https://tanstack.com/query/v5/docs/framework/react/reference/useMutation)
- **TanStack Query: `useQueryClient` and `setQueryData`.** `useQueryClient()` returns the client from `main.tsx:11`. `client.setQueryData(key, updater)` writes into the cache directly, and every `useQuery` with that key re-renders with the new value. It is how a mutation response can appear on screen before the next poll. [TanStack Query: Updates from mutation responses](https://tanstack.com/query/v5/docs/framework/react/guides/updates-from-mutation-responses), [TanStack Query: QueryClient.setQueryData](https://tanstack.com/query/v5/docs/reference/QueryClient#queryclientsetquerydata)
- **TanStack Router: `useSearch` and `useNavigate`.** `useSearch({ from: '/workflows' })` returns the search params of that route after its `validateSearch` has run, so `view` is typed as `'canvas' | 'details'`, never `undefined`. `useNavigate()` returns a function that changes the URL; `replace: true` overwrites the current history entry instead of adding one. [TanStack Router: Search params](https://tanstack.com/router/latest/docs/framework/react/guide/search-params), [TanStack Router: useNavigate](https://tanstack.com/router/latest/docs/framework/react/api/router/useNavigateHook)
- **React Flow, seen from outside.** This page does not import React Flow. It renders `WorkflowCanvas`, which does. Two facts about React Flow matter here: it keeps its own internal store of viewport and node state, and its `fitView` prop (`WorkflowCanvas.tsx:121`) fits the nodes into view once, on mount. Both are why L135 remounts the canvas per workflow. [React Flow: ReactFlow component props](https://reactflow.dev/api-reference/react-flow)
- **Tailwind utility classes and breakpoints.** Every `className` is a list of small single-purpose classes. A `md:` or `lg:` prefix applies the class only from that screen width up, so `flex-col md:flex-row` (L104) stacks on phones and sits side by side on tablets. `min-h-0` on a flex child lets it shrink below its content height, which is what lets an inner column scroll instead of the whole page. [Tailwind: Responsive design](https://tailwindcss.com/docs/responsive-design), [Tailwind: min-height](https://tailwindcss.com/docs/min-height)
- **TypeScript unions and `in` narrowing.** `Workflow | LocalWorkflow` is a union: a value is one or the other. `'steps' in selected` (L80) is a type guard: inside the true branch TypeScript knows the value is a `Workflow`, because only that type has a `steps` field. `??` returns its right side when the left is `null` or `undefined`, and `?.` stops a chain at the first `undefined`. [TypeScript: The `in` operator narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#the-in-operator-narrowing), [MDN: Nullish coalescing](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Nullish_coalescing)
- **The ARIA tabs pattern and live regions.** A tab bar is `role="tablist"` with `role="tab"` buttons; the content is `role="tabpanel"`; `aria-controls` and `aria-labelledby` link each tab to the panel by id. `role="status"` and `role="alert"` mark text that screen readers announce when it appears. The Playwright tests find elements by these roles, not by CSS classes. [WAI-ARIA APG: Tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/), [MDN: ARIA alert role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/alert_role)
- **`encodeURIComponent` and the `void` operator.** `encodeURIComponent(id)` escapes characters that would change the meaning of a URL path. `void expr` evaluates `expr` and discards the result; in front of a promise it says "I know this returns a promise and I am not waiting for it." [MDN: encodeURIComponent](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/encodeURIComponent), [MDN: void operator](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/void)

"A refresh still in flight is reused, so requests never overlap": TanStack Query deduplicates a fetch for a key that is already fetching, so a slow server gets at most one outstanding request per list, not a growing backlog. **L42–L46** — `workflowsQuery`. Key `['workflows']`; function `request<Workflow[]>('/workflows', { signal })`, which becomes `GET /api/workflows` at `api.ts:66` and is answered by `api.go:37-49` with every loaded definition plus `nextRunAt` for scheduled ones. The `{ signal }` destructured from the function's argument is an `AbortSignal`; passing it into `request`, which hands that `{ signal }` object to `fetch` unchanged as its init (`api.ts:66`), makes the request abortable. Because the signal is consumed, TanStack Query aborts an in-flight poll when the page unmounts instead of letting it finish into a dead cache entry. `refetchInterval: 1000` is the poll. The client defaults in `queryClient.ts:7-11` complete the picture: no retries, keep polling in a hidden tab, and keep polling when the browser thinks it is offline.

**L47–L51** — `runsQuery`, the same shape for `['runs']` and `GET /api/runs`. The server returns the newest 100 runs across all workflows (`api.go:92`, `README.md:435`), with any retained unsaved final result overlaid (`api.go:98-100`). Two separate queries rather than one combined request because the two lists change at different rates and fail independently; when both have errored, L73 shows the workflows error ahead of the runs error. `docs/roadmap.md:88` plans to replace these polls with server-sent events "when the engine is ready" and to write events "into the TanStack Query cache instead of replacing it", which means these keys will stay and only the refetch mechanism will change.

**L53–L53** — The comment, "Saved running statuses can outlive a server process; Start enforces capacity", explains a decision that is visible only by its absence: the Run button at L178 is not disabled when the newest run says `running`. A run that was in progress when the server died stays `running` in SQLite until the next startup marks it `interrupted` (`AGENTS.md:98-99`), and even a live `running` status is only a snapshot from up to a second ago. The server's admission check at `runner.go:119-120` is the only reliable answer, so the page asks it by posting and shows the refusal if there is one. `AGENTS.md:131` states the general rule: "Keep backend validation authoritative." The test `an old unfinished run does not disable starting another workflow` (`web/tests/workflows.spec.ts:97-127`) pins this down: a stale `running` run is served, the button is enabled, the click gets a 409, and the message is shown.

**L54–L59** — `startMutation`. `mutationFn` receives the workflow id passed to `mutate` (L93) and posts to `/workflows/{id}/runs`. `encodeURIComponent(id)` escapes the id before it enters the path. Today ids match `^[a-z0-9][a-z0-9_-]{0,63}$` (`internal/workflow/workflow.go:61`), so the call changes nothing, but it costs nothing and protects the path if the rule ever loosens. `method: 'POST'` with `headers: { 'Content-Type': 'application/json' }` and no `body` is exactly what the server demands at `api.go:53-60`: a 415 without the header, a 400 with any body. The comment at `api.go:51-52` says why: requiring JSON "prevents cross-site HTML forms from triggering checks on this unauthenticated localhost prototype", because a plain HTML form cannot send that content type. `AGENTS.md:113-114` keeps "the JSON requirement on run-start requests" as a standing rule, and `README.md:438` tells users the same. Removing the header line here would turn every click into a 415 error banner. The mutation also inherits `networkMode: 'always'` from `queryClient.ts:14`, so a browser that believes it is offline still tries the loopback server.

**L60–L67** — `onSuccess` runs with the parsed 202 body, an `engine.Run` with status `running` or `queued` (`api.go:84`, `README.md:164`). The comment at L61 states the intent: "Show the new run at once; the next poll replaces the list with the server order." L62-65 call `setQueryData` on `['runs']` with an updater. `previous = []` is a default parameter for a `['runs']` entry that holds nothing yet. That is possible: the button is drawn as soon as the workflows list has arrived (L175), so a click can land in the brief window before the first runs response, or after a first runs poll that failed and left `data` undefined. The updater puts the new run first and filters out any existing entry with the same id. That filter handles a real race: the poll at L47 may have fetched the run between the server saving it (`runner.go:140`) and this callback running, so without the filter the list could briefly hold the run twice, and React would warn about duplicate keys in `ExecutionHistory.tsx:49`. This is not an optimistic update; it uses the server's own response, so nothing has to be rolled back. The order is a guess at the server's order (newest first) that the next poll confirms within a second. L66 `setRunId(run.id)` points the history panel at the new run so the user watches it progress instead of whichever run was selected before.

**L80–L80** — `savedWorkflow` narrows `selected` to a `Workflow` using `'steps' in selected`. A `LocalWorkflow` has no `steps` (`canvasDraft.ts:11-16`); a `Workflow` always does (`api.ts:22`). ## State and rendering

Where each piece lives. The two server lists live in the TanStack Query cache under `['workflows']` and `['runs']`, inside the client created at `queryClient.ts:3` and provided at `main.tsx:11`; the cache outlives this page, which is why returning from the New workflow page shows the last lists at once (`README.md:221`). The mutation's `isPending` and `error` live in the `useMutation` observer, which belongs to this component instance and disappears on unmount. `runId` is component state (L36). `workflowId`, `localWorkflows`, and `canvasDrafts` live in `App` (`App.tsx:11-13`) and reach the page through context (L33-34). `view` lives in the URL hash and is validated by `router.tsx:28-32` on every navigation. The three class strings (L23-30) are module scope and never change. Everything at L70-83 is recomputed on every render from those sources and is never stored.

What triggers a re-render. A poll that returns different data updates the cache and re-renders this component; a poll that returns identical data leaves the cached reference in place, so the component is not re-rendered for nothing. A poll that fails sets `error` and re-renders, keeping `data`. `mutate` re-renders at start (`isPending` true) and at the end (`isPending` false plus `data` or `error`). `setQueryData` at L62 re-renders immediately with the patched list. `setRunId`, `selectWorkflow`, and `setCanvasDrafts` each re-render; when they run together inside `chooseWorkflow` React batches them. `navigate` at L97 changes the search params and re-renders with the new `view`. Unmounting the page, by going to `#/canvas`, destroys the two query observers, which stops both intervals and aborts a poll in flight; the cache keeps the last lists.

How the data reaches the screen. `GET /api/workflows` becomes `workflowsQuery.data` (L42-46), then `workflows` (L70), then the first part of `availableWorkflows` (L78), which the sidebar draws (L106). `workflowId` picks `selected` from that list (L79), and `'steps' in selected` decides whether it is a saved workflow (L80). `GET /api/runs` becomes `runs` (L71), is filtered by the selected id into `history` (L81), and `runId` picks `inspectedRun` from it (L82). `view` chooses the canvas (L134-144) or the Details column (L146-205). In the Details column, `savedWorkflow` feeds the eyebrow, the schedule line, the Run button, the step list, and the history; `selected` feeds the title and description. A click on Run posts (L93), the 202 body is pushed into the cache (L62-65) and chosen for inspection (L66), and the next poll replaces the pushed entry with the server's version, including step progress as the runner saves it (chapter 6).

How errors reach the user. A failed poll becomes `connectionError` (L73-74), which turns the header dot red (L102, `AppHeader.tsx:43-44`), shows the alert at L117, disables the Run button (L178), and hides the empty state (L147). A refused start becomes `actionError` (L76) and the alert at L119, cleared by the next start or by choosing another workflow (L88). Both come through `request` (`api.ts:68-77`), which turns a JSON error body into an `Error` with the server's sentence and a non-JSON failure into a sentence that names the Go server. A run that executed but could not be saved is not an error on this page at all: it arrives as `finalSaveFailed` on the run (`api.ts:58`), which `ExecutionHistory.tsx:66-70` and the run details draw, following `AGENTS.md:92-93`. A throw during render, including `useWorkspace` outside `App` (`workspace.ts:20`), is caught by the route boundary and drawn by `ErrorPage` (`router.tsx:55`). A throw inside a click handler would reach none of these, but the handlers here (L85-98) only call setters and `mutate`, which do not throw.

## Check yourself

1. The page has been open for a minute with two workflows and ten runs on screen. The Go server is stopped. Describe what the user sees over the next few seconds and name the lines that decide each part. Then the server comes back. What changes, and does anything need a click?

<details><summary>Answer</summary>Within a second a poll fails. <code>retry: false</code> at <code>queryClient.ts:7</code> means the failure is reported at once, so <code>connectionError</code> (L73-74) becomes the fetch error's message. The header dot turns red and reads "Disconnected" (L102, <code>AppHeader.tsx:43-44</code>), the alert at L117 appears with "Retrying automatically.", and the Run button is disabled (L178). The sidebar and the ten runs stay on screen, because a failed fetch does not clear <code>data</code>, so L70-71 still see the last good lists. "Connecting to your workspace…" does not appear, because <code>loading</code> (L72) is false once data exists. The polls keep ticking every second (L45, L50). When the server returns, the next successful poll clears <code>error</code>, the banner disappears, the dot turns green, and the button is enabled again, with no click. The test at <code>web/tests/workflows.spec.ts:67-74</code> walks through this sequence.</details>

2. L64 filters the previous list for `item.id !== run.id` before putting the new run first. Describe the timing that makes this filter necessary and what the user would see without it.

<details><summary>Answer</summary><code>Runner.Start</code> saves the run before the HTTP response is written (<code>runner.go:136-145</code>, <code>api.go:84</code>). The <code>['runs']</code> poll at L47-51 fires every second and can read that saved run before the 202 reaches <code>onSuccess</code> at L60. In that order the cache already holds the run when L62 runs. Without the filter the updater would prepend a second copy, the history panel would show the run twice for up to a second, and React would warn about two children with the same <code>key</code> at <code>ExecutionHistory.tsx:49</code>. The filter makes the patch safe in either order; the next poll then replaces the whole list with the server's version, as the comment at L61 says.</details>

3. Who owns a run after the 202 arrives, and what happens to it if the user closes the tab a moment later? Which lines and rules settle this?

<details><summary>Answer</summary>The runner does. L93 calls <code>mutate</code> and does not wait; L60-67 only update the cache and local state. On the server, <code>Runner.Start</code> admits the run under its mutex and hands it to the runner's own context (<code>runner.go:114-115</code>, <code>:138-139</code>), which <code>AGENTS.md:84-85</code> states as "Accepted runs belong to the runner's context, not the originating HTTP request." Closing the tab aborts nothing on the server; <code>api.go:155</code> notes that "A disconnected client cannot affect an already-admitted background run", and <code>README.md:451</code> says "The run continues after the request finishes or the browser closes." The page would merely stop polling. On reopening, the poll shows the run's saved progress.</details>

4. `chooseWorkflow` (L85-89) calls three setters in a fixed order. Explain the user-visible consequence of removing each one on its own.

<details><summary>Answer</summary>Remove <code>selectWorkflow(id)</code> and the sidebar click does nothing: L79 keeps finding the old id. Remove <code>setRunId('')</code> and switching from A to B still looks right, because B's history does not contain A's run id and L82 falls back to <code>history[0]</code>; but returning to A later reselects the run the user inspected before, and a run started on B in between is not what A shows. Remove <code>startMutation.reset()</code> and a 409 earned on A stays as the alert at L119 while B is open, blaming B for A's refusal, until the next click on Run on any workflow. The three lines are independent, which is why the handler is three statements rather than one.</details>

5. The newest run in the history says `running`, yet the Run button is enabled. Is this a bug? Trace what a click does in both the case where the run really is running and the case where it is a leftover from a crashed server.

<details><summary>Answer</summary>It is deliberate; the comment at L53 explains it. In both cases the click reaches <code>Runner.Start</code>. If the workflow really is queued or running, <code>runner.go:119-120</code> returns <code>ErrWorkflowBusy</code>, <code>api.go:69-70</code> maps it to 409, <code>api.ts:69-71</code> throws an <code>Error</code> with the server's sentence, and L119 shows it; the button is enabled again because <code>starting</code> is false. If the <code>running</code> row is a leftover, the server's <code>busyWorkflows</code> map does not contain it (startup cleanup marked it <code>interrupted</code> per <code>AGENTS.md:98-99</code>, or it is an old snapshot), so the start is accepted and a new run appears. Disabling the button from history would have made the second case impossible to recover from without a reload. The test at <code>workflows.spec.ts:97-127</code> covers the first case.</details>

6. `view` is in the URL and `runId` is in component state. Give one concrete behavior that would change if `runId` moved into the URL, and one that would change if `view` moved into component state.

<details><summary>Answer</summary>With <code>runId</code> in the URL, a reload would reopen the same run, and a link to a specific run would become possible; <code>docs/roadmap.md:83</code> plans exactly this "when the first link consumer arrives", such as a Discord alert link. Today a reload shows the newest run because L36 starts at <code>''</code>. With <code>view</code> in component state, a reload would always open the canvas (the component would start from its default), and the test at <code>workflows.spec.ts:90-91</code>, which reloads and expects Details to stay open, would fail. It would also make the New workflow page's tabs independent from this page's, which they already are, since each route validates its own search.</details>
