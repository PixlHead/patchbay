# 23. Tests: HTTP and TCP executors and result text

## Role in the system

These five files test the three production files from Chapter 7: `internal/nodes/httpcheck/http.go`, `internal/nodes/tcpcheck/tcp.go`, and `internal/nodes/resulttext/reason.go`. Those are the only files in Patchbay that open a network connection on the user's behalf, so their tests are where the project proves it can observe a real socket, a real timeout, and a real cancellation without ever contacting a service outside the test process. `AGENTS.md:134-137` sets the terms: "Use fake executors, temporary databases, local test servers, and controlled clocks/channels; routine tests must not depend on live homelab services, Discord, or paid model calls. Keep failure injection in tests." Every fixture here is a loopback listener, an in-memory pipe, a replaced function field, or a fake clock.

Data enters an executor exactly as it does in production. A browser click reaches `internal/httpapi/api.go:65`, which calls `runner.Start`; the runner's step loop calls `r.execute(r.ctx, step)` at `internal/engine/runner.go:247`; `cmd/server/main.go:151-162` switches on `step.Type` and calls `httpNode.Execute` or `tcpNode.Execute`. The tests skip those layers and call `Execute` directly with a `workflow.Step` (`internal/workflow/workflow.go:29-34`) and a context of their choosing. What comes back is the same pair the runner stores: a `workflow.CheckResult` value (`workflow.go:49-59`) and an `error`. The runner treats a non-nil error as a failed or canceled step (`runner.go:250-255`) and a nil error as a completed step whose `Output` is the result (`runner.go:257`), which is then written to SQLite and later shown in the browser.

So the central question these tests keep asking is: which of the two returns carries the news? The roadmap fixes the answer: "Represent a failed HTTP/TCP health check as a successful check operation with an `unhealthy` result and a reason. Reserve execution errors for invalid configuration or failure to carry out the operation" (`docs/roadmap.md:117`), and `AGENTS.md:91` repeats it as "Distinguish execution outcome, monitored-service health, and save failure." A refused port, a 503, a slow server, and a malformed response are all health data with a nil error. A canceled parent context is an engine outcome with a non-nil error and no reason text. The `resulttext` tests then prove that whatever text does get stored is bounded and valid UTF-8, because that text comes partly from an untrusted peer and will be saved into history unchanged (`README.md:262-268`).

## Concepts you need

- **Internal test packages.** All five files declare the production package name (`package httpcheck`, `package tcpcheck`, `package resulttext`), not a `_test` suffix. That lets them reach unexported fields: `node.client` (`http.go:18`) to close idle connections and swap TLS settings, and `node.dial` (`tcp.go:18`) to replace the real dialer with a fake. The production comment at `tcp.go:17` says that field exists for exactly this reason. [cmd/go: test packages](https://pkg.go.dev/cmd/go#hdr-Test_packages)
- **The `testing` package: `t.Run`, `t.Fatal`, `t.Error`, `t.Setenv`.** `t.Run` makes a named subtest with its own pass/fail line. `t.Fatal` stops the test at once and may only be called from the test's own goroutine; code running on a server goroutine, such as an `http.HandlerFunc`, must use `t.Error` instead, which records the failure and continues. `t.Setenv` sets an environment variable for the test and restores it afterward. [pkg.go.dev/testing](https://pkg.go.dev/testing)
- **Table-driven tests.** A slice of anonymous structs holds one row per case, and a loop runs the same body for every row inside `t.Run`. Three of the tests here are tables (`TestHTTPResponseLimits`, `TestTCPDialFailuresAndAddressFormatting`, `TestLimitReason`); adding a case means adding a row. The other looping tests range over a slice of codes or booleans instead. [Go wiki: TableDrivenTests](https://go.dev/wiki/TableDrivenTests)
- **`httptest.Server`.** `httptest.NewServer(handler)` starts a real HTTP server on a random loopback port and gives you its `URL`. `NewUnstartedServer` lets you set fields such as `EnableHTTP2` before calling `Start` or `StartTLS`. `StartTLS` uses a built-in self-signed certificate that covers `127.0.0.1`, `::1`, `example.com`, and `*.example.com`; `server.Certificate()` returns it so a client can trust it. `server.Listener.Addr()` is the real address. `Close` shuts the listener and waits for in-flight handlers. [pkg.go.dev/net/http/httptest](https://pkg.go.dev/net/http/httptest)
- **`http.Hijacker`.** A handler can call `w.(http.Hijacker).Hijack()` to take the raw `net.Conn` away from the server. After that, `net/http` no longer writes anything; the handler owns the bytes. This is how a test sends a response that a Go server would never produce, such as a status line that is not HTTP. [pkg.go.dev/net/http#Hijacker](https://pkg.go.dev/net/http#Hijacker)
- **`http.Transport` fields: `Proxy`, `DialContext`, `TLSClientConfig`, `MaxResponseHeaderBytes`, `Clone`.** The transport is the part of an HTTP client that opens connections. `Proxy` is a function that decides whether a request goes through a proxy; the shared `http.DefaultTransport` uses `ProxyFromEnvironment`. `DialContext` opens the TCP connection and can be replaced to redirect or observe dials. `TLSClientConfig` sets trusted roots. `MaxResponseHeaderBytes` caps the header bytes the client will read. `Clone` copies a transport so changes do not affect other clients. [pkg.go.dev/net/http#Transport](https://pkg.go.dev/net/http#Transport)
- **`ProxyFromEnvironment` and its cache.** Go reads `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` once per process, the first time any request asks, and remembers the answer in a `sync.Once`. It also skips the proxy for `localhost` and loopback addresses, and when `REQUEST_METHOD` is set it refuses to use `HTTP_PROXY` for plain-HTTP requests, returning an error from the policy instead of a proxy URL, because a CGI program's environment is attacker-controlled (`HTTPS_PROXY` is still honored). The proxy test is shaped around all three facts. [pkg.go.dev/net/http#ProxyFromEnvironment](https://pkg.go.dev/net/http#ProxyFromEnvironment)
- **Trusting a test certificate with `x509.CertPool` and `tls.Config`.** A `CertPool` is a set of root certificates. Putting the fixture's own certificate into a fresh pool and setting `tls.Config{RootCAs: pool}` makes the client accept that one certificate while still verifying names and signatures. It is the opposite of `InsecureSkipVerify`, which turns verification off. [pkg.go.dev/crypto/x509#CertPool](https://pkg.go.dev/crypto/x509#CertPool), [pkg.go.dev/crypto/tls#Config](https://pkg.go.dev/crypto/tls#Config)
- **`context`: cancellation, deadlines, and inheritance.** `context.WithCancel` gives a context and a `cancel` function; `context.WithTimeout` gives one that cancels itself after a duration. A child context is done as soon as its parent is, and a child's deadline can only be earlier than its parent's, never later. `ctx.Done()` is a channel closed on cancel; `ctx.Err()` is `context.Canceled` or `context.DeadlineExceeded`. Both executors build a child with the step timeout (`http.go:40`, `tcp.go:30`) and then ask the parent, not the child, whether the engine canceled them (`http.go:50`, `tcp.go:41`). [pkg.go.dev/context](https://pkg.go.dev/context)
- **`errors.Is` and sentinel errors.** `context.Canceled` and `context.DeadlineExceeded` are package-level error values. `errors.Is(err, context.Canceled)` reports whether `err` is that value or wraps it, which is the right way to test for it; comparing strings is not. [pkg.go.dev/errors#Is](https://pkg.go.dev/errors#Is)
- **Goroutines, channels, `close`, and non-blocking `select`.** `go f()` runs `f` concurrently. Receiving from a closed channel returns at once, so `close(started)` is a broadcast. A `select` with a `default` case never blocks: it sends or receives if it can and otherwise falls through. A buffered channel of size one plus such a `select` lets a handler record one fact without ever blocking a later request. [Tour: channels](https://go.dev/tour/concurrency/2), [Tour: select](https://go.dev/tour/concurrency/5)
- **Closures as fakes.** A closure is a function value that can read and write variables of the surrounding function, such as a `t`, a counter, or a `cancel`. The TCP tests assign a closure to `node.dial`; the proxy test assigns one to `transport.DialContext`. No mocking library is needed because the production code only calls a function of the right type. [Tour: function closures](https://go.dev/tour/moretypes/25)
- **`net` listeners, ephemeral ports, and deadlines.** `net.ListenTCP("tcp4", &net.TCPAddr{IP: 127.0.0.1})` with port zero asks the kernel for any free port; `listener.Addr().(*net.TCPAddr).Port` reads which one. `SetDeadline` on a listener bounds `Accept`; `SetReadDeadline` on a connection bounds `Read`, so a test that expects EOF fails in two seconds instead of hanging. [pkg.go.dev/net](https://pkg.go.dev/net)
- **`net.Pipe` and `io.EOF`.** `net.Pipe()` returns two connected in-memory `net.Conn` ends with no socket at all. Closing one end makes `Read` on the other return `io.EOF`. That makes "did the executor close the connection it was handed?" a one-line check. [pkg.go.dev/net#Pipe](https://pkg.go.dev/net#Pipe), [pkg.go.dev/io#EOF](https://pkg.go.dev/io#EOF)
- **`sync/atomic` counters.** `atomic.Int32` has `Add` and `Load` methods that are safe to call from several goroutines without a mutex. The proxy test's handlers run on server goroutines and increment; the test goroutine reads. [pkg.go.dev/sync/atomic#Int32](https://pkg.go.dev/sync/atomic#Int32)
- **Re-running the test binary as a child process.** `os.Args[0]` is the path of the running test binary, and `-test.run=^Name$` selects one test in it. `exec.CommandContext` runs it with a chosen environment and a deadline, and `CombinedOutput` returns everything it printed. This is the standard way to test behavior that depends on process-wide state such as environment caches. [pkg.go.dev/os/exec](https://pkg.go.dev/os/exec), [Testing flags](https://pkg.go.dev/cmd/go#hdr-Testing_flags)
- **`testing/synctest`: a fake clock.** `synctest.Test(t, f)` runs `f` in a bubble where timers and context deadlines use a fake clock that jumps forward only when every goroutine in the bubble is blocked. A 100 ms deadline fires instantly, and `time.Since` reports exactly 100 ms. [pkg.go.dev/testing/synctest](https://pkg.go.dev/testing/synctest), [Go blog: synctest](https://go.dev/blog/synctest)
- **Bytes versus runes, `utf8.ValidString`, `utf8.RuneStart`, `strings.ToValidUTF8`.** A Go string is bytes; `len` counts bytes, and a character such as `界` or `U+FFFD` takes three. `utf8.ValidString` reports whether the bytes are well-formed UTF-8. `utf8.RuneStart` says whether a byte begins a character, which is how a byte limit avoids cutting a character in half. `strings.ToValidUTF8` replaces each run of invalid bytes with a replacement string, and that replacement can make the string longer. [Go blog: strings](https://go.dev/blog/strings), [pkg.go.dev/unicode/utf8](https://pkg.go.dev/unicode/utf8), [pkg.go.dev/strings#ToValidUTF8](https://pkg.go.dev/strings#ToValidUTF8)
- **Struct values are copied.** `workflow.Step` and `workflow.CheckConfig` are plain structs with no pointers or slices, so `step := checkStep(url)` gives each test its own copy, and `step.Config.TimeoutMS = 2000` changes nothing elsewhere. [Tour: structs](https://go.dev/tour/moretypes/2)
- **Type assertions.** `w.(http.Hijacker)` and `node.client.Transport.(*http.Transport)` ask an interface value for its concrete type. The single-value form panics if the type is wrong; the tests use it where production guarantees the type (`http.go:25` clones a `*http.Transport`, which `http.go:31` stores in the client). [Tour: type assertions](https://go.dev/tour/methods/15)
- **`for range N` and `defer` order.** `for range size / 1024` repeats a block N times without a loop variable (Go 1.22). Deferred calls run in reverse order when the function returns, even after `t.Fatal`. [Spec: for range](https://go.dev/ref/spec#For_range), [Spec: defer](https://go.dev/ref/spec#Defer_statements)

## Walkthrough

### internal/nodes/httpcheck/http_test.go

**L1–L11** — `package httpcheck` makes this an internal test file that shares its package with `http.go`; the helper `checkStep` defined below is therefore visible to `http_limits_test.go:48` and `http_proxy_test.go:78` too. The imports: `context` for the first argument of `Execute` (`http.go:37`); `errors` for `errors.Is` at L60; `net/http` for `HandlerFunc` and `StatusText`; `net/http/httptest` for loopback servers; `testing`; and `patchbay/internal/workflow` for the `Step` and `CheckConfig` types the executor reads.

**L12–L15** — `checkStep` builds the one `workflow.Step` every HTTP test starts from: type `http.check`, expected status 200, and a 100 ms timeout. 100 ms is the smallest value `workflow.Validate` allows (`internal/workflow/workflow.go:112-113`); the executor itself never validates, because validation happened when the file was loaded at startup (`workflow.go:181`) and again at admission (`runner.go:106`), so the tests simply supply valid data. The short timeout keeps the timeout test at L38 fast. Because `Step` is a value type, callers that need a longer budget (`http_limits_test.go:49`) edit their own copy.

**L16–L19** — `TestHealthResponses` runs one subtest per status code: 200, 503, and 302, named by `http.StatusText` ("OK", "Service Unavailable", "Found"). The three codes cover the expected status, an unhealthy status, and a redirect.

**L20–L24** — The fixture is a loopback `httptest.Server` whose handler sets a `Location` header and then writes the chosen status. `Location` must be set before `WriteHeader`, because headers are frozen when the status goes out. On 200 and 503 the header is harmless; on 302 it is the address a redirect-following client would fetch next, and its path name `/must-not-follow` says what the test expects. `defer server.Close()` stops the listener when the subtest ends.

**L25–L28** — `New().Execute` runs the real executor with a background context, which models the runner's context when nothing is shutting down. `err` must be `nil` for all three codes: observing a 503 is a completed check, not an engine failure (`README.md:236-239`, `docs/roadmap.md:117`). The production path is `http.go:48` (`client.Do`), `http.go:50` (parent not canceled), `http.go:56` (no transport error), then `http.go:64-73`.

**L29–L31** — One condition proves two things. `StatusCode` equals the code the fixture sent (`http.go:66`), and `Healthy` is true only for 200 because `ExpectedStatus` is 200 (`http.go:67`). The 302 case also proves `CheckRedirect` at `http.go:33`: returning `http.ErrUseLastResponse` makes `client.Do` hand back the 302 itself with a nil error. Without that function the client would follow `Location`, the same handler would answer 302 again, and after ten hops `Do` would return an error; the result would then have `StatusCode` 0 and the assertion would fail. `README.md:242-243` promises "Redirects are reported as responses rather than followed."

**L32–L34** — Closing braces of the subtest, the loop, and the function.

**L35–L39** — `TestUnreachableAndTimeoutAreHealthData` first builds a server whose handler blocks on `<-r.Context().Done()`. The server-side request context is canceled when the client goes away, so the handler returns only after the executor gives up. The first `Execute` therefore runs into its own 100 ms deadline from `http.go:40`. `server.Close()` at L39 is not deferred: it must happen between the two calls, because the second call needs the port to be closed. `Close` waits for the blocked handler, which the executor's disconnect has already released.

**L40–L42** — The timeout assertion: nil error, not healthy, `StatusCode` 0, and the exact reason `"No response within 100 ms"`. That string is built at `http.go:58` when `client.Do` failed and the step's own context expired (`http.go:57`). `StatusCode` stays at its zero value from `http.go:39` because `http.go:66` is never reached.

**L43–L46** — The second `Execute` targets the closed port, so the operating system refuses the connection and `client.Do` returns an error with the step context still alive. `http.go:59-60` then stores `"Request failed: "` plus the transport's message. The test checks only that `Reason` is non-empty, since the refusal text differs between operating systems. Again a nil error: "An unreachable service is health data, not an engine failure" (`http.go:62`).

**L47** — Closing brace.

**L48–L55** — `TestParentCancellationStopsRequest` needs a request that is provably in flight when the cancel arrives. The handler closes `started` and then blocks until the request context ends. `close(started)` is a broadcast to the goroutine at L58; a second request would panic on closing a closed channel (`net/http` recovers handler panics, logs them, and drops that connection), so the fixture only serves the single request the executor sends. `defer server.Close()` runs last of the deferred calls, after `cancel`.

**L56–L58** — `context.WithCancel` makes the parent context the test controls. `defer cancel()` releases it even on failure. The goroutine waits for `started`, then cancels. Ordering matters: canceling before `Do` would make `Do` fail before any bytes were sent, and the test would prove less. The 100 ms step budget from `checkStep` must not run out first; the goroutine cancels as soon as the handler is entered, which is well inside that window.

**L59–L63** — The only assertion is `errors.Is(err, context.Canceled)`. The production path is `http.go:50-55`: after `Do` fails, the executor checks the parent `ctx.Err()` before anything else and returns it. The order matters. The child `checkCtx` is also done once its parent is canceled, so if `http.go:50-55` were removed, `http.go:57-58` would classify the cancel as `"No response within 100 ms"` with a nil error, and the runner would save an unhealthy check instead of marking the step canceled (`runner.go:250-254` decides `canceled` from the error plus `r.ctx.Err()`). The result value is discarded (`_`) because on this path it carries nothing the runner reads.

### internal/nodes/httpcheck/http_limits_test.go

**L1–L16** — Imports for the two header-limit tests: `crypto/tls` and `crypto/x509` to trust the HTTP/2 fixture's certificate (L94-96); `io` for `io.WriteString` onto a hijacked connection (L43); `strings` for `Repeat`, `Contains`, and `HasSuffix`; `time` for a write deadline (L38); `unicode/utf8` for `ValidString`; and `resulttext` for the `MaxReasonBytes` constant (`reason.go:10`). There is no `workflow` import because `checkStep` from `http_test.go:13` builds the step.

**L17–L28** — `TestHTTPResponseLimits` is a table of five raw responses. Each row names the bytes the fixture will write, a substring the stored reason must contain, and the expected `healthy` and `truncated` flags. The sizes are written in terms of two production constants so the table follows them: `maxHTTPHeaderBytes` (`http.go:14`, 64 KiB) and `resulttext.MaxReasonBytes` (4 KiB). Row by row: L23 "valid headers" is a correct 200 with a 32 KiB header and `Content-Length: 0`, so the client knows there is no body to wait for; expected healthy with the reason from `http.go:69`. L24 "malformed status" sends 12 KiB of `x` where the status line should be; Go's response parser rejects it with `malformed HTTP response` followed by the whole line, so the error text is far over 4 KiB and must come back truncated. L25 "malformed header" sends a good status line and then a 12 KiB line with no colon, which the header parser rejects as `malformed MIME header line:` plus the line; truncated again. L26 "oversized status" sends 128 KiB before any line ending, so the transport's 64 KiB cap trips before parsing with the short message `net/http: server response headers exceeded 65536 bytes; aborted`; no truncation. L27 "oversized headers" sends a valid status line followed by a 128 KiB header value and hits the same cap. The last two rows are the direct proof of `http.go:29`.

**L29–L44** — Each subtest starts a server whose handler hijacks the connection (comment at L30). `w.(http.Hijacker).Hijack()` returns the raw `net.Conn`; from then on `net/http` writes nothing, so the fixture can emit bytes a Go server never would. `t.Error` rather than `t.Fatal` at L34 and L39 because this code runs on the server's goroutine, where `t.Fatal` is not allowed. `defer conn.Close()` ends the response so the client sees EOF after the bytes. `SetWriteDeadline` of two seconds exists for the oversized rows: the client aborts after 64 KiB and stops reading, so a 128 KiB write could block forever on a full socket buffer; the deadline turns that into an error, which L43 discards on purpose (comment at L42).

**L45–L49** — `defer server.Close()`; a fresh executor; and `defer node.client.CloseIdleConnections()`, which reaches the unexported client field (`http.go:18`). Closing idle connections releases the keep-alive socket the client would otherwise hold to a server that is about to close. The step gets a 2000 ms budget instead of `checkStep`'s 100 ms so a slow machine writing 128 KiB cannot turn the expected classification into `"No response within 100 ms"`.

**L50–L53** — The executor runs, and three facts are checked together: nil error, because malformed and oversized responses "produce an unhealthy result rather than an engine failure" (`README.md:264-265`); `Healthy` as the row says; and the reason contains the row's substring, which passes through `http.go:60`. The `%.200q` verb prints at most 200 characters of a reason that may be 4 KiB long.

**L54–L56** — Status is 200 for the healthy row and 0 for every failure row. 0 is the zero value from `http.go:39`; `http.go:66` sets it only when `client.Do` returned a response.

**L57–L59** — The bound check: `len(result.Reason)` never exceeds `MaxReasonBytes`, the bytes are valid UTF-8, and the `"... [truncated]"` marker is present exactly when the row expects it. This exercises `resulttext.LimitReason` (`reason.go:14-26`) through its only HTTP caller at `http.go:60`, and shows that the `"Request failed: "` prefix is counted inside the limit, as `reason.go:12-13` states.

**L60–L62** — Closing braces.

**L63–L70** — `TestHTTP2ResponseHeaderLimit` runs twice, with valid and oversized headers, naming the subtests by hand. HTTP/2 gets its own test because the header cap is enforced by a different code path: Go maps `MaxResponseHeaderBytes` onto the HTTP/2 setting `SETTINGS_MAX_HEADER_LIST_SIZE`, which `README.md:262-263` calls "the corresponding protocol-specific accounting".

**L71–L87** — `protocol` is a one-slot buffered channel. The handler records `r.ProtoMajor` through a `select` with a `default` case, so it never blocks even if a second request arrives. It then emits either 32 KiB or 128 KiB of headers as many 1 KiB `X-Padding` values. The comment at L81 explains the shape: HTTP/2 also has a per-field limit, and one huge value would trip that instead of the total-size limit under test. `Content-Length: 0` and a 200 close the response.

**L88–L92** — `EnableHTTP2` must be set on an unstarted server, and `StartTLS` is required because Go's HTTP/2 client only negotiates over TLS. Then the usual `Close`, `New`, and `CloseIdleConnections` deferrals.

**L93–L96** — The client must trust the fixture's self-signed certificate without turning verification off (comment at L93), because `README.md:243` promises "normal HTTPS certificate validation remains enabled". A new `CertPool` holding only `server.Certificate()` goes into `TLSClientConfig` on the executor's own transport. The assertion to `*http.Transport` is safe because `New` stored a cloned transport (`http.go:25`), and because it is a clone, this change touches no other client in the process.

**L97–L99** — A 2000 ms step and the real `Execute`.

**L100–L103** — Healthy exactly when the headers were not oversized; nil error either way; reason within 4 KiB and valid UTF-8. The oversized case is a transport error at `http.go:56`, classified at `http.go:59-60`.

**L104–L106** — For the oversized case only: `StatusCode` is 0 and the reason contains `"header list"`, the distinctive part of Go's HTTP/2 error `http2: response header list larger than advertised limit`. The different wording from the HTTP/1 case is why the two tests exist.

**L107–L114** — The last `select` proves the fixture really negotiated HTTP/2. If `protocol` holds anything but 2, the test was silently exercising HTTP/1 again, and the `default` branch catches a request that never reached the handler. Without this check a change that disabled HTTP/2 on the cloned transport would leave the test green while proving nothing about HTTP/2.

**L115–L117** — Closing braces.

### internal/nodes/httpcheck/http_proxy_test.go

**L1–L17** — Imports beyond the earlier files: `fmt` for the error in the dial fake (L114); `net` for `JoinHostPort`, `Dialer`, and `Conn`; `os` for `Getenv`, `Environ`, and `Args`; `os/exec` to run the test binary again; `sync/atomic` for request counters shared with handler goroutines; and `time` for the child-process deadline.

**L18–L21** — `TestHTTPChecksIgnoreEnvironmentProxy` plays two roles. The constant names an environment variable that only this test sets. When it is unset, the function is the parent that spawns children; when set, it is the child that runs the real check.

**L22–L29** — The parent branch. The comment at L23-24 gives the reason for the two-process design: Go reads the proxy environment once per process and caches it in a `sync.Once`. Whichever read comes first wins: a request through `http.DefaultTransport` in another test, the fixture check at L90 in an earlier subtest, or a repeated run under `-count`. The executor's own transport never reads the environment (`http.go:28`), but once anything in the process has, a later `t.Setenv` is ignored, and the two schemes need different fixture URLs in any case. A fresh process per scheme guarantees that the first read sees the fixture's values, and the scrubbed environment below keeps a developer's own `HTTPS_PROXY` out of it. For each scheme the parent builds a 10 second context and a command that runs `os.Args[0]`, the current test binary, with `-test.run` anchored to this one test name.

**L30–L37** — The child's environment starts from the parent's, minus six keys. The four proxy variables are dropped so the child's first proxy read sees only what L73-74 set. `REQUEST_METHOD` is dropped because Go treats its presence as "I am a CGI script" and then refuses to use `HTTP_PROXY` for plain-HTTP requests, returning an error from the proxy policy, which would break the fixture check at L90-93 in the `http` child. The child marker is dropped so it can be re-added with the right value. `strings.Cut` splits each `KEY=value` entry at the first `=`, and `ToUpper` catches the lowercase variants `README.md:246` mentions.

**L38–L45** — The marker is appended with the scheme, the child runs, and `CombinedOutput` collects its output so a failure message shows the child's own log. The `return` at L44 means the parent never runs the fixture itself; L45 closes the parent branch.

**L46–L49** — The child rejects any marker value other than the two schemes it knows, followed by a blank line before the fixture setup.

**L50–L60** — Now the child. The comment at L50-51 names the second trap: Go never proxies `localhost` or loopback IPs, so a `127.0.0.1` URL would pass even with the bug present. The test therefore checks `check.example.com`, a name inside `*.example.com`, which the `httptest` certificate covers; the dial redirect at L106-117 will make that name reach the loopback listener without DNS. Two `atomic.Int32` counters are shared with handler goroutines. The endpoint handler counts, verifies the `Host` header, path, and method match what `http.go:42` sends (a proxy would have rewritten none of these, but a redirect mistake would), and answers 200. `t.Errorf` because it runs on a server goroutine.

## Check yourself

1. Both executors build a child context with the step timeout and then, after the dial or request, check `ctx.Err()` on the parent rather than `checkCtx.Err()` on the child. Why does the order of those two checks matter, and which test fails if you swap them?

<details><summary>Answer</summary>When the parent is canceled, the child is done too, so `checkCtx.Err()` is non-nil in both the "engine canceled us" and the "service was slow" cases. Checking the parent first (`http.go:50`, `tcp.go:41`) is the only way to tell them apart. If the executor consulted the child first, shutdown would be recorded as an unhealthy check with the reason "No response within 100 ms" and a nil error, and the runner would store a succeeded step instead of a canceled one (`runner.go:250-257`). `TestParentCancellationStopsRequest` (`http_test.go:49-63`), `TestTCPDistinguishesStepAndParentDeadlines/parent_deadline` (`tcp_test.go:141-144`), and `TestTCPParentCancellationTakesPriorityAndClosesConnection` (`tcp_test.go:178`) would all fail.</details>

2. In `TestTCPParentCancellationTakesPriorityAndClosesConnection`, the fake dialer returns a connection together with an error. A real `net.Dialer` never does that. Why test it anyway, and what production line does it exercise?

<details><summary>Answer</summary>The executor does not own the dialer's contract; the `dial` field (`tcp.go:18`) can be any function, and the executor must retain no socket no matter what comes back. `tcp.go:38-40` closes any non-nil connection before looking at the error or the context. The variant proves that line runs unconditionally, and `peer.Read` returning `io.EOF` (`tcp_test.go:182`) is the evidence. A version that wrote `if err == nil { connection.Close() }` would leak the connection in this variant and the read would time out instead.</details>

3. Why does `TestHTTPChecksIgnoreEnvironmentProxy` spawn a child process instead of calling `t.Setenv` and running in place, and why does it check `check.example.com` rather than `127.0.0.1`?

<details><summary>Answer</summary>Go reads the proxy environment once per process and caches the result in a `sync.Once`; any earlier read in the same binary, including the first scheme's own fixture check at L90, would freeze those values, so a later in-process `t.Setenv` would be ignored and the second scheme could never see its own fixture. A child with a scrubbed environment (`http_proxy_test.go:30-38`) sees the fixture's values first, and L90-93 confirms that by asking the default policy what it would do. Loopback addresses bypass the proxy automatically, so a `127.0.0.1` URL could never show the bug; a name under `*.example.com` is proxied by default and is covered by the `httptest` certificate, and the replaced `DialContext` (L106-117) routes it to the local listener without DNS.</details>

4. `TestLimitReason` has a row where the input is exactly 4096 bytes and the expected output is truncated. How can text that fits the limit need truncating, and what does that say about the order of statements in `LimitReason`?

<details><summary>Answer</summary>The input is 2048 copies of an invalid byte followed by `a`. `strings.ToValidUTF8` replaces each invalid byte with `U+FFFD`, which is three bytes, so the cleaned text is 8192 bytes. `reason.go:15` therefore has to run before the length check at `reason.go:16`; measuring first would return 4096 bytes of invalid UTF-8, or text that grows past the limit when something cleans it later. The expected output is 1020 pairs plus the marker because the cut point 4081 falls inside a replacement character and `reason.go:22-24` backs up to a rune start.</details>

5. In `TestTCPConnectsAndClosesWithoutSendingData` the executor returns before the test calls `Accept`. Why does that not make the test racy, and what would `Read` return if the executor had left the socket open?

<details><summary>Answer</summary>The TCP handshake completes in the kernel's listen backlog without the application calling `Accept`, so the executor's dial succeeds, it closes its end, and the completed connection waits in the queue. When the test accepts it, the peer's close is already recorded, so a one-byte `Read` returns zero bytes and `io.EOF`. If the executor had kept the socket open, `Read` would block until the two-second read deadline and return a timeout error, not `io.EOF`; if it had sent data, `n` would be 1. The deadlines at L42 and L50 make both failures finish in bounded time.</details>

6. Why do the fixtures in the limits test use `t.Error` and the proxy test's endpoint handler use `t.Errorf`, while the test bodies use `t.Fatal`?

<details><summary>Answer</summary>`t.Fatal` calls `runtime.Goexit` on the current goroutine and is only valid on the goroutine running the test. HTTP handlers run on goroutines owned by the `httptest.Server`; calling `t.Fatal` there would kill the handler goroutine without stopping the test and is documented as a misuse. `t.Error` records the failure and lets the handler finish, so the test goroutine's own assertions still run and the subtest reports both problems.</details>
