## Role in the system

These five files draw most of what you see on the Workflows page. `Sidebar` is the list of workflows on the left. `ViewTabs` is the Canvas/Details switch above the main column. `StepList` is the "Saved workflow steps" panel. `ExecutionHistory` is the "Execution history" heading, the clickable list of past runs, and the slot where `RunDetails` draws the one run you are inspecting. `AGENTS.md:59` calls the whole directory "Presentational pieces", and that is the rule these files follow: each one takes plain data and callbacks as props and returns JSX. None of them calls `fetch`, `useQuery`, `useState`, or `useNavigate`. They do not know where their data came from and they do not decide what happens when you click; they call a function the page gave them.

The data comes in from `WorkflowsPage` (`web/src/pages/WorkflowsPage.tsx`). It polls `GET /api/workflows` and `GET /api/runs` once per second (`WorkflowsPage.tsx:42-51`), merges the saved workflows with local drafts from the workspace context (`WorkflowsPage.tsx:78`), picks the selected workflow (`:79`), filters the run list down to that workflow (`:81`), picks the inspected run (`:82`), and hands the results down: `Sidebar` at `:105-110`, `ViewTabs` at `:113`, `StepList` at `:192`, `ExecutionHistory` at `:193-197`. `CanvasPage` reuses `ViewTabs` for the New workflow page (`CanvasPage.tsx:30`). The only data that goes back up is three callbacks: which workflow was clicked (`onSelect`), which run was clicked (`onInspect`), and which tab was clicked (`onChange`).

On the path from a browser click to a saved run, these components sit at both ends. A click in `Sidebar` changes which workflow is selected, which changes which runs `ExecutionHistory` lists. The Run button itself is in `WorkflowsPage.tsx:176-185`, not here. After the `POST` is accepted, the page inserts the new run into the `['runs']` cache (`WorkflowsPage.tsx:60-67`), the next poll replaces that with the server's list, and `ExecutionHistory` and `RunDetails` draw whatever the engine saved: the status the runner's step loop chose (`internal/engine/runner.go:224-285`) and `finishRun` recorded (`:300-314`), each step's output, the run-level error, and the memory-only `finalSaveFailed` flag that the history handler overlays on SQLite rows (`internal/httpapi/api.go:144-149`). These components are where `AGENTS.md:91-94` becomes visible to a person: execution outcome, service health, and save failure are three different things, and each gets its own badge or banner.

## Concepts you need

- **Function components, props, and destructuring.** A React component is a function that receives one object called `props` and returns JSX. All five files destructure that object in the parameter list, for example `function Sidebar({ workflows, selectedId, canvasDrafts, onSelect }: SidebarProps)` (`Sidebar.tsx:12`), so the body reads each prop as a plain variable. A `type XProps = { ... }` alias names the shape; an optional prop is written `selectedId?: string`. The caller decides the values; the component never changes them. [React: Passing props to a component](https://react.dev/learn/passing-props-to-a-component)
- **Conditional rendering with `&&` and `? :`, and fragments.** JSX cannot contain `if` statements, so a branch is written as an expression. `cond && <X />` draws `X` only when `cond` is truthy, and draws nothing for `false`, `null`, or `undefined` (`RunDetails.tsx:22`). `cond ? <A /> : <B />` chooses between two trees (`ExecutionHistory.tsx:25`). A fragment `<>...</>` groups several siblings without adding a DOM element (`ExecutionHistory.tsx:18`). [React: Conditional rendering](https://react.dev/learn/conditional-rendering), [React: Fragment](https://react.dev/reference/react/Fragment)
- **Rendering lists and the `key` prop.** `array.map((item) => <li key={item.id}>...)` turns data into elements. React uses `key` to match an element in the previous render with the same item in the next one, so it can update a row in place instead of destroying and recreating it. The key must be stable and unique among siblings; every list here uses a value that is unique among its siblings, whether a server-validated id, a browser-generated draft id, or one of the two fixed view names (`Sidebar.tsx:33`, `StepList.tsx:17`, `ExecutionHistory.tsx:49`, `RunDetails.tsx:30`, `ViewTabs.tsx:47`). [React: Rendering lists](https://react.dev/learn/rendering-lists)
- **Callback props and lifting state up.** When a child needs to change something, it calls a function the parent passed in, such as `onSelect(workflow.id)` (`Sidebar.tsx:36`). The parent owns the state and the setter; the child only reports an event. This is why `ViewTabs` has no `useState`: the current view is a prop, and clicking a tab calls `onChange` (`ViewTabs.tsx:55`). Components written this way are called controlled. [React: Responding to events](https://react.dev/learn/responding-to-events), [React: Sharing state between components](https://react.dev/learn/sharing-state-between-components)
- **React's synthetic `KeyboardEvent<T>` and `currentTarget`.** React wraps browser events in its own objects with the same field names. The type `KeyboardEvent<HTMLButtonElement>` from `'react'` (`ViewTabs.tsx:1`) says the handler is attached to a button, so `event.currentTarget` is typed as `HTMLButtonElement` and `.nextElementSibling` type-checks (`ViewTabs.tsx:29`). `currentTarget` is the element the handler is on; `target` would be whatever was clicked inside it. [React: KeyboardEvent handler](https://react.dev/reference/react-dom/components/common#keyboardevent-handler)
- **TypeScript discriminated unions and narrowing.** `Workflow | LocalWorkflow` (`Sidebar.tsx:6`) is a union. TypeScript refuses to read `workflow.steps` until you prove which member you hold. `'steps' in workflow` (`Sidebar.tsx:46`) is that proof: a `Workflow` has `steps` (`api.ts:22`), a `LocalWorkflow` does not (`canvasDraft.ts:11-16`). `CheckOutput` is a union with a `type` field, so `output.type === 'tcp.check'` narrows it (`format.ts:73`). Optional chaining `a?.b` reads `undefined` instead of throwing when `a` is missing, and `x ?? y` substitutes `y` only for `null` or `undefined` (`Sidebar.tsx:48`). [TypeScript: Narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html), [MDN: Optional chaining](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Optional_chaining)
- **`import type` under `verbatimModuleSyntax`.** `import type { Run } from '../api'` imports a name that exists only for the type checker; the bundler deletes the line. `web/tsconfig.json:11` turns on `verbatimModuleSyntax`, which requires the `type` keyword on every type-only import so Vite can strip imports without analysing them. That is why `Sidebar.tsx:1-2` say `import type` and `:3` does not. [TypeScript: verbatimModuleSyntax](https://www.typescriptlang.org/tsconfig/#verbatimModuleSyntax)
- **Tailwind utilities, responsive prefixes, arbitrary values, and theme tokens.** A class such as `px-4` sets one CSS property. `md:px-3` applies only at the `md` breakpoint and above (48rem, 768px); `lg:` is 64rem (1024px). Square brackets write an exact value Tailwind has no name for: `w-[234px]`, `leading-[1.7]`, `shadow-[inset_0_-3px_var(--color-accent-bar)]`. Names like `bg-surface-muted` and `text-2xs` are not built in; `web/src/index.css:5-71` defines them inside `@theme`, and `index.css:15` deletes Tailwind's own palette so only the project colors exist. Tailwind scans source files for complete class strings, which is why `classes.ts:1` and `Badge.tsx:6` warn against building class names at runtime. [Tailwind: Responsive design](https://tailwindcss.com/docs/responsive-design), [Tailwind: Arbitrary values](https://tailwindcss.com/docs/adding-custom-styles#using-arbitrary-values), [Tailwind: Theme variables](https://tailwindcss.com/docs/theme)
- **Tailwind ARIA state variants.** `aria-pressed:bg-surface-active` applies a class only while the element has `aria-pressed="true"`. Tailwind ships variants for a short list of boolean ARIA attributes (`aria-pressed`, `aria-selected`, and others). `aria-current` is not in that list, so `Sidebar.tsx:34` writes the arbitrary form `aria-[current=page]:...`. Styling from ARIA attributes means the thing a screen reader announces and the thing a sighted user sees cannot disagree. [Tailwind: ARIA states](https://tailwindcss.com/docs/hover-focus-and-other-states#aria-states)
- **Landmarks and accessible names.** `<aside>`, `<nav>`, `<main>`, and `<section>` are landmarks that assistive technology can jump to. A `<section>` counts as a `region` landmark only when it has a name, given by `aria-label="Run results"` (`RunDetails.tsx:13`) or by `aria-labelledby="steps-title"` pointing at a heading's id (`StepList.tsx:8-10`). The Playwright tests find these panels by exactly those names (`web/tests/workflows.spec.ts:26`, `:80`), so the names are part of the test contract. [MDN: region role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/region_role), [MDN: aria-labelledby](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-labelledby)
- **`aria-current`, `aria-pressed`, and `aria-live`.** `aria-current="page"` marks the item in a navigation list that represents where you are (`Sidebar.tsx:35`). `aria-pressed` turns a button into a toggle whose on/off state is announced (`ExecutionHistory.tsx:51`). `aria-live="polite"` tells a screen reader to announce changes inside an element when the user is idle, which matters because the run panel changes by itself while a run executes (`RunDetails.tsx:13`). [MDN: aria-current](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-current), [MDN: aria-pressed](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-pressed), [MDN: aria-live](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-live)
- **The WAI-ARIA tabs pattern and roving tabindex.** A `role="tablist"` holds `role="tab"` buttons, each with `aria-selected` and `aria-controls` pointing at a `role="tabpanel"` whose `aria-labelledby` points back. Keyboard users press Tab once to reach the list and then use arrow keys to move between tabs. That is done with a roving tabindex: the selected tab has `tabIndex={0}` and the others `-1`, so only one tab is in the Tab order (`ViewTabs.tsx:53`), and an arrow-key handler moves focus and selects (`ViewTabs.tsx:26-37`). [WAI-ARIA APG: Tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/), [WAI-ARIA APG: Roving tabindex](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_roving_tabindex)
- **Locale formatting with `toLocaleString`.** `new Date(iso).toLocaleString([], { dateStyle: 'short', timeStyle: 'medium' })` prints a timestamp in the browser's own language and time zone; the empty array means "the default locale" (`ExecutionHistory.tsx:57-60`). `number.toLocaleString()` adds thousands separators, so `30000` prints as `30,000` in English (`StepList.tsx:41`). Both come from the `Intl` machinery and need no library. [MDN: Date.prototype.toLocaleString()](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date/toLocaleString), [MDN: Number.prototype.toLocaleString()](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/toLocaleString)
- **TanStack Query data arriving as props.** `useQuery` lives in the page (`WorkflowsPage.tsx:42-51`), and these components only see the resulting arrays. Two library behaviors shape what you observe here. Polling every second does not force a re-render: the client compares each new response with the cached one and keeps the old object when nothing changed (structural sharing), so an idle page draws nothing new. And a run that the page inserted optimistically (`WorkflowsPage.tsx:62-65`) is replaced by the server's copy on the next poll. [TanStack Query: Render optimizations](https://tanstack.com/query/latest/docs/framework/react/guides/render-optimizations)
- **TanStack Router search params as UI state.** The open tab is not component state; it is `?view=` in the URL. `router.tsx:28-32` validates it into `'canvas' | 'details'`, `useSearch` reads it (`WorkflowsPage.tsx:37`), and `navigate({ search, replace: true })` writes it (`WorkflowsPage.tsx:97`). `ViewTabs` receives that value as `view` and reports clicks through `onChange`. `AGENTS.md:59` records this split: "the pages keep the choice in `?view=`". [TanStack Router: Search params](https://tanstack.com/router/latest/docs/framework/react/guide/search-params)
- **React Flow node objects, counted but not drawn.** `canvasDrafts[id].nodes` is an array of React Flow `Node` objects (`canvasDraft.ts:4-9`). `Sidebar.tsx:48` only reads `.length` to say "3 nodes · Local draft". The canvas that draws them is `WorkflowCanvas` (a later chapter); `AGENTS.md:70` and `:132` remind you that these nodes are frontend-only placeholders, not executable steps. [React Flow: Node](https://reactflow.dev/api-reference/types/node)
- **Playwright role locators.** The browser tests do not query CSS classes except one deliberate hook. They ask for roles and names: `getByRole('tab', { name: 'Canvas' })` (`workflows.spec.ts:71`), `getByRole('region', { name: 'Run results' })` (`:26`), `getByRole('article')` (`:27`). Every `role=`, `aria-label=`, and semantic element in these files is therefore load-bearing for the test suite as well as for accessibility. [Playwright: Locate by role](https://playwright.dev/docs/locators#locate-by-role)

## State and rendering

None of these five files owns state. Here is where each value they draw actually lives, and what makes it change.

**Server cache (TanStack Query).** The arrays behind `Sidebar.workflows`, `StepList.workflow`, and `ExecutionHistory.history` are the `['workflows']` and `['runs']` entries in the `QueryClient` created in `web/src/queryClient.ts` and provided at `main.tsx:11`. `WorkflowsPage.tsx:42-51` subscribes to both with `refetchInterval: 1000`. A poll whose response is deep-equal to the cached value leaves the cached object in place, so a page with nothing happening does not re-render every second; when a run's status changes, the new `Run[]` is a new object, the page re-renders, and the props flowing into `ExecutionHistory` and `RunDetails` change. The optimistic write at `WorkflowsPage.tsx:62-65` puts a just-accepted run at the front of that array until the next poll replaces it with the server's list, which already contains the run because the runner saved it before answering `202` (`AGENTS.md:83-84`). Leaving the page to `/canvas` unmounts `WorkflowsPage` and stops the polling (`App.tsx:6-8`).

**Workspace state (React `useState` in `App`).** The selected workflow id, the local drafts, and the canvas drafts live in `App.tsx:11-13` and reach the page through the context in `workspace.ts`. `Sidebar.onSelect` ends in `setWorkflowId` (`App.tsx:39`, via `chooseWorkflow` at `WorkflowsPage.tsx:85-89`). Because `App` stays mounted across routes, the selection survives a trip to the New workflow page but not a browser reload; `AGENTS.md:70` states the same for drafts.

**Page state (React `useState` in `WorkflowsPage`).** `runId` (`WorkflowsPage.tsx:36`) is the only state the page keeps for itself. `ExecutionHistory.onInspect` is literally `setRunId` (`:196`). `chooseWorkflow` resets it to `''` so a run from one workflow is never looked up inside another's history; the fallback `?? history[0]` (`:82`) then selects the newest run.

**URL search params (TanStack Router).** `view` comes from `useSearch({ from: '/workflows' })` (`:37`) after `router.tsx:28-32` has coerced anything that is not `'details'` into `'canvas'`. `ViewTabs.onChange` becomes a `navigate` with `replace: true`. This is why the tests can reload the page and find the same view (`workflows.spec.ts:90-91`).

**Module scope.** `views`, `tabClass`, `viewPanelId` (`ViewTabs.tsx:5-17`), and `helpClass`, `stepTextClass` (`RunDetails.tsx:9`, `:44`) are constants created when the module loads. They never change and are shared by every render.

**Derived values, computed every render.** `availableWorkflows`, `selected`, `savedWorkflow`, `history`, and `inspectedRun` (`WorkflowsPage.tsx:78-82`) are plain `const`s recomputed each time the page renders. Inside the components, `stepDefinition(step)` (`StepList.tsx:15`) and `outputPresentation(output)` (`RunDetails.tsx:66`) are likewise recomputed; they are cheap pure functions, so there is no memoization, which keeps with the preference for explicit code (`AGENTS.md:6-7`).

**Browser-owned state.** Focus (which tab or run button has it), scroll positions of the sidebar and the run list, and whether a `JsonDetails` `<details>` is open belong to the DOM. Because `RunDetails` is rendered without a `key` (`ExecutionHistory.tsx:74`), clicking another run keeps the same DOM subtree, so an opened "View execution JSON" stays open and shows the new run's JSON. If you ever want the panel to reset per run, adding `key={inspectedRun.id}` there is the one-line change.

**From JSON to pixels.** Go encodes `engine.Run` with the tags at `runner.go:24-46`; `api.ts:52-63` names the same keys; `WorkflowsPage` filters the array; `ExecutionHistory` draws one button per run and hands the inspected one to `RunDetails`; `RunDetails` passes the run and each step into `format.ts` helpers that return strings; the JSX places those strings. The only transformation that happens inside these components is choosing between two badges (`RunDetails.tsx:51-57`) and formatting dates and numbers for the locale.

**How errors reach the user.** Connection errors never enter these components; `WorkflowsPage.tsx:114-126` draws them above the tab panel so both views show them. A run that stopped because a progress save failed arrives as `run.error` and becomes the first alert in `RunDetails` (`:22`). A result that executed but could not be saved arrives as `finalSaveFailed` and becomes both the note in the list (`ExecutionHistory.tsx:66-70`) and the second alert (`RunDetails.tsx:23-28`). A step whose executor could not perform its check arrives as `step.error` and is printed as plain text under the step (`RunDetails.tsx:60`). A service that answered wrongly is not an error at all; it is an output with `healthy: false` and a reason, drawn as an "Unhealthy" or "Unreachable" badge (`RunDetails.tsx:52-54`). Four channels, four different renderings, as `AGENTS.md:91` asks.

2. A run has status `succeeded`, and one of its steps has `output.healthy === false`. Which badge does the panel header show, which badge does that step show, and which lines in Go and in the roadmap make that combination correct rather than a bug?

<details><summary>Answer</summary>The header shows "Completed", because <code>RunDetails.tsx:16</code> renders <code>StatusBadge</code> for <code>run.status</code> and <code>format.ts:6</code> maps <code>succeeded</code> to that label. The step shows "Unhealthy" (or "Unreachable" for TCP), because <code>RunDetails.tsx:51-54</code> sees an <code>output</code> and renders a <code>Badge</code> with tone <code>unhealthy</code> and the text from <code>outputPresentation</code> (<code>format.ts:75</code>, <code>:83</code>). The engine marks a step <code>succeeded</code> whenever the executor returned an output (<code>runner.go:257</code>), and the run <code>succeeded</code> when every step did; the service's health is inside the output, not in the status. <code>docs/roadmap.md:117</code> states the design: a failed health check is a successful check operation with an unhealthy result. <code>AGENTS.md:91</code> turns it into a rule for the UI, and <code>runSummary</code> (<code>format.ts:105-115</code>) adds "1 unhealthy service" so the header is not misleading.</details>

3. Where is `finalSaveFailed` set, how does it reach the browser when SQLite holds an older snapshot, in which two places does the UI show it, and what happens to all of that after the server restarts?

<details><summary>Answer</summary>It is set at <code>internal/engine/runner.go:310</code> when <code>saveFinalRun</code> fails after its retries, on the in-memory copy only. <code>GET /api/runs</code> reads SQLite (<code>api.go:92</code>) and then calls <code>preferUnsavedRun</code> for each row (<code>api.go:98-100</code>); if the runner's live copy has the flag, the live copy replaces the stale row (<code>api.go:144-149</code>). The browser shows the note "Final result not saved" in the list (<code>ExecutionHistory.tsx:66-70</code>) and the "temporary" banner in the panel (<code>RunDetails.tsx:23-28</code>); the status badge is unchanged because the flag is not a status (<code>AGENTS.md:92</code>). After a restart the runner's memory is empty, so the overlay no longer happens; the API returns SQLite's last snapshot, and startup marks any still-running record interrupted (<code>AGENTS.md:98-99</code>, <code>README.md:551-552</code>). The flag, the note, and the banner all disappear, and the panel shows whatever was last saved, possibly with "Interrupted".</details>

4. With focus on the "Canvas" tab, the user presses ArrowRight. Walk through `ViewTabs.tsx:26-37` and `:53`, say why `focus()` comes before `click()`, why `preventDefault()` is needed, and why pressing ArrowRight again does nothing.

<details><summary>Answer</summary><code>onKeyDown</code> runs on the Canvas button. <code>event.key</code> is <code>'ArrowRight'</code>, so <code>sibling</code> is <code>event.currentTarget.nextElementSibling</code>, the Details button (<code>:27-32</code>). It passes the <code>instanceof HTMLButtonElement</code> check (<code>:33</code>). <code>preventDefault()</code> (<code>:34</code>) stops the keypress from also scrolling the focusable <code>ScrollColumn</code> that contains the bar (<code>ScrollColumn.tsx:4-6</code>). <code>sibling.focus()</code> moves keyboard focus to Details, then <code>sibling.click()</code> runs Details' <code>onClick</code>, which calls <code>onChange('details')</code>, which navigates to <code>?view=details</code> (<code>WorkflowsPage.tsx:96-98</code>). On the re-render Details has <code>aria-selected="true"</code> and <code>tabIndex 0</code>, Canvas has <code>tabIndex -1</code> (<code>:51</code>, <code>:53</code>). Focus is moved first so that the element which ends up with <code>tabIndex 0</code> is the one holding focus; doing it in the other order would leave focus on a button that is about to drop out of the Tab order. A second ArrowRight runs the handler on Details, whose <code>nextElementSibling</code> is <code>null</code>; the <code>instanceof</code> check fails and the function returns, so there is no wrap-around.</details>

5. The Playwright test at `web/tests/workflows.spec.ts:31` parses `results.locator('pre')`. Which lines guarantee that locator finds exactly one element inside "Run results", and name two ways a well-meaning change to `RunDetails.tsx` could break that test without touching the JSON it checks.

<details><summary>Answer</summary><code>RunDetails.tsx:39</code> renders the panel's only <code>JsonDetails</code>, and <code>JsonDetails.tsx:6-8</code> renders exactly one <code>&lt;pre&gt;</code>; nothing in <code>StepResult</code> or <code>OutputMetrics</code> renders a <code>&lt;pre&gt;</code>. <code>JsonDetails.tsx:1</code> states the rule. One break: adding a <code>JsonDetails</code> per step inside <code>StepResult</code> (<code>:47-61</code>) would make the locator match several elements, and Playwright's strict mode rejects <code>textContent()</code> on an ambiguous locator. Another: wrapping a step's reason or error in a <code>&lt;pre&gt;</code> for monospace formatting (for example at <code>:60</code> or <code>:69</code>) would do the same. A third: removing <code>aria-label="Run results"</code> at <code>:13</code> would make the region unfindable in the first place.</details>

6. `ExecutionHistory` receives `inspectedRun` as a prop and also receives `history`. Why does the page compute the inspected run instead of letting `ExecutionHistory` keep its own `useState` for the clicked id, and what would go wrong with that design when polling replaces the `history` array?

<details><summary>Answer</summary>The page needs the inspected run id for more than this component: <code>chooseWorkflow</code> must clear it when the workflow changes (<code>WorkflowsPage.tsx:87</code>), and <code>startMutation.onSuccess</code> must set it to the new run so the panel jumps to what the user just started (<code>:66</code>). If the id lived inside <code>ExecutionHistory</code>, the page could not do either without a ref or an effect. Separately, the component stores an id, not a <code>Run</code> object, because every poll produces a fresh array of fresh objects (<code>:47-51</code>); holding onto the clicked object would show a frozen snapshot while the list updated around it. Looking the id up in the current <code>history</code> on each render (<code>:82</code>) means the panel always shows the newest copy, and the <code>?? history[0]</code> fallback handles an id that is no longer in the list. That is the controlled-component shape described in the Concepts section, and it is why both <code>inspectedRun</code> and <code>onInspect</code> are props (<code>ExecutionHistory.tsx:8-9</code>).</details>
