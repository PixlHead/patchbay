## Role in the system

These four files are the visual editor, in the small form it has today. `canvasDraft.ts` defines what a draft is: a name plus an array of React Flow node objects, with helpers that place nodes on a grid, build one node, and seed a draft from a saved workflow's steps. `WorkflowCanvas.tsx` is the one canvas component. It draws the React Flow surface, a node-type picker, an Add node button, a Reset layout button, and two text bars, and it turns every drag, click, and Delete key press into a new draft value. `CanvasNode.tsx` is the one node component React Flow calls to draw each tile. `CanvasPage.tsx` is the route component for `#/canvas`, the New workflow page: the same canvas for an unfinished draft plus a form that names it and turns it into a sidebar entry. `README.md:209-214` lists these responsibilities in the same words, and `AGENTS.md:62` repeats them in the code map.

Data comes in from two places and never from the server. The draft to draw comes from React state that `App.tsx` owns: the per-workflow map `canvasDrafts` (`App.tsx:13`) and the unfinished `newWorkflow` (`App.tsx:14`), passed down as a `draft` prop (`WorkflowsPage.tsx:136`, `CanvasPage.tsx:38`). For a saved workflow with no stored draft yet, `draftFromWorkflow` builds one on the fly from the polled `Workflow` value (`canvasDraft.ts:44-52`), which is the only moment server data touches this code. User events come from React Flow (change lists for position, selection, size, and removal) and from the DOM (the picker, the buttons, the name field). What goes out is always the same thing: an updater function handed to `onChange`, which the owner applies to its state (`WorkflowsPage.tsx:137-142`, `App.tsx:14`). No file here calls `request` from `web/src/api.ts:65`; the only callers of that helper are in `WorkflowsPage.tsx:44`, `:49`, and `:56`.

On the path from a browser click to a saved run, these files are a side road. A node added on the canvas, a dragged layout, and a draft created on the New workflow page exist only in memory and are gone on reload, which `AGENTS.md:70` states as a rule and `README.md:202-203` promises to users. The Run workflow button lives in the Details view and starts the saved steps (`WorkflowsPage.tsx:91-94`, `README.md:205-206`); nothing on the canvas can start a run. The roadmap keeps it that way on purpose until milestone 2, which will add a real palette, connection handles, configuration, and save controls, and will replace the current draft shape, which "stores React Flow node objects and drops step configuration", with the definition's own shape (`docs/roadmap.md:178`). Chapter 13 covered the state owner (`App.tsx`) and chapter 15 covered the page that mounts the canvas per workflow; this chapter covers the canvas itself and the page that uses it for a brand-new draft.

## Concepts you need

- **`useState` and updater functions.** `const [value, setValue] = useState(initial)` gives a component one piece of state that survives re-renders. `setValue((current) => next)` passes an updater: React calls it later with the latest state, so several updates in one burst each build on the previous result. Every state change in this chapter uses the updater form. In development, `StrictMode` (`main.tsx:10`) calls each updater twice to expose updaters that are not pure. [React: useState](https://react.dev/reference/react/useState), [React: Queueing a series of state updates](https://react.dev/learn/queueing-a-series-of-state-updates)
- **Lifting state up and passing an updater as a prop.** When two components need the same state, it lives in their nearest shared parent, and the children receive the value plus a function to request a change. `WorkflowCanvas` never stores the nodes; it receives `draft` and `onChange` and calls `onChange` with an updater. The `UpdateCanvasDraft` type (`canvasDraft.ts:19`) names that contract. [React: Sharing state between components](https://react.dev/learn/sharing-state-between-components)
- **Immutable updates with spread syntax.** React detects a change by comparing object references, so state is replaced, never mutated. `{ ...current, nodes: [...current.nodes, node] }` copies the old object and array and swaps one field. Mutating `current.nodes.push(node)` would leave the reference unchanged and React, and React Flow, would not redraw. [MDN: Spread syntax](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Spread_syntax), [React: Updating objects in state](https://react.dev/learn/updating-objects-in-state)
- **Context and the `useWorkspace` hook.** `App.tsx:36-49` provides a `Workspace` object through context; `useWorkspace` (`workspace.ts:18-22`) reads it and throws if no provider is above. `CanvasPage` reads three of its eight fields. Chapter 13 explains the provider side. [React: useContext](https://react.dev/reference/react/useContext)
- **Controlled form elements.** An input with `value={state}` and an `onChange` that sets that state shows exactly what React holds, and nothing else. The name field (`CanvasPage.tsx:58-69`) and the node-type `<select>` (`WorkflowCanvas.tsx:82-92`) are both controlled. A form's `onSubmit` runs on Enter or a submit button click, and `event.preventDefault()` stops the browser from performing its own navigation. [React: input](https://react.dev/reference/react-dom/components/input#controlling-an-input-with-a-state-variable), [MDN: Event.preventDefault()](https://developer.mozilla.org/en-US/docs/Web/API/Event/preventDefault)
- **The `key` prop as a reset switch.** React reuses a component instance when its type and position in the tree stay the same. A changed `key` throws the instance away and mounts a fresh one, resetting its `useState` values and, for React Flow, its internal store. `WorkflowsPage.tsx:135` keys the canvas by workflow id; `CanvasPage.tsx:38` has one draft and needs no key. [React: Resetting state with a key](https://react.dev/learn/preserving-and-resetting-state#resetting-a-form-with-a-key)
- **React Flow: a controlled flow.** React Flow (`@xyflow/react` 12.11.6, `web/package.json`) draws nodes from the `nodes` prop you give it. It does not change that array. When the user drags, clicks, or deletes, it calls `onNodesChange` with a list of change objects (`position`, `select`, `remove`, `dimensions`, and others). `applyNodeChanges(changes, nodes)` is the helper that returns a new array with those changes applied, and the owner stores it. [React Flow: Core concepts](https://reactflow.dev/learn/concepts/core-concepts), [React Flow: applyNodeChanges](https://reactflow.dev/api-reference/utils/apply-node-changes), [React Flow: NodeChange](https://reactflow.dev/api-reference/types/node-change)
- **React Flow: node objects, `Node<Data, Type>`, and `NodeProps`.** A node is a plain object with `id`, `position`, `data`, and an optional `type`. React Flow adds fields as it works: `selected`, `dragging`, and `measured` (the DOM size it observed). The `Node` type takes two generic arguments, the shape of `data` and the literal `type`; `NodeProps<SomeNode>` is the props a custom node component receives, typed to match. [React Flow: Node](https://reactflow.dev/api-reference/types/node), [React Flow: NodeProps](https://reactflow.dev/api-reference/types/node-props)
- **React Flow: custom node types and the `nodeTypes` object.** `nodeTypes={{ canvas: CanvasNode }}` maps a `type` string to a component. React Flow compares that object by reference, and a new object every render makes it rebuild its wrappers and log warning 002. The project keeps the object at module scope (`WorkflowCanvas.tsx:9-10`). [React Flow: Custom nodes](https://reactflow.dev/learn/customization/custom-nodes), [React Flow: Error 002](https://reactflow.dev/error#002)
- **React Flow: `Handle` and `Position`.** A handle is the small dot where an edge starts (`source`) or ends (`target`). `Position.Top` and `Position.Bottom` say which side of the node it sits on. `isConnectable={false}` stops the user from dragging a new edge out of it. [React Flow: Handle](https://reactflow.dev/api-reference/components/handle)
- **React Flow: viewport, `fitView`, `Background`, and `Controls`.** The viewport is the pan and zoom of the whole canvas; React Flow keeps it in its own store. `fitView` pans and zooms once on mount so every node is visible. `Background` draws the dot grid and `Controls` the zoom buttons. The container element must have a real width and height or React Flow cannot measure anything. [React Flow: ReactFlow props](https://reactflow.dev/api-reference/react-flow), [React Flow: Background](https://reactflow.dev/api-reference/components/background), [React Flow: Controls](https://reactflow.dev/api-reference/components/controls)
- **TanStack Router: `useSearch` and `useNavigate`.** `useSearch({ from: '/canvas' })` returns the search params of that route after `validateSearch` has run (`router.tsx:28-32`, `:44`), so `view` is always `'canvas'` or `'details'`. `useNavigate()` returns a function that changes the URL; `replace: true` overwrites the current history entry. [TanStack Router: Search params](https://tanstack.com/router/latest/docs/framework/react/guide/search-params), [TanStack Router: useNavigate](https://tanstack.com/router/latest/docs/framework/react/api/router/useNavigateHook)
- **ARIA: the tabs pattern and landmark regions.** A tab list has buttons with `role="tab"`, each pointing at a panel with `aria-controls`; the panel has `role="tabpanel"` and names its tab with `aria-labelledby`. A `<section>` with an `aria-label` becomes a `region` landmark, which is how the Playwright test finds the canvas. [WAI-ARIA APG: Tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/), [MDN: region role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/region_role)
- **Tailwind: class detection, arbitrary values, and layers.** Tailwind scans source files for complete class strings and emits CSS only for those it finds, so a class built from pieces at runtime produces nothing. Square brackets give a one-off value, such as `min-h-[560px]`. Tailwind's utilities sit in a later cascade layer than the React Flow stylesheet, which `index.css:2-3` imports into the `base` layer, so a utility on a handle overrides React Flow's own rule. [Tailwind: Detecting classes in source files](https://tailwindcss.com/docs/detecting-classes-in-source-files), [Tailwind: Arbitrary values](https://tailwindcss.com/docs/adding-custom-styles#using-arbitrary-values), [Tailwind: Theme variables](https://tailwindcss.com/docs/theme)
- **TypeScript: literal types, `Record`, `in` narrowing, and the non-null assertion.** `'canvas'` as a type accepts only that string. `Record<string, string>` is an object used as a map; under this project's `web/tsconfig.json:8` (`strict` without `noUncheckedIndexedAccess`) a lookup is typed as present even when the key is missing, so the code guards with `??`. `'steps' in workflow` narrows a union by the presence of a field. `expr!` tells the compiler a value is not `undefined` without a runtime check. [TypeScript: Literal types](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#literal-types), [TypeScript: Record](https://www.typescriptlang.org/docs/handbook/utility-types.html#recordkeys-type), [TypeScript: Narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html), [TypeScript: Non-null assertion](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-0.html#non-null-assertion-operator)
- **TypeScript: generic type arguments in JSX.** `<ReactFlow<DraftNode> ...>` passes a type argument to a generic component, so its `nodes` prop and the `changes` given to `onNodesChange` are typed for this project's node shape. [TypeScript: Generic type arguments in JSX elements](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-9.html#generic-type-arguments-in-jsx-elements)
- **`crypto.randomUUID()`, default parameters, and `??`.** `crypto.randomUUID()` makes a random id string in a secure context, which includes `http://localhost` and `http://127.0.0.1`. `{ flag = false }` in a destructuring pattern supplies a default when the caller omits the prop. `a ?? b` yields `b` only when `a` is `null` or `undefined`, not when it is `0` or `''`. [MDN: Crypto.randomUUID()](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID), [MDN: Default parameters](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Functions/Default_parameters), [MDN: Nullish coalescing](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Nullish_coalescing)

### web/src/canvasDraft.ts

**L1–L3** — Two type-only imports. `Node` is React Flow's type for one node object, the thing `ReactFlow` draws and `applyNodeChanges` rewrites. `Workflow` is the API shape of a saved workflow (`api.ts:16-25`), with its `steps` array. The file imports nothing at runtime, so it has no dependency on React Flow in the built code. L3 is blank.

**L4–L5** — `DraftNode` is React Flow's `Node` type with two arguments filled in. The first, `{ label: string; kind: string }`, is the `data` object every node carries: `label` is the text the tile shows (`CanvasNode.tsx:16`) and `kind` picks its accent colour (`CanvasNode.tsx:12`). The field is called `kind`, not `type`, because React Flow already uses `type` on the node object to choose which component draws it; the step's own type, such as `http.check`, is a different thing and gets a different name. The second argument pins React Flow's `type` to the literal `'canvas'`, which must match the key in `flowNodeTypes` (`WorkflowCanvas.tsx:10`) and the value written by `makeCanvasNode` (L41). Without the generic, `data` would be `Record<string, unknown>` and `data.label` in the node component would be `unknown`, not a string. Users: `WorkflowCanvas.tsx:3`, `:107`; `CanvasNode.tsx:4`, `:8`.

**L6–L10** — `CanvasDraft` is what the app stores for one workflow: a `name` and the `nodes` array. `App.tsx:13-14` holds one of these per workflow id plus one for the unfinished New workflow; `WorkflowCanvas.tsx:19` takes one as its `draft` prop; `Sidebar.tsx:48` counts `nodes.length` for a local draft's caption. The nodes are React Flow's objects, so a draft is the picture, not the workflow. `docs/roadmap.md:178` names this as the thing milestone 2 replaces ("Hold the draft in the definition's shape"), and `docs/roadmap.md:30` states the principle: keep the application schema independent of React Flow's own UI state. Nothing of this type is ever sent to the server (`AGENTS.md:70`).

**L11–L17** — `LocalWorkflow` is a sidebar entry that the Create draft button makes (`App.tsx:20-28`). `local: true` is a literal type, so a saved `Workflow`, which has no `local` field, can never be passed where a `LocalWorkflow` is required. `id` is `local-` plus a UUID (`App.tsx:19`), `name` is the trimmed form value, and `description` is a fixed sentence (`App.tsx:26`). All three places tell the two apart with `'steps' in workflow` (L48, `Sidebar.tsx:46`, `WorkflowsPage.tsx:80`) rather than reading `local`, so the flag is a type-level guard, not a runtime switch. A local workflow has no steps, so it gets no Run button and no history (`WorkflowsPage.tsx:174-199`, `README.md:198-199`).

**L18–L18** — `CanvasDrafts` is the map from workflow id to draft that `App.tsx:13` owns. `WorkflowsPage.tsx:136` reads it, `WorkflowsPage.tsx:138-141` and `App.tsx:29` write it, and `Sidebar.tsx:48` reads it for node counts. Two things satisfy it today: `setNewWorkflow` from `useState` (`App.tsx:14`, handed over at `CanvasPage.tsx:18`, `:38`), because a state setter accepts an updater function, and the wrapper at `WorkflowsPage.tsx:137-142` that stores the result under one workflow's id. The type allows only the updater form, never a plain value. That matters because React Flow can deliver several change lists between two renders during a drag; each must be applied to the latest draft, not to the `draft` prop the component saw at its last render.

**L31–L33** — `addNode` starts by resolving the chosen kind to its palette entry, for the label. The `!` after `find` promises the compiler the entry exists. That promise holds because `nodeKind` can only ever be one of the `<option>` values at L87-91, which come from the same array. The `!` is erased at compile time and checks nothing at runtime: if the picker ever offered a kind missing from the palette, `find` would return `undefined` here and `type.kind` at L46 would throw a `TypeError` inside the updater on the next click. Then it makes the node id with `crypto.randomUUID()`, outside the updater on purpose: React may call an updater more than once (`StrictMode` does so in development) and expects it to return the same result each time, so the random part happens exactly once, here. A UUID also will not collide in practice with the step ids that seeded nodes reuse (`canvasDraft.ts:49`).

**L34–L43** — The updater, called by the owner with the latest draft as `current`. The comment at L35 says what the loop is for: "Reuse a free grid position when earlier nodes have been removed." It walks slot numbers from 0 and stops at the first slot that no node occupies exactly. The naive choice, `current.nodes.length`, would be wrong after a delete: with nodes in slots 0, 1, and 2, deleting slot 1 leaves a length of 2, and a new node at slot 2 would sit on top of the survivor. The loop picks slot 1. The comparison is exact equality on `x` and `y`, so a node the user dragged even one pixel no longer counts as occupying its slot; the next added node may then land under it. That is accepted behaviour for a placeholder canvas, and Reset layout (L51-60) repairs it.

**L44–L49** — The updater returns a new draft: a copy of `current` with a new `nodes` array that has the new node appended. Nothing is mutated. If the code did `current.nodes.push(...)` and returned `current`, the reference would not change and neither React nor React Flow would redraw. The closing braces end the updater, the `onChange` call, and `addNode`.

**L50–L60** — `resetLayout` hands the owner an updater that rewrites every node's `position` from its array index, in insertion order (seeded steps first, then added nodes), and clears `selected` so no tile keeps the selection outline from `CanvasNode.tsx:13` after it jumps. It does not touch the viewport; `fitView` (L121) runs only on mount, so a user who zoomed in may need the fit-view button in `Controls` (L125) to see the whole grid again. The button is at L97-104. L50 is blank.

**L61–L63** — The comment gives the layout contract: "The section fills its flex-column parent. The floor keeps a usable canvas on short screens." The parent is the tab panel with `flex min-h-0 flex-1 flex-col` at `WorkflowsPage.tsx:131` and `CanvasPage.tsx:35`. Then `return (`. L61 is blank.

## State and rendering

Where each piece lives. The nodes and name of the unfinished New workflow live in `App.tsx:14` and reach `CanvasPage` through context (L18). The per-workflow drafts live in `App.tsx:13` and reach the canvas through `WorkflowsPage.tsx:136-142`; the sidebar reads the same map for its node counts (`Sidebar.tsx:48`). The local sidebar entries live in `App.tsx:12`. The picker's chosen kind is component state inside `WorkflowCanvas` (L29) and lasts as long as that instance; `key` at `WorkflowsPage.tsx:135` ends the instance when the workflow changes. The open view lives in the URL hash, validated by `router.tsx:28-32` on every navigation, so `#/canvas?view=details` survives a reload while the draft does not. React Flow keeps its own store for the viewport (pan and zoom), the drag in progress, and the measured sizes, inside the `ReactFlow` instance; that store is created on mount, which is why `fitView` runs again after every remount. The class strings, `flowNodeTypes`, `nodePalette`, `nodeKindClass`, and `handleClass` are module scope and never change. Nothing in these four files lives in the TanStack Query cache; the New workflow page runs no query, and the lists cached by the Workflows page stay in the client (`queryClient.ts`, chapter 14) until the user returns.

What triggers a re-render. Every edit goes the same way: React Flow or a DOM event calls `onChange` with an updater, the owner's setter runs it, `App` re-renders with new state, the context value is a new object, and every consumer below re-renders, down to `ReactFlow` receiving a new `nodes` array. A drag produces many `position` change lists per second, each a full trip through `App`; that is affordable because `WorkflowsPage` is the only heavy consumer and, on the New workflow page, it is not mounted. Changing the picker re-renders only `WorkflowCanvas` (L29). Clicking a tab calls `navigate` (L23), the router re-renders the page with the new `view`, and the ternary at L37 mounts or unmounts the canvas; nodes survive the unmount because they are not stored in it. Polling never re-renders the canvas on the New workflow page, since no query is active there. On the Workflows page a poll that returns an equal list leaves the cached reference alone and nothing redraws; a changed list re-renders the page and, for a workflow with no stored draft, `draftFromWorkflow` rebuilds the nodes from the fresh steps (`WorkflowsPage.tsx:136`). After the first edit the stored draft wins and polling can no longer reset it, which is the behaviour `README.md:189-192` promises.

How the data reaches the screen. For a saved workflow, `GET /api/workflows` becomes the `Workflow` value, `draftFromWorkflow` turns each step into a `DraftNode` with `type: 'canvas'` (`canvasDraft.ts:47-50`), and the array goes into `nodes` (L108). React Flow looks up `'canvas'` in `flowNodeTypes` (L10), renders `CanvasNode` for each, and passes it `data` and `selected`; the tile draws `data.label` (`CanvasNode.tsx:16`) and picks its accent from `data.kind` (`CanvasNode.tsx:12`). For a new workflow the array starts empty (`App.tsx:14`), the overlay at L127-132 shows, and Add node appends a node built by `makeCanvasNode` (L46). The reverse path is the change list: React Flow calls `onNodesChange` (L111), `applyNodeChanges` rewrites the array, `onChange` stores it, and the next render hands React Flow the array it asked for. Create draft moves the whole `newWorkflow` object into `canvasDrafts` under a fresh `local-` id, adds the sidebar entry, selects it, and navigates (`App.tsx:19-32`), so the user lands on the Workflows page looking at the nodes they just arranged.

How errors reach the user. These files make no requests, so no server error can originate here; the connection banner belongs to the Workflows page (`WorkflowsPage.tsx:114-126`), and the New workflow page's header shows "Local draft" instead of a status dot (`AppHeader.tsx:39-40`). The one throw in this path is `useWorkspace` outside `App` (`workspace.ts:20`), which the route error boundary catches and `ErrorPage` draws (`router.tsx:55`). The `!` at L32 of `WorkflowCanvas.tsx` hides the only other throw this path could raise, a `TypeError` from `type.kind` at L46, which needs the picker to offer a kind missing from the palette; the shared array prevents that. React Flow's own complaints, such as a changing `nodeTypes` object or a container with no height, go to the browser console, not to the page. The only feedback a user sees for a bad input is the disabled Create draft button (`CanvasPage.tsx:74`); the `required` attribute at `:68` never gets to show its tooltip, because the disabled button blocks the submission that would trigger it.

## Check yourself

1. Who owns the nodes array that React Flow draws, and where does a dragged tile's new position end up stored?

<details><summary>Answer</summary>Not React Flow and not <code>WorkflowCanvas</code>. The array is part of a <code>CanvasDraft</code> in <code>App</code>'s state: <code>newWorkflow</code> (<code>App.tsx:14</code>) on the New workflow page, or one entry of <code>canvasDrafts</code> (<code>App.tsx:13</code>) on the Workflows page. A drag makes React Flow call <code>onNodesChange</code> (<code>WorkflowCanvas.tsx:111</code>) with <code>position</code> changes; <code>applyNodeChanges</code> builds a new array, the updater is passed to <code>onChange</code>, and the owner's setter stores it (<code>CanvasPage.tsx:18</code> or <code>WorkflowsPage.tsx:137-142</code>). React Flow then receives that array back as its <code>nodes</code> prop on the next render.</details>

2. Why does `addNode` call `crypto.randomUUID()` before `onChange` instead of inside the updater?

<details><summary>Answer</summary>An updater must be pure: same input, same output. React may call it more than once, and <code>StrictMode</code> (<code>main.tsx:10</code>) does so in development to catch impure updaters. A random id inside the updater would make the two calls disagree. Computing the id once at <code>WorkflowCanvas.tsx:33</code> and closing over it keeps the updater deterministic. The same reasoning is why the handler at <code>CanvasPage.tsx:62-65</code> reads <code>event.target.value</code> before building its updater.</details>

3. A draft has three nodes in slots 0, 1, and 2. The user drags the slot-0 node a little to the right, then clicks Add node. Where does the new node land, and why?

<details><summary>Answer</summary>In slot 0, partly under the dragged node. The loop at <code>WorkflowCanvas.tsx:37-43</code> asks whether any node sits at exactly <code>nodePosition(0)</code>; after the drag none does, so slot 0 is free by exact equality. The comment at L35 says the loop exists to reuse slots freed by removal, and the exact comparison treats a moved node the same way. Reset layout (L51-60) puts every node back on the grid by index and fixes the overlap.</details>

4. What happens if you delete `event.preventDefault()` at `CanvasPage.tsx:50` and click Create draft?

<details><summary>Answer</summary>The handler still calls <code>createDraft</code>, which updates <code>App</code>'s state and calls <code>navigate</code>, but the browser also performs the form's native submit: a GET navigation to the current page with <code>?workflowName=...</code> appended. That reloads <code>index.html</code>, React starts from scratch, and the new sidebar entry, the arranged nodes, and every other draft are gone, exactly the loss <code>AGENTS.md:70</code> and the paragraph at <code>CanvasPage.tsx:79-82</code> describe for a reload.</details>

5. The name is checked four times: `required` on the input, `disabled` on the button, `trim()` in `onSubmit`, and `trim()` in `App.createDraft`. Which check stops a name made only of spaces, and why keep the one in `App`?

<details><summary>Answer</summary><code>required</code> does not: a string of spaces is a non-empty value to the browser. The <code>disabled={!draft.name.trim()}</code> at <code>CanvasPage.tsx:74</code> is what stops it, by refusing the click and, through implicit submission, the Enter key. The <code>trim()</code> at <code>CanvasPage.tsx:51</code> backs that up if the button is ever enabled by other means. The check at <code>App.tsx:17-18</code> protects <code>createDraft</code> itself, so any future caller, not only this form, cannot create a draft without a name.</details>

6. Why is `flowNodeTypes` defined at module scope while `nodeKind` is defined with `useState` inside the component, when both are "canvas settings"?

<details><summary>Answer</summary>They have different lifetimes. <code>flowNodeTypes</code> never changes and React Flow compares it by reference, so creating it once (<code>WorkflowCanvas.tsx:9-10</code>) avoids a new object per render and the warning that would come with it. <code>nodeKind</code> changes when the user picks an option, must trigger a re-render, and should be separate for each canvas instance; <code>useState</code> gives it exactly that, and the <code>key</code> at <code>WorkflowsPage.tsx:135</code> resets it per workflow. Putting <code>nodeKind</code> at module scope would share one choice across all canvases and would not re-render on change; putting <code>flowNodeTypes</code> in state would be a constant pretending to be state.</details>
