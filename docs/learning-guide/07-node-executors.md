# 7. The HTTP and TCP check executors

Files: [internal/nodes/httpcheck/http.go](../../internal/nodes/httpcheck/http.go), [internal/nodes/tcpcheck/tcp.go](../../internal/nodes/tcpcheck/tcp.go), [internal/nodes/resulttext/reason.go](../../internal/nodes/resulttext/reason.go)

Revision: commit 1c4786e

## Role in the system

These three files are the only code in Patchbay that touches the network on the user's behalf. `httpcheck` sends one GET request and reports the status code it saw. `tcpcheck` opens one TCP connection and closes it. `resulttext` caps the error text both of them store. Each check package follows the pattern that `AGENTS.md:118-121` prescribes for a node type: its own package under `internal/nodes`, a `New` constructor, an `Executor` type, and one `Execute` method. There is no registry and no interface; `cmd/server/main.go:150-162` holds a plain `switch` on `step.Type` that calls one of the two `Execute` methods, and the roadmap keeps it that way "until custom nodes need registration" (`docs/roadmap.md:99`).

Data comes in as a `workflow.Step` (`internal/workflow/workflow.go:29-34`) whose `Config` was already validated at startup (`workflow.go:87-114`), plus a `context.Context` that belongs to the runner, not to any HTTP request. Data goes out as a `workflow.CheckResult` value (`workflow.go:49-59`) and an `error`. Those two returns carry different meanings, and this chapter is mostly about keeping them apart. A non-nil error means Patchbay could not carry out the check: an invalid request, or the server is shutting down. A nil error with a result means the check happened and the result says what the monitored service did, including "it was down". The roadmap sets this rule: "Represent a failed HTTP/TCP health check as a successful check operation with an `unhealthy` result and a reason. Reserve execution errors for invalid configuration or failure to carry out the operation" (`docs/roadmap.md:117`).

On the path from a browser click to a saved run, these files are the leaf. The click becomes `POST /api/workflows/{id}/runs` (`internal/httpapi/api.go:50`), the handler calls `runner.Start` (`api.go:65`), the runner launches a goroutine per run (`internal/engine/runner.go:197`), saves the step as `running` (`runner.go:233`), then calls `r.execute(r.ctx, step)` (`runner.go:247`), which is the `main.go:152` closure, which is one of these `Execute` methods. When `Execute` returns, the runner stores the result (`runner.go:257`), saves it (`runner.go:269`), and `store.UpdateRun` writes it as JSON into the `output_json` column (`internal/store/runs.go:97-110`). The browser reads it back as the `CheckOutput` type (`web/src/api.ts:27-40`) and `outputPresentation` turns `healthy`, `statusCode`, and `type` into badges and labels (`web/src/format.ts:72-88`).

## Concepts you need

- **Constructors and pointer receivers.** Go has no classes. The convention is a function `New` that returns a pointer to a struct, and methods declared with a pointer receiver such as `func (h *Executor) Execute(...)`. The pointer means every call shares the one `client` or `dial` field instead of copying it. [A Tour of Go: Pointer receivers](https://go.dev/tour/methods/4), [Effective Go: Constructors](https://go.dev/doc/effective_go#composite_literals)
- **Multiple return values and the `(value, error)` contract.** A Go function can return several values; `(workflow.CheckResult, error)` is the standard shape for "a result or a reason it could not be produced". The caller must look at the error first. Here the contract is sharper than usual: a nil error with `Healthy: false` is a normal, successful check. [A Tour of Go: Multiple results](https://go.dev/tour/basics/6), [Go blog: Error handling](https://go.dev/blog/error-handling-and-go)
- **Interfaces and type assertions.** `http.DefaultTransport` is declared as the interface type `http.RoundTripper`. Writing `x.(*http.Transport)` is a type assertion: it asks for the concrete value behind the interface and panics if the type differs. The two-value form `v, ok := x.(T)` avoids the panic; this file uses the one-value form because the standard library always stores a `*http.Transport` there. [A Tour of Go: Type assertions](https://go.dev/tour/methods/15)
- **`http.Client`, `http.Transport`, and `Transport.Clone`.** A `Client` sends requests; its `Transport` owns connections, TLS, proxies, and HTTP/2. Both are safe for concurrent use by many goroutines. `Clone` returns a deep copy of a transport's configuration with its own connection pool, so you can change settings without affecting the shared default. [net/http Client](https://pkg.go.dev/net/http#Client), [Transport](https://pkg.go.dev/net/http#Transport), [Transport.Clone](https://pkg.go.dev/net/http#Transport.Clone)
- **Function literals, unnamed parameters, and `http.ErrUseLastResponse`.** `func(*http.Request, []*http.Request) error { ... }` is an anonymous function written in place. Go lets you omit parameter names when the body never uses them. `ErrUseLastResponse` is a sentinel error value that `Client` recognizes as "stop following redirects and give me this response". [Spec: Function literals](https://go.dev/ref/spec#Function_literals), [http.ErrUseLastResponse](https://pkg.go.dev/net/http#ErrUseLastResponse)
- **Function-typed fields and method values.** A struct field can hold a function, declared with a signature such as `func(context.Context, string, string) (net.Conn, error)`. `dialer.DialContext` without parentheses is a method value: a function bound to that specific `dialer`. Storing one in a field lets a test swap in a fake with no network. [Spec: Method values](https://go.dev/ref/spec#Method_values), [Spec: Function types](https://go.dev/ref/spec#Function_types)
- **`context.WithTimeout`, parent and child contexts, `ctx.Err()`.** `WithTimeout(parent, d)` returns a child context that is canceled when `d` passes or when the parent is canceled, whichever is first, plus a `cancel` function you must call. `ctx.Err()` is nil until cancellation, then `context.Canceled` or `context.DeadlineExceeded`. A child canceled through its parent reports the parent's error, so when both carry deadlines the child cannot tell you which one fired; asking the parent can. [context](https://pkg.go.dev/context), [Go blog: Context](https://go.dev/blog/context)
- **`defer`.** A deferred call runs when the surrounding function returns, by any path. Deferred calls run last-in, first-out. It is the idiom for releasing what you acquired on the line before: `defer cancel()` after `WithTimeout`, `defer response.Body.Close()` after a successful request. `go vet` reports a `WithTimeout` whose cancel is never called. [A Tour of Go: Defer](https://go.dev/tour/flowcontrol/12), [cmd/vet lostcancel](https://pkg.go.dev/cmd/vet)
- **Error wrapping with `%w`.** `fmt.Errorf("create HTTP request: %w", err)` builds a message that still contains the original error, so a caller can use `errors.Is` or `errors.As` on it. Use `%w` for the cause and plain text for the context you add. [fmt.Errorf](https://pkg.go.dev/fmt#Errorf), [Go blog: Working with errors in Go 1.13](https://go.dev/blog/go1.13-errors)
- **`time.Duration`, `time.Now`, and `time.Since`.** A `Duration` is an `int64` count of nanoseconds. Converting an `int` with `time.Duration(n)` gives `n` nanoseconds, so you multiply by a unit constant such as `time.Millisecond`. `time.Since(start)` returns the elapsed `Duration`, and `.Milliseconds()` converts it to an `int64`. [time.Duration](https://pkg.go.dev/time#Duration), [time.Since](https://pkg.go.dev/time#Since)
- **Struct literals and value copies.** `workflow.CheckResult{URL: config.URL, ExpectedStatus: config.ExpectedStatus}` builds a struct, naming only the fields you set; the rest are zero values. Structs are copied when assigned, passed, or returned, so `step` and `result` here are private to one call. `CheckResult` holds only strings, numbers, and a bool, which is why copying it is safe and why the engine can store it in a snapshot without a deep copy. [A Tour of Go: Struct literals](https://go.dev/tour/moretypes/5)
- **`net.Dialer.DialContext`, `net.JoinHostPort`, `strconv.Itoa`.** `DialContext` resolves a name and opens a connection under one context; its deadline covers both steps, and once connected the context no longer affects the connection. `JoinHostPort` builds `host:port` and wraps an IPv6 address in brackets. `Itoa` converts an `int` to its decimal string. [net.Dialer](https://pkg.go.dev/net#Dialer.DialContext), [net.JoinHostPort](https://pkg.go.dev/net#JoinHostPort), [strconv.Itoa](https://pkg.go.dev/strconv#Itoa)
- **Strings, bytes, runes, and UTF-8.** A Go string is a sequence of bytes. `len(s)` counts bytes, `s[i]` is a byte, and `s[:n]` slices bytes, so cutting in the middle of a multibyte character produces invalid text. `strings.ToValidUTF8` replaces each run of invalid bytes; `utf8.RuneStart` tells whether a byte can begin a character. [Go blog: Strings, bytes, runes and characters](https://go.dev/blog/strings), [strings.ToValidUTF8](https://pkg.go.dev/strings#ToValidUTF8), [utf8.RuneStart](https://pkg.go.dev/unicode/utf8#RuneStart)
- **Constants and exported names.** `const` declares a value fixed at compile time; `64 * 1024` is folded by the compiler. A name that starts with a capital letter, such as `MaxReasonBytes`, is visible to other packages; a lowercase name such as `maxHTTPHeaderBytes` is private to its package. [A Tour of Go: Exported names](https://go.dev/tour/basics/3), [Go blog: Constants](https://go.dev/blog/constants)
- **Same-package tests, `httptest`, and `testing/synctest`.** A `_test.go` file that declares the same package name can read unexported fields such as `node.client` and `node.dial`. `httptest.NewServer` starts a real local HTTP server for one test. `testing/synctest` runs a test in a bubble with a fake clock, so a 100 ms timeout passes instantly. [testing](https://pkg.go.dev/testing), [net/http/httptest](https://pkg.go.dev/net/http/httptest), [testing/synctest](https://pkg.go.dev/testing/synctest)

The field is unexported, so only `New` and same-package tests (`http_limits_test.go:47`, `:96`; `http_proxy_test.go:77`, `:94`) can touch it.

It returns `*Executor` so that the pointer-receiver method at L37 operates on one shared value. Callers: `main.go:105`, `cmd/server/checks_test.go:63`, and every test in this package.

**L23–L25** — Copy the default transport. `http.DefaultTransport` is an `http.RoundTripper` interface value; `.(*http.Transport)` is a type assertion that recovers the concrete pointer, and `.Clone()` deep-copies its configuration into a transport this package owns. The comment at L23-24 states the intent: keep Go's connection, TLS, and HTTP/2 defaults, but do not change the shared transport "used by other clients". Those other clients include anything else in the process that uses `http.DefaultClient`, such as the Discord webhook delivery the roadmap plans (`docs/roadmap.md:132`). `TestHTTPChecksIgnoreEnvironmentProxy` asserts at `http_proxy_test.go:86-89` that `DefaultTransport.Proxy` is still set after `New` runs; writing `transport := http.DefaultTransport.(*http.Transport)` without `Clone()` would fail that check and silently change proxy behavior for the whole process.

**L26–L28** — Disable the proxy on the copy. The default transport's `Proxy` is `http.ProxyFromEnvironment`, which reads `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY`. Setting it to `nil` means "connect directly". The comment and `README.md:245-249` give the reason: a check measures the route from this server to the target, and a proxy would measure the proxy instead. `TestHTTPChecksIgnoreEnvironmentProxy` (`http_proxy_test.go:19`) runs itself in a child process per scheme with the proxy variables pointing at a server that rejects everything, then checks at `http_proxy_test.go:120` that the endpoint received exactly one request and the proxy none. Without this line, a Patchbay container that happens to carry proxy settings would report the proxy's refusal as the LAN service's health.

**L29** — Apply the header limit. `MaxResponseHeaderBytes` caps the bytes Go reads while parsing a response's status line and headers; past the cap, `Do` returns an error instead of a response, which L56-63 turns into an unhealthy result. `TestHTTPResponseLimits` covers HTTP/1 with hijacked raw bytes (`http_limits_test.go:26-27`), and `TestHTTP2ResponseHeaderLimit` (`http_limits_test.go:64`) proves the same field bounds HTTP/2, where the error text mentions "header list" (`http_limits_test.go:104`). This is the executor's only memory bound on what a server sends, because it never reads bodies (L65).

**L30–L34** — Build the client and the executor. `&http.Client{...}` takes the address of a composite literal, so `client` is a pointer. `Transport` is the cloned transport. `CheckRedirect` is a function literal with unnamed parameters, since it uses neither; it always returns `http.ErrUseLastResponse`, which the client treats as "return the redirect response itself, with a nil error and an open body". The comment at L32 and `README.md:242` state the policy: observe the configured endpoint's response, including redirects. `TestHealthResponses` sends a 302 with a `Location` header named `/must-not-follow` (`http_test.go:21`) and expects `StatusCode == 302` and `Healthy == false` (`http_test.go:29`). Without this line, Go would follow up to ten redirects, a 302 to a login page could look like a healthy 200, and the request could leave the host the user configured. Note that no `Timeout` field is set on the client: each step carries its own `TimeoutMS`, so the deadline comes from the context at L40.

**L35** — Closing brace of `New`.

**L36** — Blank line.

**L37** — `Execute` signature. Receiver `h`, a context, a `Step` by value, and the `(CheckResult, error)` pair. This is exactly the shape of `engine.ExecuteStep` (`runner.go:51`), and `main.go:152-161` wraps both executors in a closure of that type. The runner calls it at `runner.go:247`. The contract: a non-nil error makes the runner mark the step `failed`, or `canceled` if its own context ended (`runner.go:250-255`), and stop the run; a nil error makes it store the result as the step's output (`runner.go:257`) and continue. `README.md:236-239` describes the same split for the UI: "Completed" is about execution, "Healthy" is about the service.

**L38** — `config := step.Config` copies the `CheckConfig` value (`workflow.go:39-45`) under a short name. It arrived validated: `workflow.go:92-98` guarantees an absolute `http` or `https` URL without credentials or fragment and a status between 100 and 599, and `workflow.go:112-114` bounds `TimeoutMS` to 100-30000. The executor trusts validation and does not re-check; `AGENTS.md:131` keeps "backend validation authoritative".

**L39** — Start the result with the target. `URL` and `ExpectedStatus` are copied in before any network work, so every return carries what was checked. The browser shows both (`web/src/api.ts:35-36`), and history must still describe the check after the workflow file is edited, which `AGENTS.md:126-127` requires: "Keep historical results independent of the currently loaded workflow." `Type` is deliberately left empty: an HTTP result has no `type` field so the JSON format that existed before TCP support stays unchanged (`workflow.go:47-48`; `AGENTS.md:125-126`).

**L40–L41** — The step's own deadline. `time.Duration(config.TimeoutMS)*time.Millisecond` converts the validated integer into a duration. `checkCtx` is a child of `ctx`: it ends when the timer fires or when the runner's context is canceled, whichever is first. `defer cancel()` releases the timer on every return path; without it `go vet` reports a lost cancel and the timer would linger until it fires. Without the timeout, a target that accepts the connection and never responds would hold this run's goroutine until shutdown. The roadmap requires it: "Apply deadlines to network and process operations" (`docs/roadmap.md:119`).

**L42–L45** — Build the request under `checkCtx`. `http.NewRequestWithContext` ties the request to the context, so cancellation aborts the connection attempt and the wait for headers. The method is GET and the body is `nil`. This constructor fails only for a URL it cannot parse, an invalid method, or a nil context; validation parsed the same URL at `workflow.go:92`, so the branch is defensive. It is also the only non-cancellation error `Execute` can return. `%w` wraps the cause so a caller could unwrap it; the runner records the text at `runner.go:255` and fails the run, which is right for "invalid configuration" under `docs/roadmap.md:117`.

**L46** — Identify the checker. The target's access log shows `patchbay-m0` instead of Go's default `Go-http-client/1.1`, which helps an administrator tell monitoring traffic from real traffic. The name dates from milestone 0 and has not been changed; it has no behavioral effect.

**L47–L49** — Time the request. `h.client.Do(req)` sends the request and returns once the response status and headers are parsed, without reading the body. `DurationMS` is assigned before any branch, so a timeout, a refused connection, and a healthy response all record how long the attempt took. `README.md:241` defines the number as "receipt of HTTP response headers", and the UI labels it "Time to headers" (`web/src/format.ts:86`). `.Milliseconds()` returns `int64`, matching `CheckResult.DurationMS` (`workflow.go:57`).

**L50–L55** — Parent cancellation takes priority. This check runs before the error check at L56, and the order is the point. If the runner's context ended, `Execute` returns `ctx.Err()` and the runner marks the step `canceled` (`runner.go:252-253`). `checkCtx.Err()` alone could not reliably distinguish "my 3000 ms timer fired" from "the runner's context ended", because a child canceled along with its parent reports the parent's error, which is also `context.DeadlineExceeded` whenever the parent had a deadline; only the parent knows. The inner `if` handles a narrow timing: `Do` can return a real response just before the parent is canceled, and in that case the body must be closed to release the connection. On most error paths `response` is nil, hence the nil guard. `TestParentCancellationStopsRequest` (`http_test.go:49`) cancels the parent while the fixture holds the request open and expects `errors.Is(err, context.Canceled)` (`http_test.go:60`). Without this ordering, shutdown would write "No response within N ms" into history as if the monitored service had failed. `README.md:255` states the intended behavior, "Application shutdown cancels the operation", and the TCP test names the bug this ordering prevents: "parent deadline was reported as service health" (`tcp_test.go:143`).

**L56–L63** — A failed request is health data. This branch runs only when the parent context is alive, so a non-nil `checkCtx.Err()` can only mean the step's own timer fired; L58 writes a fixed message built from the configured timeout. Every other failure (DNS, connection refused, TLS, a malformed status line, oversized headers) uses Go's error text with a "Request failed: " prefix, passed through `LimitReason` (`reason.go:14`) because that text can echo bytes the remote server sent; `http_limits_test.go:24-25` sends a 12 KiB malformed status line and a 12 KiB malformed header to prove the bound holds. The return is `result, nil`, and the trailing comment says why: "An unreachable service is health data, not an engine failure." `StatusCode` stays 0, which `omitempty` drops from the JSON (`workflow.go:54`), so the UI prints "No response" (`web/src/format.ts:85`). `TestUnreachableAndTimeoutAreHealthData` (`http_test.go:36`) covers both sub-branches. This is the executor's half of the rule at `AGENTS.md:91`, "Distinguish execution outcome, monitored-service health, and save failure." Without it, one dead service would fail the run and skip every later step (`runner.go:282-284`), hiding the state of the other services.

**L64** — `defer response.Body.Close()`. `net/http` requires the caller to close every response body; closing releases the connection back to the transport or shuts it. Deferred, so it runs after L66-73 on both the healthy and unhealthy branches. Because the body is never read, Go cannot reuse the connection unless the body was empty; that is the accepted price of the comment at L65.

**L65–L67** — Record the status and decide health. The comment restates the memory rule: only headers are needed, and bodies are never buffered. `Healthy` is exact equality with `ExpectedStatus`. Combined with L33, a 301 or 302 when 200 is expected counts as unhealthy, which is what a user who configured the exact endpoint wants to know.

**L68–L72** — The reason text for each outcome. Both messages are built from integers only, so they are bounded by construction and do not go through `LimitReason`. The UI shows the reason under the badge, and `TestHTTPResponseLimits` checks the healthy message at `http_limits_test.go:23`.

**L73** — `return result, nil`: the check completed, whatever the service said.

**L74** — Closing brace of `Execute`.

That sentence is the whole contract: `README.md:251-253` spells out that "Connected" does not verify application health, perform a TLS handshake, or log in. `main.go:22` imports it; `main.go:106` constructs it.

**L4–L13** — Imports. `context`, `fmt`, and `time` serve the same roles as in `http.go`. `net` supplies `Dialer`, `Conn`, and `JoinHostPort`; `strconv` supplies `Itoa` for L34. The project imports are the same two packages as the HTTP executor, and again neither `engine` nor `store` appears.

**L14** — Blank line.

**L15–L19** — The `Executor` type with one function-typed field. `dial` has the signature of `net.Dialer.DialContext`: `func(context.Context, string, string) (net.Conn, error)`, where the strings are the network ("tcp") and the address. The comment at L17 explains the design: tests replace this field to exercise timeouts and cancellation without a network. `tcp_test.go:99-104` substitutes a dial that returns a fabricated DNS error, `tcp_test.go:133-136` one that blocks until its context ends, and `tcp_test.go:169-176` one that cancels the parent and then returns a live connection. This honors `AGENTS.md:135-137`, which forbids depending on live services and says to "Keep failure injection in tests", and the roadmap's "Prove cancellation with a test beside each new executor" (`docs/roadmap.md:119`). The HTTP executor needs no such field because `http.Client` already exposes a replaceable `Transport`, which `http_proxy_test.go:106` uses the same way.

**L21–L25** — `New`. `&net.Dialer{}` is a dialer with every option at its zero value, which Go defines as "dial without that option": no per-dial timeout, default dual-stack behavior. `dialer.DialContext` without parentheses is a method value, a function bound to that dialer, which is stored in the field. There is no proxy consideration here because plain TCP dialing never consults the proxy environment.

**L27** — `Execute` signature. Identical shape to `http.go:37`, with receiver `n`. Go does not require receiver names to match across packages; each package picks a short one. `main.go:157` calls it for `tcp.check` steps.

**L28** — `config := step.Config`. Validation (`workflow.go:100-108`) guarantees a host that is a bare DNS name or IP address with no brackets, port, or URL parts (`validTCPHost`, `workflow.go:119`), a port from 1 to 65535, and the same 100-30000 ms timeout bound at `workflow.go:112-114`.

Setting `Type` first means every return, including failures, identifies itself as TCP; `tcp_test.go:73-74` checks a refused connection still carries its type and target. The reason is history: HTTP results predate TCP and have no type field, so a TCP result must say what it is (`workflow.go:47-48`; `AGENTS.md:125-126`: "TCP results carry `type: "tcp.check"`; a missing result type means legacy HTTP"). The UI reads this saved type to choose the "Connected" badge and the "Time to connect" label (`web/src/format.ts:73-80`), so an old HTTP run is never relabeled (`README.md:259-260`).

**L30–L31** — The step deadline and its deferred cancel, exactly as `http.go:40-41`.

**L32–L34** — Build the dial address. `strconv.Itoa` turns the port into text and `net.JoinHostPort` joins the two, wrapping an IPv6 literal in brackets so `2001:db8::1` and port `8443` become `[2001:db8::1]:8443` (`tcp_test.go:89`). Without the brackets, the dialer could not tell where the address ends and the port begins. The comment's second sentence matters for L36: `DialContext` performs the DNS lookup and the connection attempt under one context, so the step deadline covers both, and `README.md:258` documents that the duration "includes DNS lookup and connection establishment".

**L35–L37** — Time the dial. `n.dial(checkCtx, "tcp", address)` resolves and connects; "tcp" lets Go choose IPv4 or IPv6 from what the name resolves to. `DurationMS` is recorded before any branch. `TestTCPDistinguishesStepAndParentDeadlines` checks the value equals whichever deadline fired, 100 ms or 50 ms (`tcp_test.go:125-131`, `:138`), using `synctest` so no real time passes.

**L38–L40** — Close any connection at once. This sits before every decision, so no branch can forget it. The comment states the contract: connectivity only, no data sent, no socket kept. It also covers an unusual return of both a connection and an error, which `tcp_test.go:172-174` fabricates on purpose. Once a dial succeeds, the context no longer controls the connection, so an explicit `Close` is the only thing that releases it. `TestTCPConnectsAndClosesWithoutSendingData` accepts the connection on the listener side and verifies it reads zero bytes and then `io.EOF` (`tcp_test.go:53-56`). Without this, a healthy check would leak one file descriptor per run, and a check against an SSH or database port would leave a half-open session in that service's logs.

**L41–L43** — Parent cancellation takes priority, as in `http.go:50-55`. The result goes back without a `Reason`, and the error is the parent's. `TestTCPParentCancellationTakesPriorityAndClosesConnection` (`tcp_test.go:153`) asserts `errors.Is(err, context.Canceled)` and an empty reason (`tcp_test.go:178`), then reads EOF from the peer to prove L39 ran first (`tcp_test.go:181-184`). The "parent deadline" subtest (`tcp_test.go:141-144`) checks the same for `context.DeadlineExceeded`, since the contract is about any end of the parent, not only `Cancel`.

**L44–L51** — Dial failure is health data. With the parent alive, a non-nil `checkCtx.Err()` is the step timer, so L46 writes "No connection within N ms"; everything else is "Connection failed: " plus Go's error text, bounded by `LimitReason`. The trailing comment lists the cases: refusal, DNS failure, and timeout. `README.md:253-255` promises they "do not prevent the next step from running". `TestTCPRefusedConnectionIsHealthData` (`tcp_test.go:59`) closes a listener and dials its port; `TestTCPDialFailuresAndAddressFormatting` (`tcp_test.go:78`) injects a DNS error and, in the "bounded reason" case, a 12 KiB error made of three-byte characters to prove the result is both capped and valid UTF-8 (`tcp_test.go:94`, `:109-110`).

**L52–L54** — Success. `Healthy` becomes true with a fixed reason, and the error is nil. The connection was already closed at L39.

### internal/nodes/resulttext/reason.go

**L1–L2** — Package comment and clause. "Package resulttext bounds the reason text shared by check executors." It exists because two executors needed the same guard and `AGENTS.md:122` names it as the home of "the message limiter shared by the two check executors". It imports nothing from the project, so either executor can import it without a cycle.

**L3** — Blank line.

**L4–L7** — Imports. `strings` for `ToValidUTF8` at L15, `unicode/utf8` for `RuneStart` at L22.

**L8** — Blank line.

**L9–L10** — `MaxReasonBytes`, 4 KiB. Exported so tests in other packages can derive expectations from it rather than repeating the number (`http_limits_test.go:24-25`, `:57`; `tcp_test.go:94`, `:109`). The comment says "in bytes" on purpose: Go's `len` counts bytes, and a reason full of three-byte characters holds far fewer than 4096 characters. `README.md:265` documents the cap.

**L11** — Blank line.

**L12–L14** — `LimitReason` and its doc comment. The comment makes two promises: the bound includes the prefix and the truncation marker, and it applies "before it reaches history". Its only callers are `http.go:60` and `tcp.go:48`, both on the path where Go's error text, which can quote bytes from the remote server, becomes part of the stored result. The fixed messages elsewhere never need it.

**L15** — Make the text valid UTF-8 first. `strings.ToValidUTF8` replaces each run of invalid bytes with `U+FFFD`, the replacement character, which is three bytes long, so this step can make the text longer; `reason_test.go:19-20` builds an input that fits the limit before replacement and overflows after. Running it first keeps the length check at L16 honest and, more importantly, makes the loop at L22 safe: on an arbitrary byte string, a long run of continuation bytes could walk `end` below zero and panic with an index out of range. `encoding/json` would replace invalid bytes anyway when `store.UpdateRun` marshals the result (`internal/store/runs.go:99`), so raw bytes never reach SQLite; but that replacement would happen after the limit was measured and could grow the stored reason past `MaxReasonBytes`. Doing it here means the text the limit measured is the text that is stored and shown, which `README.md:266-268` describes as "Invalid UTF-8 is replaced" and "The text limit applies before JSON escaping".

**L16–L18** — The fast path. Text that fits is returned unchanged, including text of exactly `MaxReasonBytes` (`reason_test.go:15`).

**L19** — The marker, declared as a function-local constant. It is 15 bytes, and `README.md:266` promises the exact text `... [truncated]`, which `http_limits_test.go:57` and `tcp_test.go:93` check.

**L20** — `end` is the cut index: the limit minus the marker, so that the kept bytes plus the marker never exceed the limit.

**L21–L24** — Back up to a character boundary. `utf8.RuneStart(b)` is true for an ASCII byte or the first byte of a multibyte character and false for a continuation byte. The loop moves `end` down until the byte at `end` begins a character, so `reason[:end]` ends with a complete one. On valid UTF-8 this takes at most three steps, since no character is longer than four bytes. `reason_test.go:17` proves it with a string of three-byte characters, where the arithmetic at L20 lands one byte into a character. Without the loop, the result would be invalid UTF-8, the UI would show a stray replacement character, and the tests that assert `utf8.ValidString` would fail.

**L25** — Slice the kept bytes and append the marker. `reason[:end]` is bytes 0 through `end-1`; the total is at most `MaxReasonBytes`.

**L26** — Closing brace of `LimitReason`.

## State, concurrency, and cancellation

**Who runs this code.** Every `Execute` call runs on a run goroutine that the runner started with `go r.run(...)` (`runner.go:197`), one goroutine per active run. Different workflows run at the same time, so two calls to the same `Execute` method can overlap. That is why neither executor keeps any per-call state in its struct: `step`, `config`, `result`, `checkCtx`, `req`, `response`, `address`, and `connection` are all locals owned by one call. The only shared things are the `http.Client` and the `dial` function, both documented as safe for concurrent use. There is no mutex in these files and no lock order to learn. The runner's history mutex is never held while `Execute` runs; the comment at `runner.go:246` says "Neither external work nor database writes hold the history mutex." The executors must not call back into the runner, and they do not import it, so that invariant cannot be broken from here.

**Which context, and what cancels it.** The `ctx` parameter is `r.ctx` (`runner.go:247`), created from `context.Background()` in `engine.New` (`runner.go:97`). It has no deadline. `Runner.Close` cancels it (`runner.go:176-179`), and `main.go:140` calls `Close` when the process receives SIGINT or SIGTERM (`main.go:38`, `:137-140`); `main.go:115` also defers it so any startup error path stops the runner. The browser's HTTP request has no part in this: the handler returns `202` while the run keeps going, which is `AGENTS.md:84-85`, "Accepted runs belong to the runner's context, not the originating HTTP request." Each `Execute` derives `checkCtx` from `ctx` with the step's own `TimeoutMS` and cancels it on return through `defer cancel()`. The network call sees only `checkCtx`, which ends on the earlier of the step timer and the runner's cancellation.

**Every failure path and its result.**

| What happens | HTTP (`http.go`) | TCP (`tcp.go`) | What the runner does |
| --- | --- | --- | --- |
| Request cannot be built | L43-45: returns `fmt.Errorf(...)` | not applicable | `runner.go:250-255`: step `failed`, run stops |
| Runner context canceled during the call | L50-55: closes any body, returns `ctx.Err()` | L39, L41-43: closes any connection, returns `ctx.Err()` | `runner.go:252-253`: step `canceled`; result ignored |
| Step timer fires, runner alive | L57-58: "No response within N ms", nil error | L45-46: "No connection within N ms", nil error | `runner.go:257`: stored as output, next step runs |
| DNS, refusal, TLS, malformed or oversized response | L60: "Request failed: ..." bounded, nil error | L48: "Connection failed: ..." bounded, nil error | same as above |
| Response arrives | L66-72: `Healthy` iff status matches | L52-53: `Healthy` true | same as above |

After the executor returns, the runner saves the result (`runner.go:269`). A failed save is handled there, never here: `AGENTS.md:86` says "Save step start before execution and step result before proceeding", and the executors stay out of persistence entirely so that rule lives in one place.

**Why repeating a check is safe.** Both executors are read-only probes: a GET with no body, a connect followed by a close. `AGENTS.md:98-99` warns "Never infer that an uncertain external action is safe to repeat", and that caution is why startup marks interrupted runs rather than re-executing them. Today's executors would be safe to repeat; the SSH and script executors the roadmap plans will not be, and the rule is written for them.

**Rules from `AGENTS.md` that this code implements.**
- "Executors and update callbacks may run concurrently for different workflows." (`AGENTS.md:80`) The executors hold no per-call state and share only concurrency-safe values.
- "Accepted runs belong to the runner's context, not the originating HTTP request." (`AGENTS.md:84-85`) `Execute` receives `r.ctx`, and the cancellation branches at `http.go:50` and `tcp.go:41` answer to it.
- "Distinguish execution outcome, monitored-service health, and save failure." (`AGENTS.md:91`) The nil-error returns at `http.go:62` and `tcp.go:50` carry an unhealthy service as data; the error returns at `http.go:44`, `http.go:54`, and `tcp.go:42` carry an execution failure.
- "TCP results carry `type: "tcp.check"`; a missing result type means legacy HTTP." (`AGENTS.md:125-126`) `tcp.go:29` sets the type; `http.go:39` leaves it empty.
- "`resulttext` holds the message limiter shared by the two check executors." (`AGENTS.md:122`) `http.go:60` and `tcp.go:48` are its only callers.
- "Use fake executors, temporary databases, local test servers ... Keep failure injection in tests." (`AGENTS.md:135-137`) The `dial` field at `tcp.go:18` and the `client` field at `http.go:18` exist so tests can inject failures without a network.

## Check yourself

1. `http.go:50` checks the parent `ctx.Err()` before `http.go:56` checks `err`. Swap them in your head. During shutdown, what would the saved step look like, and which test catches it?

<details><summary>Answer</summary>When the runner cancels <code>r.ctx</code>, <code>checkCtx</code> is canceled with it and <code>Do</code> returns an error. With the checks swapped, the code would reach the error branch first, see <code>checkCtx.Err() != nil</code>, and return "No response within N ms" with a nil error. The runner would store that as a successful check of an unhealthy service (<code>runner.go:257</code>) instead of marking the step <code>canceled</code> (<code>runner.go:252-253</code>), so history would blame the monitored service for a Patchbay restart. <code>TestParentCancellationStopsRequest</code> (<code>http_test.go:49</code>) fails because <code>errors.Is(err, context.Canceled)</code> is false. The TCP equivalents are the "parent deadline" subtest at <code>tcp_test.go:141-144</code> and <code>TestTCPParentCancellationTakesPriorityAndClosesConnection</code>.</details>

2. A fake dial returns both a live `net.Conn` and a non-nil error. Trace `tcp.go:36-51` and say what happens to the connection and what the caller receives.

<details><summary>Answer</summary>L37 records the duration. L38-40 close the connection immediately, because the close runs before any branch looks at <code>err</code>. If the parent context is alive, L44-51 treat the error as health data and return an unhealthy result with a bounded "Connection failed: ..." reason and a nil error. If the parent was canceled, L41-43 return <code>ctx.Err()</code> with no reason. Either way the socket is released. <code>tcp_test.go:172-174</code> fabricates exactly this case and <code>tcp_test.go:181-184</code> proves the peer sees EOF.</details>

3. Why does `New` call `Clone()` at `http.go:25` instead of setting `Proxy = nil` on `http.DefaultTransport` directly? Name the test that would fail and the line that fails it.

<details><summary>Answer</summary><code>http.DefaultTransport</code> is shared by every <code>http.Client</code> in the process that does not set its own transport, including <code>http.DefaultClient</code> and any future Discord webhook client. Changing it would silently disable proxies and shrink header limits for all of them, and would couple this package's behavior to whoever else touched the global. <code>Clone()</code> gives this executor its own configuration and connection pool. <code>TestHTTPChecksIgnoreEnvironmentProxy</code> fails at <code>http_proxy_test.go:87-88</code> with "New changed the shared default transport's proxy policy".</details>

4. Follow a `CheckResult` from `http.go:73` to SQLite. Who takes its address, and why does the engine not need a deep copy of it?

<details><summary>Answer</summary><code>Execute</code> returns the struct by value. The <code>main.go:155</code> closure passes it through unchanged. At <code>runner.go:247</code> the run goroutine receives its own copy in <code>output</code>, and <code>runner.go:257</code> stores <code>&output</code> in <code>StepRun.Output</code>. <code>store.UpdateRun</code> marshals that pointer's target to JSON at <code>internal/store/runs.go:97-103</code>. <code>CheckResult</code> contains only strings, integers, and a bool (<code>workflow.go:49-59</code>), no slices, maps, or pointers, so copying the struct copies all of its data; <code>AGENTS.md:130</code> says to "revisit snapshot copying if adding nested pointers", which is the day this stops being true.</details>

5. `reason.go:15` runs `ToValidUTF8` before the length check at L16. Give two concrete things that go wrong if you move it below the loop, after L24.

<details><summary>Answer</summary>First, the bound breaks: the fast path at L16-18 would return invalid bytes untouched, and when <code>store.UpdateRun</code> marshals the result <code>encoding/json</code> turns each run of bad bytes into a three-byte <code>U+FFFD</code>, so text that measured 4096 bytes at L16 is stored longer than <code>MaxReasonBytes</code> (<code>reason_test.go:19-20</code> is built to show this: its input fits the limit before replacement and overflows after, so <code>got != test.want</code> fails). Second, the loop at L22-24 would run on possibly invalid bytes; a string that is nothing but continuation bytes makes <code>RuneStart</code> false at every index, so <code>end</code> decrements past zero and <code>reason[end]</code> panics with an index out of range, and since nothing in the runner calls <code>recover</code>, that panic ends the whole server process.</details>

6. A TCP step's target refuses the connection. Say what `Execute` returns, what status the step gets, and whether the next step in the workflow runs. Then say what changes if the executor returned an error instead.

<details><summary>Answer</summary><code>Execute</code> returns a result with <code>Healthy: false</code>, <code>Reason</code> beginning "Connection failed: ", the type, host, port, and duration, plus a nil error (<code>tcp.go:48-50</code>). The runner marks the step <code>succeeded</code> with that output (<code>runner.go:257</code>), saves it, and continues to the next step; the UI shows an "Unreachable" badge (<code>web/src/format.ts:75</code>) and the run summary counts one check that did not pass. If the executor returned an error instead, <code>runner.go:251-255</code> would mark the step <code>failed</code> with the error text and no output, <code>runner.go:282-284</code> would break out of the loop, and <code>finishRun</code> would mark the remaining steps <code>skipped</code>, so a single outage would hide the state of every later service.</details>
