# 5. Strict step decoding and cron schedules

Files: [internal/workflow/step_json.go](../../internal/workflow/step_json.go), [internal/workflow/schedule.go](../../internal/workflow/schedule.go)

Revision: commit 1c4786e

## Role in the system

Chapter 4 showed that `Load` decodes each workflow file into a `Definition` with `DisallowUnknownFields` switched on (`internal/workflow/workflow.go:173-177`). That strictness stops at the edge of every `Step`, because `Step` takes over its own decoding. `step_json.go` holds that custom decoder. Its job is to read one step object in the flat JSON shape the README documents, pick the allowed `config` keys by the step's `type`, refuse everything else, and only then fill the shared `CheckConfig` value that the rest of the backend uses. It runs exactly once per step, at startup, inside `Load` (`workflow.go:175`, called from `cmd/server/main.go:58`). After that the decoded `Step` travels by copy: the runner copies its ID and name into each `StepRun` (`internal/engine/runner.go:134`), and the two executors read `step.Config` to build their requests (`internal/nodes/httpcheck/http.go:37-40`, `internal/nodes/tcpcheck/tcp.go:27-30`). The file was added with TCP support in commit 14ba1b0, because that was the moment one `config` object could mean two different things.

`schedule.go` holds the other optional part of a workflow file: the `schedule` object with its `cron` and `timezone` keys. It defines the `Schedule` data type and a `Timetable` that can answer one question, "when is the next occurrence after this instant?". `NewTimetable` is the validator for a schedule. `Validate` calls it to reject bad files at startup (`workflow.go:70-73`), the scheduler calls it again to keep the parsed timetable per workflow (`internal/schedule/scheduler.go:62`), and the scheduler's goroutines call `Next` to compute each occurrence (`scheduler.go:87`, `scheduler.go:139`). The file was added with cron scheduling in commit 7bc8df5.

On the path from a browser click to a saved run, both files sit before the click. When the page loads, `GET /api/workflows` returns each definition with its steps and schedule in the file's shape, plus a `nextRunAt` computed by `Timetable.Next` (`internal/httpapi/api.go:38-48`, `web/src/api.ts:21-24`). When the user clicks Run, `POST /api/workflows/{id}/runs` hands the in-memory definition to `Runner.Start` (`api.go:65`), which calls `Validate` and therefore `NewTimetable` again (`runner.go:106`, `workflow.go:71`), copies the schedule pointer (`runner.go:110-113`), and saves the whole definition as JSON in the `runs` table (`internal/store/runs.go:18`). The scheduled path replaces the click with a timer: `Scheduler.loop` waits for the instant that `Next` returned and then calls the same `Runner.Start` (`scheduler.go:119-125`). Neither file starts a goroutine, holds a lock, or touches the network. They are pure data and validation, like the rest of the package.

## Concepts you need

- **Pointer receivers versus value receivers.** `func (s *Step) UnmarshalJSON(...)` has a pointer receiver, so the method can change the caller's `Step` through `*s = step`. `func (t Timetable) Next(...)` has a value receiver, so it works on a copy and can never change the stored timetable. Go picks the receiver kind per method; use a pointer when the method must mutate or the struct is large, a value when the method only reads. [Go Tour: pointer receivers](https://go.dev/tour/methods/4), [Effective Go: pointers vs. values](https://go.dev/doc/effective_go#pointers_vs_values)
- **Interfaces are satisfied implicitly, and `json.Unmarshaler`.** `encoding/json` defines `type Unmarshaler interface { UnmarshalJSON([]byte) error }`. Nothing in `step_json.go` says "Step implements Unmarshaler"; the method with the right name and signature is enough. When the decoder in `Load` reaches an element of `Definition.Steps`, it sees that `*Step` has this method, hands it the raw bytes of that one object, and uses whatever the method leaves in the struct. The outer decoder's `DisallowUnknownFields` does not reach inside, which is why this file repeats the strictness itself. [encoding/json: Unmarshaler](https://pkg.go.dev/encoding/json#Unmarshaler), [Go Tour: interfaces are implemented implicitly](https://go.dev/tour/methods/10)
- **Anonymous struct types.** `var wire struct { ID string ... }` declares a variable whose type has no name. It exists only inside this function, so nothing else can depend on it. The file uses three: one for the step's outer keys and one for each check type's `config` keys. Each one lists exactly the JSON keys that are legal in that place, and the strict decoder turns "not in this list" into an error. [Go spec: struct types](https://go.dev/ref/spec#Struct_types)
- **`json.RawMessage`.** A `RawMessage` is a `[]byte` that the decoder fills with the exact bytes of one JSON value without interpreting them. It lets you read the `type` key first and decide later how to decode `config`. Its cost is that the bytes are not checked when captured, which is what the duplicate-key guard in this file compensates for. [encoding/json: RawMessage](https://pkg.go.dev/encoding/json#RawMessage)
- **Streaming with `json.Decoder`: `Token`, `More`, `Delim`, and mixing in `Decode`.** `Token()` returns the next piece of JSON: a delimiter (`{`, `}`, `[`, `]`) as a `json.Delim`, an object key as a `string`, or a scalar. `More()` reports whether the current object or array has another element. In between tokens you may call `Decode` to swallow one whole value, however deeply nested. This file walks an object's keys with `Token` and skips each value with `Decode`. [encoding/json: Decoder.Token](https://pkg.go.dev/encoding/json#Decoder.Token), [encoding/json: Decoder.More](https://pkg.go.dev/encoding/json#Decoder.More)
- **Type assertions and comparing interface values.** `Token()` returns the interface type `json.Token` (declared as `type Token any`, an empty interface). `key, ok := token.(string)` asks "is the dynamic value a string?" and gives `ok` instead of panicking when it is not. `opening != json.Delim('{')` compares an interface value with a concrete `Delim`; the comparison is true only when both the dynamic type and the value match. [Go Tour: type assertions](https://go.dev/tour/methods/15), [Go spec: comparison operators](https://go.dev/ref/spec#Comparison_operators)
- **`any`, `new`, and the `io.EOF` sentinel.** `any` is the empty interface; a value of any type fits in it. `new(any)` allocates one and returns its pointer, which gives `Decode` a target that accepts any JSON value. `io.EOF` is a package-level error value that readers return at end of input; `Decode` returns it unwrapped when nothing is left, so the code compares with `!=` directly. [builtin: any](https://pkg.go.dev/builtin#any), [builtin: new](https://pkg.go.dev/builtin#new), [io: EOF](https://pkg.go.dev/io#EOF)
- **`bytes.NewReader` and the `io.Reader` interface.** `json.NewDecoder` wants an `io.Reader`, a stream. `bytes.NewReader(data)` wraps a byte slice so it looks like a stream. `workflow.go:173` does the same with `strings.NewReader`; the two readers differ only in the input type. [bytes: NewReader](https://pkg.go.dev/bytes#NewReader), [io: Reader](https://pkg.go.dev/io#Reader)
- **Case-insensitive key matching in `encoding/json`.** The documentation for `Unmarshal` says it matches a key to a field "preferring an exact match but also accepting a case-insensitive match". So `"ID"` fills the `id` field, and `"Config"` fills `config`. A duplicate check that compared keys exactly would miss those. [encoding/json: Unmarshal](https://pkg.go.dev/encoding/json#Unmarshal)
- **Build locally, assign at the end.** `UnmarshalJSON` fills a local `step` and only writes `*s = step` on the last line before `return nil`. If any earlier check fails, the caller's value is untouched. The test `tcp_test.go:123-125` checks exactly this property. The pattern is general: when a function can fail halfway, do not mutate the shared result until success is certain. [Go spec: assignment statements](https://go.dev/ref/spec#Assignment_statements)
- **`fmt.Errorf` with `%q` and `%w`.** `%q` prints a Go-quoted string, so an empty ID shows as `""` instead of disappearing. `%w` wraps the inner error so its text is kept and `errors.Is` can still find it. Chapter 4 introduced both; this file uses them in every error that leaves a decoder. [fmt: Errorf](https://pkg.go.dev/fmt#Errorf), [Working with Errors in Go 1.13](https://go.dev/blog/go1.13-errors)
- **Third-party modules and the `/v3` major-version suffix.** `github.com/robfig/cron/v3` is the module path, with the major version as its last element, and `go.mod:6` pins `v3.0.1`. In the code the package is still referred to as `cron`. `gofmt` sorts imports within each blank-line-separated group; the convention is standard-library imports in one group and third-party imports in another. [Go Modules Reference: major version suffixes](https://go.dev/ref/mod#major-version-suffixes)
- **Interface-typed fields and unexported fields.** `Timetable.schedule` has the interface type `cron.Schedule`, whose only method is `Next(time.Time) time.Time`. The field holds whichever concrete schedule the parser returned. Both fields are lowercase, so code outside the package cannot set them; the only way to get a usable `Timetable` is `NewTimetable`. A zero `Timetable{}` has a nil interface, and calling `Next` on it would panic, so the constructor is the gate. [cron: Schedule](https://pkg.go.dev/github.com/robfig/cron/v3#Schedule), [Effective Go: interfaces](https://go.dev/doc/effective_go#interfaces)
- **Returning a zero value with an error.** Every failure in `NewTimetable` returns `Timetable{}, err`. The convention is that a non-nil error means "ignore the other result", and returning the zero value instead of a half-built one makes accidental use harmless to read, though still a bug. [Effective Go: multiple return values](https://go.dev/doc/effective_go#multiple-returns)
- **`time.Duration` and its typed constants.** `time.Minute` is a `time.Duration`, an `int64` count of nanoseconds with its own type. `const minimumInterval = time.Minute` therefore has type `time.Duration`, and `second.Sub(first)` returns the same type, so the comparison needs no conversion. [time: Duration](https://pkg.go.dev/time#Duration)
- **`time.Location`, `LoadLocation`, `Time.In`, `IsZero`, and `Sub`.** A `time.Time` is an instant plus a `*Location` that decides how it prints and how its wall-clock fields read. `LoadLocation("Europe/Amsterdam")` reads the IANA zone database; it returns UTC for `""` and the host's zone for `"Local"`. `t.In(loc)` keeps the instant and changes the location. `IsZero` reports the zero time, which the cron library uses to mean "no occurrence". [time: LoadLocation](https://pkg.go.dev/time#LoadLocation), [time: Time.In](https://pkg.go.dev/time#Time.In)
- **The embedded zone database `time/tzdata`.** `cmd/server/main.go:17` imports `_ "time/tzdata"` for its side effect: the binary carries a copy of the zone database, used when the host has none. `README.md:389-390` describes this. Without it, `LoadLocation` on a minimal container would fail for every zone but UTC. [time/tzdata](https://pkg.go.dev/time/tzdata)
- **Cron expressions and `robfig/cron`.** `cron.ParseStandard` accepts the classic five fields (minute, hour, day of month, month, day of week) and descriptors such as `@hourly` and `@every 30m`. The parser also accepts a `TZ=` or `CRON_TZ=` prefix, which this file forbids. The returned schedule's `Next` searches forward field by field and gives up with the zero time after five years. `docs/roadmap.md:85` names this library as the chosen parser. [cron: ParseStandard](https://pkg.go.dev/github.com/robfig/cron/v3#ParseStandard), [cron package overview](https://pkg.go.dev/github.com/robfig/cron/v3)
- **`strings.TrimSpace` and `strings.Contains`.** Small helpers used for the first two schedule checks: `TrimSpace` so that `"   "` counts as empty, and `Contains` so a time-zone prefix is found whatever comes before `TZ=`. [strings: TrimSpace](https://pkg.go.dev/strings#TrimSpace), [strings: Contains](https://pkg.go.dev/strings#Contains)

## Walkthrough

### internal/workflow/step_json.go

**L1–L2** — `package workflow` and a blank line. This file belongs to the same package as `workflow.go`, so it can attach a method to `Step` and read the lowercase `CheckConfig` fields directly. Go lets a type's methods live in any file of its package; the type is declared at `workflow.go:29-34`, and its decoder lives here to keep the data declarations and the decoding rules readable separately.

**L3–L10** — The import block, standard library only, and a blank line. `bytes` provides `NewReader` for both decoders (L59, L93). `encoding/json` provides `Decoder`, `RawMessage`, `Delim`, and `Token`. `fmt` builds the error messages. `io` is used once, for the `io.EOF` comparison at L98. `strings` is used once, for `ToLower` at L78. Delete any of these uses and the compiler reports the import as unused. The cron library is imported by `schedule.go:8`, not here.

**L11–L13** — The doc comment for `UnmarshalJSON`. It states the two design decisions of this file. First, "selects the config by type while preserving the existing flat JSON shape": the file format did not change when TCP arrived, a step is still `{id, name, type, config}`, and `Step` has no custom `MarshalJSON`, so encoding still follows the tags in `workflow.go:29-34` and `workflow.go:40-44`. `tcp_test.go:73-104` proves a decode-then-encode round trip reproduces the file. Second, "Each decoder is strict: even a zero-valued field for the other check type is rejected": `"host": ""` inside an HTTP config is an error, not a harmless no-op. `README.md:321-322` documents that promise to authors. The reason is that silently dropping a field during conversion hides mistakes, and `AGENTS.md:131` says to "Keep backend validation authoritative".

**L14** — `func (s *Step) UnmarshalJSON(data []byte) error`. The signature matches `json.Unmarshaler`, so `encoding/json` calls it for every `Step` it decodes. In production that happens in `Load` (`workflow.go:175`) for each element of the `steps` array. The tests call `json.Unmarshal` on a lone `Step` (`tcp_test.go:120`, `tcp_test.go:139`). `data` holds exactly one JSON value, the step object, as the outer decoder captured it. The receiver is a pointer because the method must store the result into the caller's struct at L52.

**L15–L17** — The first action is `rejectDuplicateStepFields(data)`, before anything is decoded. Order matters: `encoding/json` does not reject a repeated key; the last value wins. With `config` captured as a `RawMessage` (L22), a first `config` full of unknown fields would be overwritten by a clean second `config` and never inspected. The comment at L56-57 explains this, and `tcp_test.go:129-147` lists five inputs that must fail here, including `"config"` followed by `"Config"` and `"id"` followed by `"ID"`. Without this call, four of those five files would load; the second, whose last `config` holds the unknown field, would still fail, but with an unknown-field message rather than a duplicate-field one.

**L18–L23** — The anonymous `wire` struct. It describes the step's outer keys exactly: `id`, `name`, `type`, and `config`. The first three are plain strings. `Config` is a `json.RawMessage`, so its bytes are captured but not yet interpreted, because the right shape depends on `Type`, which is not known until this object is decoded. The variable is named `wire` to say "this is the shape on the wire, not the Go shape"; the Go shape is `Step` with a typed `CheckConfig`.

**L24–L26** — `decodeStrict(data, &wire)` fills the four fields and fails on any other key. This is where `"extra": true` at the step level is refused (`tcp_test.go:108`) and where a `data` that holds more than one JSON value is refused (L98-100). The error is returned as is, since `decodeStrict` already produces a readable message and the caller, `Load`, adds the file path (`workflow.go:176`).

**L27** — `step := Step{ID: wire.ID, Name: wire.Name, Type: wire.Type}` starts the result as a local value with an empty `Config`. It is deliberately not `*s`. If a later line fails, the caller's `Step` stays as it was, which `tcp_test.go:123-125` checks with `got != original`. That comparison works because `Step` is comparable (chapter 4).

**L28** — `switch wire.Type {` dispatches on the step type string. There are exactly two supported values; `AGENTS.md:129` says "There is no generic node registry", and this switch is the explicit, readable alternative. `Validate` has the same three branches at `workflow.go:87-111`, and `cmd/server/main.go` has the matching executor dispatch.

**L29–L34** — The `"http.check"` case and its anonymous `config` struct with `url`, `expectedStatus`, and `timeoutMs`. The struct lists the only legal keys for an HTTP config. Because `host` and `port` are absent from it, the strict decoder treats them as unknown even when their values are `""` or `0` (`tcp_test.go:109-110`). That is how the promise at L12-13 is kept without any value inspection. The field types matter too: `ExpectedStatus int` means `"expectedStatus": "200"` is a type error, not a silent coercion.

**L35–L37** — `decodeStrict(wire.Config, &config)` decodes the captured bytes. On failure, the error is wrapped as `step %q HTTP config: %w`, so the message names the step and the config kind before the decoder's own text, for example `step "health" HTTP config: json: unknown field "host"`. One edge: when the file has no `config` key at all, `wire.Config` is nil, the decoder reads empty input, and `Decode` returns `io.EOF`, so the message ends in `EOF`. It is terse but still identifies the step. A `config` of `null` passes here with zero fields and is rejected by `Validate` at `workflow.go:92-95`.

**L38** — `step.Config = CheckConfig{URL: ..., ExpectedStatus: ..., TimeoutMS: ...}` copies the three HTTP values into the shared struct from `workflow.go:39-45`. `Host` and `Port` keep their zero values, which is exactly what `Validate` checks at `workflow.go:89-91` for definitions built in Go code. The executor reads these fields at `http.go:38-40`.

**L39–L44** — The `"tcp.check"` case with its own anonymous struct: `host`, `port`, and `timeoutMs`. Same mechanism, mirrored: `url` and `expectedStatus` are unknown here (`tcp_test.go:111-112`), `"port": "22"` is a type error (`tcp_test.go:114`), and `"port": 22.5` is a type error because `22.5` does not fit an `int` (`tcp_test.go:115`).

**L45–L47** — The TCP config decode, wrapped as `step %q TCP config: %w`. The two messages differ only in the kind name, so a reader of the server log knows which branch failed without opening the file.

**L48** — `step.Config = CheckConfig{Host: ..., Port: ..., TimeoutMS: ...}`. `URL` and `ExpectedStatus` remain zero, which `workflow.go:100-102` relies on for the programmatic path. The TCP executor reads `Host`, `Port`, and `TimeoutMS` at `tcp.go:28-30`.

**L49–L51** — `default:` returns `step %q type must be http.check or tcp.check`. The text is identical to `workflow.go:110`, and that is intentional: there are two entrances, JSON files and Go code, and both report the same rule. `tcp_test.go:116` feeds `ssh.command` through this branch. Without this `default`, an unknown type would fall out of the switch with an empty `Config`, and the problem would surface later and less clearly in `Validate`.

**L52** — `*s = step` publishes the result through the pointer receiver. This is the only write to the caller's value in the whole method, and it happens only after every check passed. The decoder in `Load` then moves on to the next array element.

**L53–L55** — `return nil`, the closing brace, and a blank line. A nil error tells `encoding/json` the step decoded successfully.

**L56–L57** — The doc comment for `rejectDuplicateStepFields`. It scopes the function to "only the step object's keys" and explains the threat: "accepting a second config here could hide unknown fields in the first one". Notice what is not guarded. Duplicates inside `config` are tolerated, because both values go through the same strict decoder and nothing can be hidden; the last one simply wins. Duplicates at the `Definition` level, such as two `schedule` keys, are also not detected, for the same reason: `Schedule` and `Definition` have no `RawMessage` fields, so every value is decoded strictly. The guard exists precisely where deferred decoding exists.

**L58–L59** — The signature and a `json.Decoder` over the same bytes. This decoder is separate from the one in `decodeStrict`; it is used only for tokens and is discarded when the function returns.

**L60–L63** — `decoder.Token()` reads the first token. Errors here are a syntax error at the very start or `io.EOF` for empty input. When called through `Load`, the bytes are never empty, but the direct `json.Unmarshal` path in tests and any future caller can send anything, so the error is returned rather than assumed away.

**L64–L66** — `if opening != json.Delim('{')` requires an object. A step written as an array, a string, or `null` fails here with `step must be a JSON object`. The comparison works because `Token()` returned an interface value whose dynamic type is `json.Delim` for delimiters; a string token would compare unequal even if it contained `{`.

**L67** — `seen := make(map[string]bool)` is the set of key names met so far, the same map-as-set idiom as `workflow.go:78`.

**L68** — `for decoder.More() {` loops while the object has another member. `More` looks ahead without consuming, so the loop ends exactly at the closing `}` and leaves it for L88.

**L69–L72** — Read the next token, which inside an object is the member's key. A syntax error at this point, such as a missing comma, is returned as the decoder reports it.

**L73–L76** — `key, ok := token.(string)` asserts the key is a string. The decoder itself only returns string keys inside an object, so the `!ok` branch is defensive: it turns an impossible state into a clear error rather than a panic. Defensive checks like this are cheap when the alternative is a crash during startup.

**L77–L82** — The comment states the rule: "encoding/json accepts case-insensitive matches for these ASCII names." So the key is lowered with `strings.ToLower` before the `seen` test, and `"Config"` after `"config"` is a duplicate (`tcp_test.go:133`), as is `"ID"` after `"id"` (`tcp_test.go:135`). The error quotes the original spelling with `%q` so the author can find it. `ToLower` is enough because the four legal keys are ASCII; `encoding/json` uses a Unicode case fold, but the only non-ASCII runes that fold to an ASCII letter are the Kelvin sign (to `k`) and the long s (to `s`), and neither letter appears in the four names, so no exotic key can match a field that ASCII lowering misses. Without the lowering, the third and fifth inputs of `TestStepJSONRejectsDuplicateMembers` would load.

**L83–L86** — `var value json.RawMessage` and `decoder.Decode(&value)` consume the member's value, whatever it is, including a nested object or array. This is the "mix `Decode` with `Token`" technique from the concepts list. The value is thrown away; this function cares only about key names. Using `Decode` rather than more `Token` calls means nested braces are handled by the library, not by hand-written nesting counters.

**L87** — Closes the `for` loop.

**L88–L89** — `_, err = decoder.Token()` consumes the closing `}`; the comment says so. The result is returned directly: `nil` on a well-formed object, or the syntax error if the object never closed. Trailing bytes after the `}` are not examined here; `decodeStrict` catches them at L98-100.

**L90–L91** — The closing brace and a blank line.

**L92** — `func decodeStrict(data []byte, target any) error`. A small helper used three times (L24, L35, L45). `target` is `any` so one function serves the three different anonymous struct types; each call passes a pointer, as `Decode` requires.

**L93–L94** — A fresh decoder with `DisallowUnknownFields()`. This single call is what makes every anonymous struct above an allowlist. `Load` sets the same option on the outer decoder (`workflow.go:174`); because custom unmarshalers do not inherit decoder options, it has to be set again here.

**L95–L97** — `decoder.Decode(target)` fills the struct and returns the first problem: an unknown field, a type mismatch, a syntax error, or `io.EOF` for empty input. The error is returned unchanged; the callers at L36 and L46 add the step context.

**L98–L100** — `decoder.Decode(new(any))` must return `io.EOF`. If it decodes something, or fails for another reason, `data` held more than one JSON value and the function reports `expected exactly one JSON document`. `Load` applies the same check to the whole file at `workflow.go:178-180`. Inside `Load` the step bytes are always a single value, so this guard protects the direct-call path and keeps the helper correct no matter who calls it.

**L101–L102** — `return nil` and the closing brace.

### internal/workflow/schedule.go

**L1–L2** — `package workflow` and a blank line. `Schedule` lives here rather than in its own package because `Definition` holds a pointer to it (`workflow.go:25`) and `Validate` must call `NewTimetable`. Keeping both in one package avoids an import cycle between a schedule package and the workflow package.

**L3–L10** — Imports in two groups and a blank line. The standard library group: `fmt` for errors, `strings` for the two text checks, `time` for locations and durations. The third-party group: `github.com/robfig/cron/v3`, the package's only external dependency, pinned at `go.mod:6` to `v3.0.1`. The blank line between the groups is the convention for separating standard from external imports; `gofmt` sorts each group on its own. `docs/roadmap.md:85` records the decision to use this library "for parsing and time calculations" while "the application owns admission, overlap, and restart policy".

**L11–L12** — The doc comment for `Schedule`: an optional trigger, and "A workflow with a schedule can still be started by hand." That second sentence is a design rule the API honors: `api.go:61-65` starts any loaded workflow on request, scheduled or not, and `README.md:345-346` tells users the same.

**L13–L17** — `type Schedule struct` with `Cron` (key `cron`) and `Timezone` (key `timezone`), then a blank line. Neither field has `omitempty`: when a schedule exists, both keys are always written, so the API and the saved `definition_json` always show the full pair. Optionality lives one level up, in `Definition.Schedule *Schedule` with `schedule,omitempty` (`workflow.go:25`). The TypeScript mirror is `WorkflowSchedule` at `web/src/api.ts:14`. `Schedule` has no custom decoder, so `Load`'s `DisallowUnknownFields` rejects any third key inside the object. Because this struct holds only two strings, `Runner.Start` can copy it with a plain dereference (`runner.go:111`).

**L18** — The doc comment for `Timetable`: it "computes a validated schedule's occurrences in the schedule's time zone". The word "validated" is the contract: a `Timetable` only exists after `NewTimetable` accepted the schedule.

**L19–L23** — `type Timetable struct` with two unexported fields, then a blank line. `schedule cron.Schedule` is the parsed expression, held through the library's interface, which is either a `*cron.SpecSchedule` for five-field expressions and named descriptors or a `cron.ConstantDelaySchedule` for `@every`. `location *time.Location` is the zone the wall-clock fields refer to. Both are lowercase, so only this package can set them, and only `NewTimetable` does. The scheduler stores one per scheduled workflow in its `entry` (`scheduler.go:32-35`). The zero `Timetable{}` is unusable: its `schedule` is a nil interface and `Next` would panic.

**L24–L27** — The comment and `const minimumInterval = time.Minute`, then a blank line. The comment explains why the constant is needed at all: a five-field expression cannot repeat faster than once a minute on its own, but `ParseStandard` also accepts `@every`, and `@every 10s` would repeat every ten seconds. The floor applies to both forms so that `README.md:368`, "Occurrences must be at least one minute apart", is true for every accepted expression. The constant has type `time.Duration` because `time.Minute` does. `schedule_test.go:30` is the `@every 10s` case.

**L28–L29** — The doc comment and `func NewTimetable(s Schedule) (Timetable, error)`. "Each error names the schedule field at fault" is a user-facing promise: every message below begins with `schedule` and names `cron` or `timezone` (the two missing-value messages read `schedule needs a cron expression` and `schedule needs an explicit timezone name ...`), so an author of a bad file knows which key to fix. `s` is passed by value; it is two strings, so copying is trivial. Two callers: `Validate` discards the timetable and keeps only the error (`workflow.go:71`), and `schedule.New` keeps the timetable (`scheduler.go:62`).

**L30–L32** — Reject an empty or whitespace-only `cron`. This is the first check because the parser's own message for an empty string would be less specific. It also decides what `"schedule": {}` means: a configuration mistake, not "no schedule". `schedule_test.go:114-122` asserts that `Load` fails on an empty schedule object, and the test comment states the reasoning. A file that wants no schedule omits the key, which leaves the pointer nil (`workflow.go:25`).

**L33–L35** — Reject a `cron` string containing `TZ=`. The library accepts a leading `TZ=Zone ` or `CRON_TZ=Zone ` and would use that zone instead of the `timezone` field. Two zones in one schedule can disagree silently, and the file would no longer "mean the same thing on every host" (`README.md:371-372`). `strings.Contains` rather than `strings.HasPrefix("TZ=")` is what makes the check cover `CRON_TZ=` as well; `schedule_test.go:26` uses `CRON_TZ=UTC` on purpose. The message tells the author where the zone belongs.

**L36–L39** — `cron.ParseStandard(s.Cron)` parses the five fields or a descriptor. On failure the error is wrapped with `%w` and the expression is quoted with `%q`, so `schedule cron "every five minutes" is invalid: ...` carries both the offending text and the parser's explanation. `schedule_test.go:24-25` cover words instead of fields and a six-field expression; the standard parser has no seconds field, so six fields is an error. `README.md:366-367` documents the accepted forms.

**L40–L42** — Require an explicit `timezone` and reject `"Local"`. The two cases are different mistakes with the same fix. An empty name is not host-dependent (`LoadLocation("")` returns UTC) but it is implicit, and the author may have assumed local time; `"Local"` is the host's zone and would make the same file fire at different instants on different machines. Both break the "same on every host" rule at `README.md:369-372`. The message names two valid examples. `schedule_test.go:27-28` are the two cases.

**L43–L46** — `time.LoadLocation(s.Timezone)` resolves the IANA name. The error message deliberately drops the library's error and says only that the zone is unknown, naming the field and the value. `LoadLocation` reads the host's zone database or, failing that, the copy embedded by `main.go:17`; `README.md:389-390` explains both sources. `schedule_test.go:29` uses `Mars/Olympus_Mons`.

**L47** — `timetable := Timetable{schedule: parsed, location: location}` builds the value. From here on the function uses the timetable's own `Next`, so the next two checks exercise the same code path the scheduler will use.

**L48–L51** — `first := timetable.Next(time.Now())` asks for the first occurrence after right now. The library searches up to five years ahead and returns the zero time if the fields never line up, which L50 reports as "no occurrence in the next five years". `schedule_test.go:31` uses `0 0 30 2 *`, February 30th. This is the only check in the package that reads the real clock, so its answer can in principle change with the date; see "Where `NewTimetable` runs" and the failure paths below. Without it, the scheduler would accept the workflow and immediately log "schedule has no further occurrences" (`scheduler.go:144`), a worse place to find out.

**L52–L54** — `if second := timetable.Next(first); second.Sub(first) < minimumInterval` computes the occurrence after the first and measures the gap. An `if` with a short statement keeps `second` scoped to the check. For a five-field expression the gap is always at least a minute, so this only ever fires for `@every` with a sub-minute duration, which is the case the comment at L24-25 describes. One gap is enough to decide: `@every` gaps are constant, and five-field gaps cannot go below the floor. The message quotes the expression.

**L55–L57** — `return timetable, nil`, the closing brace, and a blank line. Only a fully checked timetable leaves this function.

**L58–L59** — The doc comment for `Next`: "the first occurrence after the given instant, expressed in the schedule's time zone", and "The zero time means no occurrence within five years." Both halves are relied on by the scheduler: `loop` runs `for !occurrence.IsZero()` (`scheduler.go:115`) and `NextRun` reports `false` for a zero time (`scheduler.go:109`).

**L60** — `func (t Timetable) Next(after time.Time) time.Time`. A value receiver, because the method reads two fields and changes nothing. That also means every scheduler goroutine can call it on its own copy of the entry without coordination.

**L61** — `return t.schedule.Next(after.In(t.location))`. The conversion is the whole point of the method. The library evaluates the wall-clock fields of an expression in the location of the time it is given, and it returns the result in that same location. Passing `after` converted into the schedule's zone therefore makes `0 9 * * *` mean 09:00 in that zone, not 09:00 in whatever zone the caller's clock happened to carry, and it makes the returned time print with that zone's offset. `schedule_test.go:46-60` checks both effects: a 12:00 UTC input yields 14:00 UTC for a New York 09:00 schedule, and the result's `Location()` is `America/New_York`. The two daylight-saving tests at `schedule_test.go:64-94` show the library's wall-clock behavior that `README.md:380-383` documents: a skipped 02:30 waits a day, a repeated 01:30 runs twice. Callers: L48 and L52 above, `scheduler.go:87` for the first occurrence after `Start`, and `scheduler.go:139` for each following one. The scheduler forwards the value to `NextRun`, which the API encodes as `nextRunAt` with the zone offset (`api.go:42-44`, `README.md:388-389`).

**L62** — The closing brace.

## State, concurrency, and cancellation

These two files create no goroutines, hold no mutex, and take no `context.Context`. What they define is which data is immutable, who may call them from where, and what each failure means for the process.

**Ownership of decoded steps.** `Step.UnmarshalJSON` writes to exactly one place, the `*Step` it was given, and only on success (L52). During `Load` that pointer is an element of a `[]Step` being built inside a local `Definition` in the main goroutine (`workflow.go:172-175`); no other goroutine exists yet. After `Load` returns, the definitions slice is shared read-only by the API closures and the scheduler (chapter 4), and `Runner.Start` clones the steps before keeping them (`runner.go:109`). No code decodes a `Step` later: the store writes the definition as JSON (`runs.go:18`) and never decodes it back, which is what `docs/roadmap.md:105` asks for when it says to return snapshots "as stored bytes without strict decoding".

**Ownership of timetables.** A `Timetable` is immutable once built. Its two fields are set in `NewTimetable` and never written again; the cron library's schedule values are read-only after parsing, and a `*time.Location` is never modified after `LoadLocation` builds it. The scheduler stores one timetable per entry (`scheduler.go:66`), and each entry is copied by value into its own goroutine at `scheduler.go:92`. `Start` calls `Next` under `s.mu` (`scheduler.go:79-87`) and each `loop` goroutine calls it without the lock (`scheduler.go:139`); both are safe because `Next` reads only immutable data and its argument. The one lock in the scheduler protects the `next` map and the `started` flag, not the timetable.

**Where `NewTimetable` runs, and how often.** Three places, at different times. At startup inside `Load` for every scheduled file (`workflow.go:71`), then again inside `schedule.New` (`scheduler.go:62`), both in the main goroutine before the HTTP server exists. Then on every run start, because `Runner.Start` calls `Validate` first (`runner.go:106`): each manual start runs in an HTTP handler goroutine, and each scheduled start runs in that workflow's scheduler goroutine. Each call reparses the expression, reloads the location, and reads `time.Now()`. That is cheap and safe, since the function has no shared state, but it means validation is not free of the clock. `Validate` runs before the runner takes `r.mu` (`runner.go:114`), so the parsing stays outside the critical section, in line with `AGENTS.md:78-79`: "Keep admission, capacity, queue promotion, and same-workflow overlap checks under the runner's mutex." Validation is none of those.

**Contexts and cancellation.** Neither file uses a context. Decoding is CPU-only and finishes in microseconds. `time.LoadLocation` may read a file from the zone database, but it has no cancellation hook in the standard library. The signal context created at `main.go:38` is not consulted until later in `runServer`, so a Ctrl+C during startup takes effect after `Load` returns. The timestamps `Next` produces become the deadlines the scheduler waits on with `clock.After` (`scheduler.go:119`), and that wait is what the scheduler's own context cancels on shutdown (`scheduler.go:117`). The timetable itself never waits.

**Failure paths.** Every error from `Step.UnmarshalJSON` surfaces through the decoder in `Load` as `<path>: <message>` (`workflow.go:176`), is wrapped by `main.go:59-61`, logged as `patchbay failed`, and ends the process with status 1 (`main.go:40-43`) before the database is opened. The specific causes, in the order the code can hit them: a non-object step (L65), a duplicate or case-variant key (L80), an unknown outer key or trailing data (L24), an unknown or mistyped config key for the declared type (L36, L46), or an unsupported type (L50). Every error from `NewTimetable` surfaces the same way through `Validate` (`workflow.go:72`). If `schedule.New` fails, which can only happen for the clock-dependent check at L48-51 between `Load` and `New`, `main.go:116-119` reports `create scheduler` and exits. At run time, a `Validate` failure inside `Runner.Start` returns to the caller: the API answers 400 with the message (`api.go:66-67`, `api.go:80`), and the scheduler logs `scheduled run skipped` and moves to the next occurrence (`scheduler.go:131-139`). For file-loaded definitions those run-time failures are theoretical, since the same checks already passed at startup.

**Rules from "Execution and persistence rules" that this code implements.**

- `AGENTS.md:100-102`: "Scheduled starts call `Runner.Start` exactly as the API does. The scheduler never executes steps, never retries a rejected occurrence, and never replays occurrences missed during downtime." `Timetable` is what makes this division possible: it answers "when" and nothing else. It never starts a run, never holds a goroutine, and never looks backwards. The scheduler computes the first occurrence from the current time at startup (`scheduler.go:85-87`) and, after each firing, from the later of now and the occurrence that just fired (`scheduler.go:135-139`), so occurrences that passed are skipped, as `README.md:377-378` states.
- `AGENTS.md:103-104`: "Preserve atomic run/step snapshots and existing data." The snapshot written by `store.CreateRun` is the definition in its file shape, including `schedule` and every step's flat `config`. Because `UnmarshalJSON` accepts exactly the shape the default encoder writes (L11-12), old snapshots and new files share one format, and neither TCP steps nor schedules required rewriting saved JSON. TCP did bring a schema migration, but only a marker: version 3 bumps `user_version` so older HTTP-only builds refuse a database whose JSON may now hold TCP checks (`internal/store/schema.go:51-54`, `AGENTS.md:127-129`); schedules needed no migration at all.
- `AGENTS.md:82`: "Return copied snapshots." `Schedule` was designed as two plain strings so that the runner's copy at `runner.go:110-113` is a complete copy. `AGENTS.md:130` warns to "revisit snapshot copying if adding nested pointers"; `Schedule` has none.
- From the extending section, `AGENTS.md:124-125`: "`CheckConfig` and `CheckResult` hold HTTP/TCP fields as plain values; step decoding selects the allowed config fields by type." That sentence is a description of L28-51. `docs/roadmap.md:101` plans to replace the shared struct with per-type structs "inside the SSH increment"; until then, this switch is the type boundary.

## Check yourself

1. A step file contains `"config": {"unexpected": true}, "config": {"host": "nas", "port": 22, "timeoutMs": 1000}`. Which line rejects it, and what would happen if `rejectDuplicateStepFields` were removed?

<details><summary>Answer</summary>
L79-80 rejects it: the second <code>config</code> key is already in <code>seen</code>, so the error is <code>duplicate step field "config"</code>. Without the guard, <code>decodeStrict</code> at L24 would decode the outer object with <code>encoding/json</code>'s last-value-wins rule, so <code>wire.Config</code> would hold only the second, clean object. The first object, with its unknown field, would never be decoded, and the step would load. The comment at L56-57 names this exact risk, and <code>tcp_test.go:131</code> is this input.
</details>

2. Why does the duplicate check lowercase keys, and why is that not needed inside `config` or at the `Definition` level?

<details><summary>Answer</summary>
<code>encoding/json</code> matches keys case-insensitively, so <code>"Config"</code> fills the same field as <code>"config"</code> (L77-78). Without <code>ToLower</code>, the pair would pass the <code>seen</code> test and then collapse into one field with the last value winning, hiding the first. Inside <code>config</code> and at the <code>Definition</code> level there is no <code>RawMessage</code>: every value is decoded strictly, so a duplicate can only change which value wins, never hide an unknown field. The guard lives only where deferred decoding lives.
</details>

3. `Step.UnmarshalJSON` fails on the second step of a three-step file. What is the state of the first step's `Step` value, of the second's, and of the process?

<details><summary>Answer</summary>
The first step decoded fully and its value is complete, because its own call reached L52. The second step's value is still the zero <code>Step</code>, because the method fills a local <code>step</code> (L27) and only assigns <code>*s</code> after every check. Neither matters: the decoder in <code>Load</code> returns the error, <code>Load</code> returns <code>&lt;path&gt;: step "..." ...</code> (<code>workflow.go:176</code>), and <code>main.go:40-43</code> logs <code>patchbay failed</code> and exits with status 1 before the database is opened. The third step is never decoded.
</details>

4. `NewTimetable` is called three times for one scheduled workflow during a normal day. Name the three callers, the goroutine each runs in, and which one keeps the result.

<details><summary>Answer</summary>
<code>Validate</code> at <code>workflow.go:71</code>, in the main goroutine during <code>Load</code>, discards the timetable. <code>schedule.New</code> at <code>scheduler.go:62</code>, also in the main goroutine at startup, keeps it in an <code>entry</code>. <code>Validate</code> again at <code>workflow.go:71</code>, reached from <code>Runner.Start</code> (<code>runner.go:106</code>), for every run start: in an HTTP handler goroutine for a manual start, or in that workflow's scheduler goroutine for a scheduled start. Only the scheduler's copy is used to compute occurrences.
</details>

5. The schedule is `"cron": "0 9 * * *", "timezone": "America/New_York"` and the scheduler calls `Next` with a UTC time. Which line makes 09:00 mean New York time, and what would `Next` return if that line passed `after` unchanged?

<details><summary>Answer</summary>
L61, through <code>after.In(t.location)</code>. The cron library evaluates the hour and minute fields in the location of the time it receives and returns the result in that location. With the conversion, 09:00 is New York time and the result carries the New York zone (<code>schedule_test.go:52-59</code>). Without it, the library would see a UTC time, match 09:00 UTC, and return a UTC instant five or four hours too early depending on daylight saving; the <code>timezone</code> field would be validated at L43 and then ignored.
</details>

6. Why is the minimum-interval check (L52-54) computed from `first` rather than from `time.Now()`, and why is checking one gap enough?

<details><summary>Answer</summary>
The gap between <code>time.Now()</code> and the first occurrence is arbitrary; it could be a few seconds for a perfectly valid <code>*/5 * * * *</code> if the clock sits just before a five-minute boundary. The gap between two consecutive occurrences is the schedule's real period. One gap suffices because the parser only produces two kinds of schedule: five-field expressions, whose consecutive matches are always at least one minute apart since there is no seconds field, and <code>@every</code> schedules, whose gap is constant. The comment at L24-25 explains that the floor exists for the second kind.
</details>
