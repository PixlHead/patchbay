## Role in the system

These four files test `internal/httpapi`, the package from Chapter 11 that turns HTTP requests into runner calls and SQLite reads. The production code is small: `New` (`internal/httpapi/api.go:32-140`) builds a `http.ServeMux` with seven handler patterns (five API routes, a JSON 404 for everything else under `/api/`, and the file server), `preferUnsavedRun` (`api.go:144-149`) overlays a retained in-memory result on a stale saved row, and `HostGuard.Wrap` (`internal/httpapi/host_guard.go:39-50`) rejects requests for hostnames that are not on the allowlist. In production `cmd/server/main.go:123` wires them together as `hostGuard.Wrap(httpapi.New(definitions, runner, scheduler, db, webDir))`. The tests build the same objects by hand, but swap the real pieces for controlled ones: the executor is a closure instead of `httpcheck`, the database is a temporary file from `t.TempDir()`, and the schedule source is a map with one method.

The path from a browser click to a saved run passes straight through this package. `web/src/pages/WorkflowsPage.tsx:54-59` sends `POST /api/workflows/{id}/runs` with `Content-Type: application/json`. The guard checks `r.Host` (`host_guard.go:41-42`). The route at `api.go:50-88` checks the content type and body, calls `runner.Start` (`api.go:65`), which saves the new run through `store.CreateRun` before admitting it (`internal/engine/runner.go:136-145`), and answers `202` with a `Location` header (`api.go:83-84`). The frontend then polls `GET /api/runs` every second (`WorkflowsPage.tsx:47-51`), which reads SQLite (`api.go:92`) and overlays any retained unsaved final result (`api.go:98-100`). Every status code, header, and body shape in that path has a test here.

The files split by subject. `api_test.go` holds the shared helpers `testDefinitions` and `openTestDB` plus the start route: request-independent run lifetime, save failure, error codes, and admission under concurrency. `history_test.go` covers the two read routes: ordering, reopen, progress-save failure reasons, read failures, final-save recovery, and the overlay. `host_guard_test.go` covers the allowlist, its configuration parser, and that the guard runs before any route. `schedule_test.go` covers the `nextRunAt` field on the workflow list. None of them opens a network connection to a real service, which is what `AGENTS.md:134-137` requires: "fake executors, temporary databases, local test servers, and controlled clocks/channels".

## Concepts you need

- **`net/http/httptest`: `NewRequest`, `NewRecorder`, `NewServer`.** `httptest.NewRequest` builds an incoming server request in memory with `Host` set to `example.com` and `ContentLength` taken from a `*strings.Reader` body. `httptest.NewRecorder` is a fake `http.ResponseWriter` that keeps the status code, headers, and body for assertions. `httptest.NewServer` starts a real HTTP server on a random loopback port and gives you a matching client, which is the only way to test what a real request context does. [pkg.go.dev/net/http/httptest](https://pkg.go.dev/net/http/httptest)
- **`http.Handler` and `ServeHTTP`.** Anything with a `ServeHTTP(w, r)` method is a handler. `New` returns one, `guard.Wrap` takes one and returns another, and `http.HandlerFunc` turns a plain function into one. Tests call `handler.ServeHTTP(recorder, request)` directly, so no port is opened. [pkg.go.dev/net/http#Handler](https://pkg.go.dev/net/http#Handler)
- **`http.ServeMux` method patterns.** Since Go 1.22, a pattern such as `"GET /api/runs/{id}"` matches a method and a path, and `r.PathValue("id")` reads the wildcard. A trailing-slash pattern such as `"/api/"` matches every path under it, which gives the API a JSON 404 for unknown routes. [pkg.go.dev/net/http#ServeMux](https://pkg.go.dev/net/http#ServeMux)
- **Closures as fakes.** A closure is a function literal that reads and writes variables of the enclosing function. Every fake executor and fake save callback in this chapter is one: it counts calls, records snapshots, blocks on a channel, or returns an error on the first call. The runner only sees a function of the right type (`runner.go:51-60`). [Tour: function closures](https://go.dev/tour/moretypes/25)
- **`context` and cancellation.** A `context.Context` carries a cancel signal. `ctx.Done()` is a channel closed on cancel and `ctx.Err()` says why. `context.WithCancel` returns the child and a `cancel` function. The first test cancels a request context to prove the run does not care. [pkg.go.dev/context](https://pkg.go.dev/context)
- **Channels, `close`, and `select`.** A channel passes a signal between goroutines. Receiving from a closed channel returns at once, so `close(release)` wakes every waiting executor. `select` waits on several channel operations and takes the first that is ready; paired with `time.After`, a hang becomes a failed test rather than a frozen one. [Tour: channels](https://go.dev/tour/concurrency/2), [Tour: select](https://go.dev/tour/concurrency/5)
- **Table-driven tests and `t.Run`.** A slice of anonymous structs lists cases; a loop runs the same body per case. `t.Run(name, f)` gives each case its own pass/fail line and its own `t`, so `t.Cleanup` inside a subtest runs when that subtest ends. [Go wiki: TableDrivenTests](https://go.dev/wiki/TableDrivenTests), [pkg.go.dev/testing#T.Run](https://pkg.go.dev/testing#T.Run)
- **`t.Helper`, `t.Cleanup`, `t.TempDir`, `t.Fatal`.** `t.Helper` makes a failure inside a helper point at the caller's line. `t.Cleanup` registers a function to run when the test ends, even after `t.Fatal`. `t.TempDir` gives a fresh directory that is removed afterwards. `t.Fatal` stops the current test function immediately. [pkg.go.dev/testing](https://pkg.go.dev/testing)
- **`reflect.DeepEqual`.** Compares two values field by field, following pointers and slices. The history tests use it to say "the JSON the API returned decodes to exactly the run we saved", including the nested `*CheckResult`. [pkg.go.dev/reflect#DeepEqual](https://pkg.go.dev/reflect#DeepEqual)
- **`encoding/json`, struct tags, `omitempty`, `omitzero`, and embedded structs.** A `json:"name,omitempty"` tag names the JSON key and drops the field when it is nil or empty; `omitzero` (Go 1.24) drops a zero `time.Time`. An embedded struct's fields are promoted into the outer JSON object, which is how `workflowSummary` (`api.go:25-28`) adds `nextRunAt` beside the definition's own fields. Decoding into a smaller struct ignores keys it does not declare. [pkg.go.dev/encoding/json#Marshal](https://pkg.go.dev/encoding/json#Marshal)
- **SQLite triggers and `RAISE(ABORT)`.** A `CREATE TRIGGER ... BEFORE UPDATE OF column ON table WHEN condition BEGIN SELECT RAISE(ABORT, 'message'); END` statement makes a matching `UPDATE` fail with that message and roll back its statement. The history tests use triggers to make one specific save fail inside a real database, with no mock of `*sql.DB`. [sqlite.org: CREATE TRIGGER](https://www.sqlite.org/lang_createtrigger.html)
- **`database/sql`: `ExecContext`, `sql.ErrNoRows`, idempotent `Close`.** `db.ExecContext` runs a statement without rows. `Scan` on a missing row returns `sql.ErrNoRows`, which the store wraps with `%w` so the API can map it to 404. `DB.Close` may be called twice; the second call returns at once. [pkg.go.dev/database/sql](https://pkg.go.dev/database/sql)
- **Error wrapping: `%w`, `errors.Is`, `errors.Join`.** `fmt.Errorf("%w: %w", a, b)` builds one error whose chain contains both. `errors.Is` walks that chain. `errors.Join(a, b)` makes a single error from several, and `errors.Join(nil, nil)` is `nil`. The recovery test uses `Join` so a cleanup failure cannot hide the save failure. [pkg.go.dev/errors](https://pkg.go.dev/errors)
- **`log` and `log/slog` defaults.** `slog.Error` with no handler configured writes through the standard `log` package's default logger, in the text form `ERROR message key=value`. `log.SetOutput` therefore captures production `slog` lines in a test. The output is process-wide, so such a test must not run in parallel. [pkg.go.dev/log/slog](https://pkg.go.dev/log/slog), [pkg.go.dev/log#SetOutput](https://pkg.go.dev/log#SetOutput)
- **`time.Time` precision, `UTC()`, `Truncate`, `Equal`.** SQLite stores Unix milliseconds (`internal/store/schema.go:15`), so a time that round-trips through the store loses nanoseconds. `time.Now()` carries a monotonic reading that `UTC()` and `Truncate` strip. `Equal` compares instants regardless of location; `DeepEqual` also compares the location pointer, so both sides must be built the same way. [pkg.go.dev/time#hdr-Monotonic_Clocks](https://pkg.go.dev/time#hdr-Monotonic_Clocks)
- **Interfaces are satisfied implicitly; methods on named map types.** `NextRunSource` (`api.go:21-23`) needs one method. `fakeNextRuns` is a named map type with that method, so a map literal is a valid source without any `implements` keyword. The production `*schedule.Scheduler` satisfies the same interface (`internal/schedule/scheduler.go:105`). [Tour: interfaces are implemented implicitly](https://go.dev/tour/methods/10), [Spec: method declarations](https://go.dev/ref/spec#Method_declarations)
- **Map iteration order is random.** `for path, message := range map[...]` visits entries in an unspecified order. Two tests loop over a map on purpose: both routes must pass in either order. [Spec: for statements](https://go.dev/ref/spec#For_statements)
- **`net.SplitHostPort` and `net/netip`.** `SplitHostPort` separates `host:port`, stripping IPv6 brackets, and fails when there is no port or too many colons. `netip.ParseAddr` parses an IP, `Is6` is true for IPv6 including IPv4-mapped forms, `Unmap` turns `::ffff:127.0.0.1` into `127.0.0.1`, `Zone` reports a `%iface` suffix, and `IsUnspecified` is true for `0.0.0.0` and `::`. The host guard cases walk every one of these branches. [pkg.go.dev/net#SplitHostPort](https://pkg.go.dev/net#SplitHostPort), [pkg.go.dev/net/netip](https://pkg.go.dev/net/netip)
- **The Go memory model and joining goroutines.** Reading a variable another goroutine wrote is only safe when something orders the write before the read. Several tests call `runner.Close()` before reading counters a callback incremented, because `Close` waits on the runner's `sync.WaitGroup` (`runner.go:190`). `make test` runs with `-race` (`Makefile:16`) and would report a missing join. [The Go memory model](https://go.dev/ref/mem), [Race detector](https://go.dev/doc/articles/race_detector)
- **`for range N`.** Since Go 1.22, `for range 2` repeats a body twice without a loop variable. [Spec: for statements with range clause](https://go.dev/ref/spec#For_range)
- **`defer`.** A deferred call runs when the surrounding function returns, including through `t.Fatal`. `defer runner.Close()` next to an explicit `runner.Close()` later is fine because `Close` is safe to call twice (`runner.go:176-191`). [Spec: defer statements](https://go.dev/ref/spec#Defer_statements)

## Check yourself

1. `TestRunLifecycleSurvivesRequestEnd` uses `httptest.NewServer`; every other test in the package uses `httptest.NewRecorder`. Why does this one need a real server, and what would the `cancel()` at L68 prove with a recorder?

<details><summary>Answer</summary>A recorder calls `ServeHTTP` on the test goroutine with whatever request you built; there is no client, no socket, and `r.Context()` is just the context you attached. Only a real server gives the handler a request whose lifetime is controlled by a client on the other end of a connection, which is the situation `AGENTS.md:84-85` talks about. With a recorder, `cancel()` would cancel a context the handler had already finished with, proving nothing about the server. The deeper proof is in the production code either way: `api.go:65` passes no context to `runner.Start`, and `runner.go:139` derives the save context from `r.ctx`, so the run cannot be tied to the request. The test observes that at L72–L75, where the run is still `running` after the cancel.</details>

2. In `TestProgressSaveFailureReasonSurvivesDatabaseReopen`, the trigger is never dropped, yet the final save succeeds at L121–L128. Which two lines of production code make that true, and what would happen if `UpdateRun` wrote the step rows before the run row?

<details><summary>Answer</summary>The trigger's `WHEN` clause (L84–L85) requires the parent run's row to still read `running`. `store.UpdateRun` updates the `runs` row first (`internal/store/runs.go:75-77`) and the `run_steps` rows afterwards (`runs.go:96-119`) inside one transaction, and `finishRun` sets the terminal status before the save (`internal/engine/runner.go:302`). So when the step update runs, the subquery already sees `failed` and the trigger stays silent. If the order were reversed, the step update would run while the row still said `running`, the trigger would abort every final attempt, and the run would end up retained with `finalSaveFailed` instead of saved with its reason. The test would then fail at L123–L124 with "final save did not recover from the progress failure".</details>

3. `TestHistoryShowsUnsavedFinalResultWithoutHidingReadFailures` truncates `older` to a millisecond at L348 but never truncates anything about the live run. Why is `reflect.DeepEqual` at L418 still exact for both?

<details><summary>Answer</summary>`older` is written to SQLite, whose timestamp columns hold Unix milliseconds (`internal/store/schema.go:15`, `runs.go:127-132`), and read back with `time.UnixMilli(...).UTC()` (`run_reads.go:83-88`). A value with nanoseconds would come back rounded, so the fixture pre-rounds it. The live run is different: `preferUnsavedRun` (`api.go:144-149`) returns the runner's own snapshot, which never passes through SQLite. `writeJSON` encodes its nanosecond times with `RFC3339Nano`, the test decodes them back, and both sides have a `nil` location because `time.Now().UTC()` and parsing a `Z` suffix produce the same representation. The stale SQLite row for the live run is the one thing that would not match, and the test's point is that it is replaced.</details>

4. In `TestHostGuard`, every request sets a `Host` header, `X-Forwarded-Host`, and `Forwarded` to `localhost:8080`, an allowed value. What does a rejected row prove because of those headers, and which production line is being tested?

<details><summary>Answer</summary>A rejected row proves that none of those headers can rescue a request whose `r.Host` is not allowed. The guard reads only `r.Host` (`host_guard.go:41`); the comment at `host_guard.go:38` and `README.md:130` say forwarded headers must not override the requested hostname. If someone "improved" the guard to honor `X-Forwarded-Host`, every rejected row would suddenly get 204 and `called == true`, and L83–L84 would fail. The header named `Host` in `r.Header` is a decoy too: Go's server moves the real `Host` into `r.Host` and a value set in the map is not consulted.</details>

5. `TestRunSaveFailureReturnsServerError` checks `runner.List()` is empty and `executed` is false. Which lines in `runner.Start` make both true, and what capacity bug would this catch?

<details><summary>Answer</summary>`Start` calls `recordNewRun` at `runner.go:140` while holding the mutex and returns at `runner.go:143` on error. The registration lines come after: `r.order`/`r.runs` at `runner.go:146-147`, `busyWorkflows` at `runner.go:148`, and `launchLocked` at `runner.go:154`, which is the only place `activeRuns` is incremented and a goroutine started. Because none of them ran, `List` sees nothing and the executor never got a call. The bug this catches is a save that fails after registration: the workflow would stay marked busy forever (every later start would get 409), or a slot would be consumed with no goroutine to release it, which is exactly what `AGENTS.md:83-85` forbids.</details>

6. `TestConcurrentAdmissionErrorsAndShutdownPersistence` reads the database twice, at L248 before `Close` and at L265 after. What does each read prove that the other cannot?

<details><summary>Answer</summary>The first read proves that admission itself persisted the queued run `c` with status `queued`, a `NULL` start time, and a creation time, before any goroutine existed for it (`runner.go:136-152`; `README.md:166-167`). Reading after `Close` would not show that, because by then `c` has been rewritten as `canceled`. The second read proves two shutdown facts: that `Close` did not return until the final saves of `a`, `b`, and `c` were committed (otherwise the rows would still say `running` or `queued`), and that the three rejected starts never produced rows at all, since the count is exactly three. Neither read alone covers both the admission-time write and the shutdown-time write.</details>
