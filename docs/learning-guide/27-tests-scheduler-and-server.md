## Role in the system

These five files test the two places where the outside world enters the program through something other than an HTTP request: time, and the operating system. `internal/schedule/scheduler_test.go` tests the cron loop from chapter 12 (`internal/schedule/scheduler.go`), which decides *when* a run is asked for. The four files under `cmd/server/` test the composition root from chapter 3 (`cmd/server/main.go` and `cmd/server/database_lock.go`), which decides *in what order* flags are checked, workflow files are read, the database is locked, opened, write-checked and cleaned up, and the HTTP listener is started, and in what order all of that is released again. Both components are thin: the scheduler is 145 lines and `runServer` is about a hundred. What makes them worth sixteen tests is that every mistake in them is an ordering mistake, and ordering mistakes do not show up when you click Run in a browser. They show up at 03:00 when the host wakes from sleep, or when two containers are pointed at one volume.

Data comes in as hand-built `workflow.Definition` values, a fake clock the test advances by hand, temporary SQLite files, a local `httptest` server and a local TCP listener, and in one case a child copy of the test binary. Data goes out as returned errors whose *type* and *text* say which startup stage failed, as rows read back from SQLite, as JSON decoded from the API handler, and as the arguments the fake start function receives. No test here reaches a real homelab service, binds a fixed port, or waits on a real timer longer than a `time.After` safety net. That is the `AGENTS.md:134-137` rule: "Use fake executors, temporary databases, local test servers, and controlled clocks/channels; routine tests must not depend on live homelab services." The roadmap says the same for scheduling in particular: "fake clocks for scheduling and backoff, local HTTP/SSH fixtures for integration tests" (`docs/roadmap.md:235`).

On the path from a browser click to a saved run, the scheduler sits beside the click: it is the second caller of `Runner.Start` (`internal/schedule/scheduler.go:125`, next to `internal/httpapi/api.go:65`), and the scheduler tests prove it calls `Start` at the right instants and never more than once per occurrence. `runServer` sits at both ends of that path: it builds the runner and the API handler the click reaches (`cmd/server/main.go:107-123`), and it releases them in reverse order on exit (`main.go:70-84`, `:115`, `:121`, `:127`). The server tests prove the build order by making the *last* stage, the listener, fail on purpose with an address that has no port, so that reaching that failure means every earlier stage ran. `checks_test.go` is the one test in the repository that drives the real executors, the real dispatcher, the real store and the real API handler together, then reopens the database as a restart would and reads the run back.

## Concepts you need

- **Same-package test files, `testing.T`, and its helpers.** A `_test.go` file that says `package schedule` or `package main` is compiled into the test binary together with the package, so it can call unexported names such as `runServer`, `lockDatabase`, and `errDatabaseInUse`. `t.Fatal` stops the test at once (only from the test's own goroutine), `t.Error` records a failure and continues, `t.Helper()` makes a failure inside a helper point at the caller's line, `t.Skip` marks a test skipped with a reason, `t.TempDir()` gives a directory that is removed when the test ends, and `t.Cleanup(f)` registers `f` to run after the test and its subtests, last registered first. [testing](https://pkg.go.dev/testing)
- **Table-driven tests and `t.Run` subtests.** A slice of anonymous structs plus `t.Run(name, func(t *testing.T) {...})` gives each case a name you can select with `go test -run 'Test/case_name'` (spaces become underscores). The `t` inside the closure belongs to the subtest and shadows the outer one. [testing: Subtests](https://pkg.go.dev/testing#hdr-Subtests_and_Sub_benchmarks)
- **Function-typed dependencies and method values.** The scheduler takes a `StartRun` function and a `Clock` struct of two functions (`scheduler.go:19`, `:23-26`) instead of interfaces. `runner.Start` without parentheses is a *method value*: a function bound to that runner, which is what production passes (`main.go:116`) and what the busy test passes (`scheduler_test.go:163`). A fake is then just a closure or a bound method. [Spec: Method values](https://go.dev/ref/spec#Method_values), [A Tour of Go: Function closures](https://go.dev/tour/moretypes/25)
- **A fake clock made of channels.** `time.After(d)` returns a channel that receives once after `d`. The fake `After` returns a channel the *test* holds the sending end of, and pushes a record of the request onto a second channel so the test can see what the scheduler asked for. The test decides when the tick arrives and what time it carries. A channel that carries channels is an ordinary pattern in Go. [A Tour of Go: Channels](https://go.dev/tour/concurrency/2), [time.After](https://pkg.go.dev/time#After)
- **`select` with timeouts and a non-blocking `default`.** `select` waits on several channel operations and runs whichever is ready first. Pairing a receive with `case <-time.After(2 * time.Second)` turns "wait for the scheduler" into "wait at most two seconds, then fail". A `select` with `default` never blocks: it reports whether something is ready *right now*, which is how a test asserts that nothing has happened yet. [A Tour of Go: Select](https://go.dev/tour/concurrency/5), [Default selection](https://go.dev/tour/concurrency/6)
- **`sync.Mutex` for one shared field.** The fake clock's `now` is written by the test goroutine and read by the scheduler's loop goroutines, so every access is wrapped in `Lock`/`Unlock`; `defer c.mu.Unlock()` releases it on every return path. Without it `go test -race` reports a data race. [sync.Mutex](https://pkg.go.dev/sync#Mutex)
- **Closing a channel as a broadcast.** `close(release)` makes every receive on `release` return at once, forever. The busy test uses it to let a blocked fake executor finish. Closing twice panics, so it is done once. [Spec: Close](https://go.dev/ref/spec#Close)
- **Goroutines, joining, and the race detector's happens-before.** `go func() {...}()` starts a goroutine. A test joins it by receiving from a channel the goroutine closes, or by calling a production `Close` that ends with `sync.WaitGroup.Wait` (`scheduler.go:100`, `internal/engine/runner.go:190`). Under `go test -race`, a value written by a goroutine may be read only after such a join; `checks_test.go:100` exists for exactly that reason. [Race detector](https://go.dev/doc/articles/race_detector), [The Go Memory Model](https://go.dev/ref/mem)
- **`context.WithTimeout` and `ctx.Done()` in a fake.** `context.WithTimeout(context.Background(), 5*time.Second)` gives a context that is canceled after five seconds; `defer cancel()` releases its timer. A fake executor that waits on `<-ctx.Done()` behaves like a real network call that honors cancellation, so a runner shutdown can always finish. `runServer` treats its context's `Done` as the shutdown signal (`main.go:137`), so a test's deadline is also its escape hatch. [context](https://pkg.go.dev/context)
- **`errors.Is`, `errors.As`, and `%w` chains.** `fmt.Errorf("lock database %q: %w", ...)` keeps the inner error reachable. `errors.Is(err, errDatabaseInUse)` finds a sentinel anywhere in the chain; `errors.As(err, &addressError)` finds the first error of a given type and stores it. `net.Listen` with a port-less address returns a `*net.OpError` whose `Unwrap` yields a `*net.AddrError`, so `errors.As` sees through two wrappers. [errors](https://pkg.go.dev/errors), [net.AddrError](https://pkg.go.dev/net#AddrError)
- **Build constraints.** `//go:build darwin || linux` on the first line makes the file part of the package only on those systems. `database_lock.go` needs it because `syscall.Flock` does not exist on Windows; `database_lock_test.go` and `database_write_test.go` carry the same line. `main_test.go` also calls `lockDatabase` and carries no constraint, which only works because `main.go:66` calls `lockDatabase` unconditionally, so the whole `cmd/server` package already builds only on those two systems. [Build constraints](https://pkg.go.dev/cmd/go#hdr-Build_constraints)
- **Re-running the test binary as a child process.** `os.Args[0]` is the path of the running test binary. `exec.CommandContext(ctx, os.Args[0], "-test.run=^TestName$")` starts a second copy that runs one test; an environment variable tells that copy it is the child. `StdoutPipe` and `StdinPipe` give the parent a line to read and a way to keep the child blocked; `Process.Kill` then `Wait` ends it. This is the standard way to test what the operating system does when a process dies. [os/exec](https://pkg.go.dev/os/exec), [testing: flags](https://pkg.go.dev/cmd/go#hdr-Testing_flags)
- **`flock` and open file descriptions.** `syscall.Flock(fd, LOCK_EX|LOCK_NB)` takes an exclusive advisory lock on an *open file*, failing at once with `EWOULDBLOCK` if another open file holds it. The lock belongs to the open file description, not the process, so two `OpenFile` calls in one process conflict, and the kernel drops the lock when the file is closed or the process exits. Chapter 3 covers the production side. [flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html), [syscall.Flock](https://pkg.go.dev/syscall#Flock)
- **Symlinks and path normalization.** `os.Symlink(target, link)` creates a link; `os.Lstat` reports the link itself while `os.Stat` follows it; `filepath.EvalSymlinks` returns the real path or an error if a link is dangling; `filepath.Abs` and `filepath.Rel` convert between absolute and relative spellings. The lock tests use all of these to build four spellings of one file. [path/filepath](https://pkg.go.dev/path/filepath), [os.Lstat](https://pkg.go.dev/os#Lstat)
- **Unix permission bits, `os.Chmod`, and `os.Geteuid`.** `0o600` is owner read/write; `0o555` on a directory lets everyone list and enter it but lets nobody create or delete entries; `0o700` restores the owner's write bit. Root (effective uid 0) ignores these bits, so a test that relies on them must `t.Skip` as root. [os.Chmod](https://pkg.go.dev/os#Chmod), [os.Geteuid](https://pkg.go.dev/os#Geteuid)
- **`database/sql` used directly, SQLite triggers, and `PRAGMA journal_mode`.** `sql.Open("sqlite", path)` returns a lazy handle; `QueryRowContext(...).Scan(&x)` reads one row; `ExecContext` runs a statement. A SQLite `TRIGGER ... BEGIN SELECT RAISE(ABORT, 'msg'); END` makes a matching `UPDATE` fail, which is how one test injects a storage failure without a fake. `PRAGMA journal_mode = DELETE` makes every write transaction create and delete a `-journal` file beside the database. [database/sql](https://pkg.go.dev/database/sql), [SQLite CREATE TRIGGER](https://sqlite.org/lang_createtrigger.html), [PRAGMA journal_mode](https://sqlite.org/pragma.html#pragma_journal_mode)
- **`net/http/httptest`.** `httptest.NewServer(handler)` starts a real HTTP server on a random loopback port and gives its `URL`; `httptest.NewRequest(method, "/path", body)` builds a request with `Host` set to `example.com`; `httptest.NewRecorder()` captures status and body when you call `handler.ServeHTTP(recorder, request)` with no network at all. [net/http/httptest](https://pkg.go.dev/net/http/httptest)
- **`net.ListenTCP` on port 0, `AcceptTCP`, and `SetDeadline`.** Port 0 asks the OS for any free port; `Addr().(*net.TCPAddr).Port` reads which one. A connection the kernel has accepted waits in the listener's backlog until `Accept` is called, even if the client already closed it. `SetDeadline` makes a later `Accept` fail instead of blocking forever. [net.ListenTCP](https://pkg.go.dev/net#ListenTCP), [net.TCPListener.SetDeadline](https://pkg.go.dev/net#TCPListener.SetDeadline)
- **`sync/atomic` counters.** `atomic.Int32` has `Add` and `Load` that are safe from several goroutines without a mutex. The `httptest` handler runs on the server's goroutines while the test reads the count on its own. [sync/atomic](https://pkg.go.dev/sync/atomic)
- **`reflect.DeepEqual` and millisecond UTC times.** `DeepEqual` compares structs field by field, slices element by element, and pointers by what they point to. Two `time.Time` values compare equal only if their instant *and* location match, so fixtures use `time.UnixMilli(...).UTC()`, which is exactly how the store writes and reads timestamps (`internal/store/runs.go:33`, `internal/store/run_reads.go:83-88`). [reflect.DeepEqual](https://pkg.go.dev/reflect#DeepEqual), [time.UnixMilli](https://pkg.go.dev/time#UnixMilli)
- **`encoding/json` round trips.** `json.Unmarshal(bytes, &run)` decodes the API's response body into an `engine.Run` using the same struct tags that produced it (`runner.go:24-46`), so a test can assert on typed fields instead of string-matching JSON. [encoding/json](https://pkg.go.dev/encoding/json)

A temporary database path and a ten-second context. `exec.CommandContext(ctx, os.Args[0], "-test.run=^TestDatabaseLockReleasedAfterProcessExit$")` runs the same test binary, restricted by an anchored regex to this one test, and kills it if the context expires. The environment is the parent's plus the variable (L112), which is the only thing that makes the child take the other branch. `StdoutPipe` (L113-116) lets the parent read the handshake. `StdinPipe` (L117-121) is kept open and closed by `defer`, so the child's `io.Copy` blocks until the parent decides. Stderr is captured for the failure message (L122-123). After `Start` (L124-126), a deferred cleanup (L127-132) kills and waits for the child if the test exits before L145 ran, which is detectable because `cmd.ProcessState` stays nil until `Wait` returns. Without it, a failing assertion would leave an orphan holding the lock and the pipe.

The handshake (L133-135). One line is read; it must be exactly `locked\n`. After this line the child holds the lock. Anything else, including a `t.Fatal` message from the child, fails here with the text shown.

Cross-process exclusion (L136-141). The parent's own `lockDatabase` must return `errDatabaseInUse`. This is the production scenario of `README.md:94-97`: two servers, two processes, one `.lock` file, one `flock`.

The child dies (L142-147). `Process.Kill` sends `SIGKILL`: no deferred `Close` runs in the child, nothing cleans up. `Wait` must return an error, because a process killed by a signal does not exit zero; a nil would mean the child had ended on its own.

The lock is free (L148-152). `lockDatabase` must now succeed. The kernel released the `flock` when the child's descriptors were closed at exit. That is the last sentence of the doc comment at `database_lock.go:17`, "The OS also releases the lock on process exit", and `README.md:100-101`, "the OS also releases it if the process crashes". It is also what makes keeping the `.lock` file on disk safe: a leftover file never means a leftover lock.

**L3–L4** — `package main` and a blank line.

**L20–L126** — A blank line and `TestRunServerRejectsUnwritableJournalDirectoryBeforeCleanup` (L21–L126). It proves `AGENTS.md:110-112`: "After opening and recognizing the database, commit a bounded write check before interruption cleanup or HTTP startup. Preserve schema metadata and run history." The store-level behavior of `CheckWritable` has its own tests in chapter 24 (`internal/store/writable_test.go:12`); this test proves where `runServer` places the call and what it leaves behind.

Root skip (L22-24). The effective user id 0 bypasses directory permission bits, so the injected failure would not happen and the test would fail for the wrong reason. `t.Skip` makes that visible in `-v` output instead of red.

Two subtests (L25-30). `empty history` proves the check works with no rows at all, which is the point of the comment at `internal/store/writable.go:13-14`. `unfinished history` proves the *order*: a run that cleanup would have changed must be unchanged afterwards.

Fixture (L31-44). A ten-second context, the workflow directory, `Load`, a temporary directory, and `store.Open` to create and migrate `history.db`.

Pinning the journal mode (L45-53). `PRAGMA journal_mode = DELETE` is run while the directory is still writable, and the returned mode must read `delete`. The comment explains: a committed write must create a rollback journal (`history.db-journal`) beside the database, and creating a file requires write permission on the directory. DELETE is SQLite's default, but setting it explicitly means the fixture keeps failing in the same place if the store ever switches to WAL, where the extra files are created at open time and the failure would move.

Optional unfinished run (L54-70). The same crash-shaped run as `main_test.go:110-118`: status `running`, a running step, no finish times, saved with `store.CreateRun`. `expected` holds it so L106 and L121 can compare.

Closing and preparing the directory (L71-91). The handle is closed (L71-73). The `.lock` file is created in advance (L74-78), with the comment explaining why: `lockDatabase` opens it with `O_CREATE` (`database_lock.go:47`), and in a read-only directory that creation would fail with "permission denied", making `runServer` stop at `lock database` instead of at the stage under test. Precreating it isolates the failure to the write check. L79-83 set both files to `0600` explicitly, so the files themselves stay writable; only the directory will not be. L84-88 register a `t.Cleanup` that restores `0700`. `t.TempDir()` registered its own removal cleanup earlier (L38), and cleanups run last-registered first, so the restore runs before the removal; otherwise the temporary directory could not be deleted and the test would report a cleanup error. L89-91 then set the directory to `0555`: readable and searchable, so existing files can be opened, but no entry can be created or removed.

The `readHistory` helper (L93-105). A closure that opens the store and lists runs, failing with "fixture must allow ..." messages if the read itself breaks. Opening works in a read-only directory because the file exists (`O_EXCL` reports `ErrExist`, allowed at `sqlite.go:39`), `migrate` finds version 3 and the marker and writes nothing (`schema.go:87-89`), and read transactions need no journal. The distinct messages separate a broken fixture from the behavior under test. L106-108 use it once before startup as a sanity check.

The call (L109-115). `runServer` with the invalid address; the comment at L109-110 repeats that the address prevents a listener if startup wrongly advances. Inside: `lockDatabase` succeeds (the file exists and is writable); `store.Open` succeeds (reads only); `store.CheckWritable` (`main.go:88`, `writable.go:17`) executes `PRAGMA main.user_version = 3`. SQLite dirties the header page even though the value is unchanged (`writable.go:13`), so it begins a write transaction and tries to create the journal, which fails on the `0555` directory. `runServer` wraps the error as `check database writeability` (`main.go:91`), and L113-115 require that text and reject an `AddrError`. `README.md:499-507` describes this check and its failure message.

What is left behind (L116-123). `lockDatabase` must succeed: the defer at `main.go:70-74` released ownership, as `README.md:507` promises ("the database closes and its ownership lock is released"). Then `readHistory` must equal `expected`. In the `unfinished history` subtest the run is still `running`, not `interrupted`, which proves `MarkUnfinishedRunsInterrupted` (`main.go:96`) never ran: the write check at `main.go:88` comes first. In `empty history` the list is still empty, and the schema and marker are intact because `readHistory`'s `store.Open` recognized the file. If the two stages were swapped, the operator would see a cleanup error and go looking at run history when the real problem is a volume mounted read-only.

## Check yourself

1. In `TestStartsRunsAtOccurrencesAndSkipsMissedOnes`, L124 calls `nextWait` and L128 immediately asserts `NextRun` is 10:10, with no sleep in between. Why can the test be sure the map is already updated?

<details><summary>Answer</summary>
Because of the order inside <code>loop</code>. After the tick, the loop calls <code>start</code> (<code>scheduler.go:125</code>), computes the next occurrence (<code>:134-139</code>), writes it to <code>s.next</code> under the mutex (<code>:140-142</code>), and only then goes back to the top of the <code>for</code> and calls <code>s.clock.After</code> (<code>:119</code>). The fake <code>After</code> is what sends on <code>clock.waits</code> (<code>scheduler_test.go:53</code>), and <code>nextWait</code> receives from that channel. A channel receive completes after the matching send, and the send happens after the map write, so when <code>nextWait</code> returns, <code>NextRun</code> already answers 10:10. The comment at L65-66 states this: the wait request doubles as a join on the previous start.
</details>

2. `fireAt` (L58-63) sets `c.now` before sending on `request.fire`. Describe what could go wrong in the host-sleep step (L134-142) if the two statements were swapped.

<details><summary>Answer</summary>
The loop goroutine wakes on the send, calls <code>start</code>, and then reads <code>s.clock.Now()</code> at <code>scheduler.go:135</code>. If the test goroutine had not yet stored 10:23, <code>Now</code> would still return 10:05, the value stored by the previous <code>fireAt</code> at L120. The guard at <code>scheduler.go:136-138</code> would clamp <code>from</code> up to the 10:10 occurrence, so <code>Next(10:10)</code> would be 10:15 instead of 10:25, <code>NextRun</code> would report 10:15, and the wait at <code>:119</code> would be 10:15 minus whatever <code>Now</code> returned by then: ten minutes if still 10:05, minus eight minutes if 10:23 had landed. L137 or L140 would fail, but only on the runs where the loop goroutine won the race. The mutex prevents a data race, not a logic race; the statement order is what prevents the logic race.
</details>

3. In the `failed cleanup prevents startup` subtest of `TestRunServerReconcilesHistoryBeforeListening`, the `UPDATE run_steps` statement runs successfully before the trigger aborts the `UPDATE runs` statement. Why does L177 still find the step with status `running`?

<details><summary>Answer</summary>
<code>MarkUnfinishedRunsInterrupted</code> does both updates inside one transaction opened at <code>run_interruptions.go:16</code> with <code>defer tx.Rollback()</code> at <code>:20</code>. When the second statement fails, the function returns an error at <code>:33-34</code> without reaching <code>tx.Commit()</code> at <code>:40</code>, so the deferred rollback discards the step change too. That is the rule at <code>AGENTS.md:103</code>, "Preserve atomic run/step snapshots". The store-level version of this proof is <code>TestMarkUnfinishedRunsInterruptedRollsBackStepChanges</code> at <code>internal/store/run_interruptions_test.go:75</code>; the server-level test adds that the failure also stops startup and releases the lock.
</details>

4. `TestDatabaseLockExcludesAliasesAndAllowsOtherDatabases` proves exclusion with two `lockDatabase` calls in one process. Why does that work, and what can it not prove that `TestDatabaseLockReleasedAfterProcessExit` must?

<details><summary>Answer</summary>
A <code>flock</code> lock belongs to the open file description created by each <code>OpenFile</code> call (<code>database_lock.go:47-51</code>), not to the process. Two opens of the same <code>.lock</code> file, even in one process, are two descriptions, so the second <code>LOCK_EX|LOCK_NB</code> fails with <code>EWOULDBLOCK</code> and becomes <code>errDatabaseInUse</code> (<code>:53-54</code>). What a single process cannot show is that the kernel drops the lock when the owner dies without calling <code>Close</code>, because the test process never dies. The child-process test kills the child with <code>SIGKILL</code>, so no deferred <code>Close</code> runs (<code>database_lock_test.go:142-144</code>), and then takes the lock (<code>:148-151</code>). That is the guarantee in the doc comment at <code>database_lock.go:17</code> and in <code>README.md:100-101</code>.
</details>

5. `checks_test.go` calls `runner.Close()` at L100 and also has `defer runner.Close()` at L79. Why the explicit call, and what two rules does its position satisfy?

<details><summary>Answer</summary>
<code>Runner.Close</code> ends with <code>wg.Wait()</code> (<code>runner.go:190</code>), which returns only after the run goroutine has exited. The executor closure appended to <code>executed</code> on that goroutine (L65), and the test reads <code>executed</code> at L158; without a join between them, <code>go test -race</code> reports a data race, and the comment at L100 says so. The position also puts the runner's shutdown before <code>db.Close()</code> at L101, which is <code>AGENTS.md:96</code>, "Stop the runner before closing SQLite", the same order <code>runServer</code> arranges with defers at <code>main.go:80-84</code> and <code>:115</code>. The deferred call at L79 is then a no-op that only protects a <code>t.Fatal</code> exit before L100.
</details>

6. Why does `TestRunServerRejectsUnwritableJournalDirectoryBeforeCleanup` create `history.db.lock` by hand (L76) before making the directory read-only?

<details><summary>Answer</summary>
<code>lockDatabase</code> opens the lock file with <code>os.O_CREATE</code> (<code>database_lock.go:47</code>). Creating a file in a <code>0555</code> directory fails with "permission denied", so without the precreated file <code>runServer</code> would stop at <code>main.go:66-68</code> with <code>lock database ... open database lock file</code>. The test would then be checking the wrong stage, and L113 would fail with a message that has nothing to do with writeability. Opening an <em>existing</em> file needs only permission on the file itself, which <code>0600</code> grants, so startup gets past the lock and past <code>store.Open</code> and fails at exactly <code>store.CheckWritable</code> (<code>main.go:88-91</code>), which is the comment at L74-75: "isolate that failure".
</details>
