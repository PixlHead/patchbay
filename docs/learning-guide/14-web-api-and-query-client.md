# 14. Talking to the API: types, request helper, and query defaults

Files: [web/src/api.ts](../../web/src/api.ts), [web/src/queryClient.ts](../../web/src/queryClient.ts)

Revision: commit 1c4786e

## Role in the system

`api.ts` is the frontend's picture of the Go API. It holds six type aliases that copy the JSON shapes the Go server writes (`Workflow`, `WorkflowStep`, `WorkflowSchedule`, `CheckOutput`, `StepRun`, `Run`) and one function, `request`, that performs every HTTP call the browser makes. Nothing else under `web/src` calls `fetch`; `api.ts:66` is the only call site. The types exist only at compile time. TypeScript erases them, so their job is to let `tsc` catch a component that reads a field the server never sends, and to let Playwright fixtures be checked against the same shapes (`web/tests/tcp.spec.ts:80`, `web/tests/workflows.spec.ts:279`). The code map in `AGENTS.md:54` names this file "Explicit TypeScript API types and request helper", and the first comment in the file says why they are hand-written: "Keep them explicit until the API is large enough to justify code generation" (`api.ts:2`).

On the path from a click to a saved run, `request` is the border between the browser and Go. The Run button calls `startRun` (`web/src/pages/WorkflowsPage.tsx:91-94`), which calls `startMutation.mutate`, whose `mutationFn` calls `request<Run>` with `POST` and `Content-Type: application/json` (`WorkflowsPage.tsx:56-59`). `request` turns that into `fetch('/api/workflows/<id>/runs')` (`api.ts:66`). In development Vite forwards `/api` to the Go server (`web/vite.config.ts:11`); in production the Go server serves the page and the API from one port. The Go handler at `internal/httpapi/api.go:50` checks the content type, calls `runner.Start` (`api.go:65`), which saves the run before accepting it, and answers `202` with the run as JSON (`api.go:83-84`). `request` parses that body (`api.ts:78`), the mutation's `onSuccess` puts the run into the cache (`WorkflowsPage.tsx:60-67`), and from then on the page learns about progress by calling `request<Run[]>('/runs')` once a second (`WorkflowsPage.tsx:47-51`), which reads SQLite (`api.go:89-101`).

`queryClient.ts` creates the one `QueryClient` the whole app shares. A `QueryClient` owns the cache of server data and the rules for fetching it. This file sets three rules, each a one-line policy decision for a monitoring dashboard that talks to a server on the same machine: fail fast instead of retrying, keep polling in a hidden tab, and ignore the browser's idea of being offline. `AGENTS.md:56` summarizes the file as "no retries, background polling, loopback-safe network mode". The client is created once at module scope and handed to React in `web/src/main.tsx:11`, so the cache lives outside any component and survives moving between pages (`README.md:219-221`).

## Concepts you need

- **ES modules and `import type`.** A file that uses `export` is a module; another file reaches its names with `import`. TypeScript's `import type` imports a name that exists only for type checking and is removed from the built JavaScript. This project turns on `verbatimModuleSyntax` (`web/tsconfig.json:11`), which makes `import type` mandatory for type-only imports, so every consumer of the aliases in `api.ts` writes `import type { Run } from '../api'`. [MDN: JavaScript modules](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules), [TypeScript: verbatimModuleSyntax](https://www.typescriptlang.org/tsconfig/#verbatimModuleSyntax)
- **Type aliases and object types.** `type Run = { id: string; ... }` gives a name to an object shape. The checker then verifies that every value you call a `Run` has those fields with those types. Aliases cost nothing at runtime; they are instructions to the compiler, not code the browser runs. [TypeScript handbook: Object types](https://www.typescriptlang.org/docs/handbook/2/objects.html)
- **Literal types and unions.** `'queued' | 'running'` is a type whose only values are those exact strings. A union lists the alternatives a value may take. Comparing a literal union to a string that is not in the list is a compile error, which is how a typo in a status check gets caught. [TypeScript handbook: Literal types](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#literal-types)
- **Discriminated unions and narrowing.** When each member of a union carries a field with a different literal value (here `type: 'http.check'` versus `type: 'tcp.check'`), one `if` on that field tells the checker which member you hold, and the other member's fields become available. The field is called the discriminant. [TypeScript handbook: Discriminated unions](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#discriminated-unions)
- **Intersection types.** `A & B` is a type with all the fields of `A` and all the fields of `B`. `api.ts` uses it to put the shared fields of a step or a result in front of a union of the type-specific fields. [TypeScript handbook: Intersection types](https://www.typescriptlang.org/docs/handbook/2/objects.html#intersection-types)
- **Optional properties.** `nextRunAt?: string` means the key may be missing; reading it gives `string | undefined`. Each `?` in `api.ts` corresponds to a Go field tagged `omitempty` or `omitzero`, which `encoding/json` leaves out of the JSON when the value is empty. [TypeScript handbook: Optional properties](https://www.typescriptlang.org/docs/handbook/2/objects.html#optional-properties), [Go: encoding/json](https://pkg.go.dev/encoding/json#Marshal)
- **Generics.** `request<T>` is a function with a type parameter. The caller writes `request<Run[]>(...)` and the return type becomes `Promise<Run[]>`. The function body does not know or check what `T` is; it only promises the compiler that the parsed body has that shape. [TypeScript handbook: Generics](https://www.typescriptlang.org/docs/handbook/2/generics.html)
- **Type assertions.** `value as T` tells the compiler to treat `value` as a `T` without any runtime check. It is the escape hatch used where data comes from outside the program, such as a parsed JSON body. If the server sends something else, the mismatch shows up later as `undefined` fields, not as an error at the assertion. [TypeScript handbook: Type assertions](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions)
- **Promises, `async`, and `await`.** An `async` function returns a Promise, an object that will hold a value later. `await` pauses the function until a Promise settles, then gives its value or throws its error. A `throw` inside an `async` function rejects the returned Promise, which is how `request` reports failures to TanStack Query. [MDN: async function](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function)
- **`fetch`, `Response`, and `RequestInit`.** `fetch(url, init)` sends an HTTP request and resolves with a `Response` once the headers arrive. The `init` object carries the method, headers, and an abort signal. `fetch` rejects only when no response arrives at all (network failure or abort); a `404` or `500` resolves normally with `response.ok === false`. A relative URL such as `/api/runs` is sent to the same origin as the page. [MDN: fetch](https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch), [MDN: Response.ok](https://developer.mozilla.org/en-US/docs/Web/API/Response/ok)
- **Optional chaining and nullish coalescing.** `a?.b` evaluates to `undefined` instead of throwing when `a` is `null` or `undefined`. `x ?? y` gives `y` only when `x` is `null` or `undefined`, unlike `||`, which also replaces `0`, `''`, and `false`. [MDN: Optional chaining](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Optional_chaining), [MDN: Nullish coalescing](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Nullish_coalescing)
- **`Error` and `throw`.** `new Error(message)` builds an error object with a `message` string. Throwing it inside an `async` function rejects the Promise, and whoever awaits it can read `error.message`. The page's `errorMessage` helper reads exactly that field (`web/src/format.ts:19-21`). [MDN: Error](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Error)
- **`AbortSignal`.** An `AbortSignal` is a flag that a request can watch. Passing it to `fetch` lets the owner cancel the request later, at which point `fetch` rejects with an `AbortError`. TanStack Query hands each query function a signal and aborts it when the query is no longer wanted. [MDN: AbortSignal](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal), [TanStack Query: Query cancellation](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation)
- **React hooks and context.** A hook is a function such as `useQuery` that a component calls during render to subscribe to something. Context is how a value placed high in the tree (`QueryClientProvider` in `main.tsx:11`) becomes readable by any hook below it without passing it through props. `useQuery` and `useQueryClient` find the client this way. [React: Hooks](https://react.dev/reference/react/hooks), [React: Passing data deeply with context](https://react.dev/learn/passing-data-deeply-with-context)
- **TanStack Query: `QueryClient` and `defaultOptions`.** The client owns a cache keyed by query keys such as `['runs']` and runs the fetch, retry, and refetch logic. `defaultOptions` sets values that every `useQuery` and `useMutation` call inherits unless the call overrides them. The library's defaults are tuned for a public web app: three retries, no refetch while hidden, no fetching after the browser fires an `offline` event. [TanStack Query: QueryClient](https://tanstack.com/query/latest/docs/reference/QueryClient), [TanStack Query: Important defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)
- **TanStack Query: retries.** A failed query is retried three times by default with delays of about one, two, and four seconds before the error reaches the component. `retry: false` reports the first failure at once. [TanStack Query: Query retries](https://tanstack.com/query/latest/docs/framework/react/guides/query-retries)
- **TanStack Query: network mode.** The default mode `'online'` pauses queries and mutations while the library's `onlineManager` says the browser is offline. In version 5 that manager starts as online and changes only on the window's `offline` and `online` events; it never reads `navigator.onLine`. The mode `'always'` ignores that signal and always calls the query function. [TanStack Query: Network mode](https://tanstack.com/query/latest/docs/framework/react/guides/network-mode)
- **TanStack Query: `useQuery` options.** `refetchInterval` polls on a timer; `refetchIntervalInBackground` decides whether the timer keeps firing while the tab is hidden. The result object exposes `data`, `error`, `isPending`, and more. [TanStack Query: useQuery](https://tanstack.com/query/latest/docs/framework/react/reference/useQuery)
- **Vite dev server proxy.** In development the page is served by Vite on port 5173 while the Go API listens on 8080. A proxy rule forwards every request whose path starts with `/api` to Go, so the browser sees one origin. [Vite: server.proxy](https://vite.dev/config/server-options#server-proxy)

### web/src/api.ts

**L1–L2** — The file's only comment states the design: these types "mirror internal/workflow and internal/engine in Go" and stay hand-written "until the API is large enough to justify code generation". The mirror runs in one direction. Go's struct tags decide the JSON key names (`internal/workflow/workflow.go:21-26`, `internal/engine/runner.go:25-45`) and TypeScript copies them. There is no generator and no shared schema file, which follows `AGENTS.md:6-7`, "Prefer explicit code over a framework or an abstraction added for a possible future feature", and the rule to "update examples and relevant UI/API types together" (`AGENTS.md:131-132`). The cost is discipline: whoever changes a Go tag must come here too, and the only automated check is the Playwright fixtures that `tsc` compares against these aliases.

**L65–L65** — The signature of `request`. `T` is the shape the caller claims for the response body; the three callers pass `Workflow[]` (`WorkflowsPage.tsx:44`), `Run[]` (`WorkflowsPage.tsx:49`), and `Run` (`WorkflowsPage.tsx:56`). `path` is the route without the `/api` prefix. `init?: RequestInit` is passed through to `fetch` unchanged, so a caller can add a method and headers (`WorkflowsPage.tsx:57-58`) or the abort `signal` that TanStack Query provides (`WorkflowsPage.tsx:44, 49`). `async` makes the function return a `Promise<T>` and allows `await` inside.

**L66–L66** — The one `fetch` in the frontend. The URL is relative, so the browser sends it to the page's own origin. In development that is Vite on port 5173, which forwards `/api` to Go on 8080 (`vite.config.ts:11`, `README.md:64-65`); in production it is the Go server, which routes `/api` paths to handlers (`api.go:34-121`) and everything else to the built files (`api.go:122-134`). Because the request stays same-origin, no CORS setup is needed, and the `Host` that reaches Go is a loopback name either way: in production it is the one the page was loaded from, and in development Vite's string proxy rule expands to `changeOrigin: true`, so Go sees the proxy's target, `127.0.0.1:8080`. Both pass the host guard (`internal/httpapi/host_guard.go:41-42`, `README.md:109-113`). Prefixing `/api` here, once, means callers never repeat it and Vite's proxy has one prefix to match. `await` suspends until the response headers arrive. `fetch` rejects only for a network failure or an abort; those rejections leave this function as they are, so a severed connection surfaces as the browser's own error (Chrome says "Failed to fetch").

**L67–L67** — Decide whether the body is JSON by looking at `Content-Type`. The Go writer sets exactly `application/json` (`api.go:152`); `includes` also accepts `application/json; charset=utf-8` from another server or proxy. `headers.get` returns `null` when the header is missing, so `?.includes` yields `undefined` and `?? false` turns that into a plain boolean. This line exists because the function must not call `response.json()` on an HTML or text body; doing so throws a parse error whose message would be useless to the person reading the banner.

**L68–L68** — `response.ok` is true only for statuses 200 through 299, so the `202 Accepted` from a run start (`api.go:84`) passes. This check is necessary because `fetch` does not reject on HTTP errors. Without it, a `409` body such as `{"error":"this workflow is already queued or running..."}` would be returned as if it were a `Run`, the page would read `run.id` as `undefined`, and the real message would never be shown.

**L69–L72** — A JSON error body. Every error the Go server writes has the shape `{"error": message}`: `writeError` (`api.go:160-162`) is used by every handler and by the host guard (`host_guard.go:45`). The statuses are `400`, `404`, `409`, `415`, `429`, `500`, and `503` from `api.go:54-120` and `403` from the guard. The body is read as `{ error?: string }` and the message becomes the thrown `Error`; `?? Request failed (...)` covers a JSON error from some other server that lacks the key. The server writes these messages for people, for example `runner.go:18` and `api.go:78`, so they can go straight into the banner: the `409` case travels from `startMutation.error` (`WorkflowsPage.tsx:76`) through `errorMessage` (`format.ts:20`) to the `ErrorBanner` at `WorkflowsPage.tsx:119`, and `workflows.spec.ts:114-125` checks that text. If the body claims to be JSON but is not, `response.json()` rejects with a `SyntaxError`, which also propagates; the function makes no attempt to hide that.

**L73–L73** — A non-JSON error. No Patchbay handler produces one for an `/api` path, since even the catch-all at `api.go:119-121` writes JSON. So this branch means the request reached something else: Vite's proxy when the Go process is down, which answers `502` with an empty `text/plain` body, or a reverse proxy's HTML error page. The message names the status and the likely cause, "Check that the Go server is running", which is the first thing to check in `make api` plus `make web` development (`README.md:60-65`).

**L74–L74** — Closes the `if (!response.ok)` block.

**L75–L77** — A successful status with a non-JSON body. This happens when `/api/...` is served by the wrong thing, such as a static server that answers every path with `index.html`. Without this check, `response.json()` on L78 would throw a parse error with a message like "Unexpected token '<'". The fixed message points at the real problem instead.

**L78–L78** — Parse the body and assert it is a `T`. There is no runtime validation; the Go server is the trusted side, and `AGENTS.md:131` keeps "backend validation authoritative". A mismatch between a Go tag and an alias above is not caught here; it appears later as an `undefined` field in a component. The project's protection against that is `tsc` checking the Playwright fixtures: `tsconfig.json:14` includes `tests`, and the fixtures at `tcp.spec.ts:80` and `workflows.spec.ts:279, 304` are declared as `Run`, so a field renamed in `api.ts` without updating the fixtures fails `npm --prefix web run typecheck`.

**L2–L2** — Blank line.

**L3–L3** — `export const queryClient = new QueryClient({` creates the single client at module scope. The module is evaluated once, when `main.tsx:5` imports it, so there is exactly one client and one cache for the whole page. `main.tsx:11` places it in a `QueryClientProvider`; `useQuery` (`WorkflowsPage.tsx:42, 47`), `useMutation` (`WorkflowsPage.tsx:54`), and `useQueryClient` (`WorkflowsPage.tsx:35`) find it through context. The cache lives in this object, not in any component, which is why the workflow and run lists are still there after a visit to the canvas page (`README.md:219-221`).

**L4–L5** — `defaultOptions.queries` holds settings every `useQuery` call inherits. A call can override any of them; `WorkflowsPage.tsx:45, 50` add only `refetchInterval: 1000` and keep the rest. Putting the three rules here, rather than repeating them on each query, means a future query gets the same behavior without anyone remembering to copy it.

**L6–L7** — `retry: false`, with the comment "The connection banner must appear on the first failed poll, not after retries." The library's default is three retries with delays of about one, two, and four seconds, so a dead server would be reported roughly seven seconds after the first failed poll. The page already retries by itself: both queries refetch every second (`WorkflowsPage.tsx:40-41, 45, 50`), and that interval keeps running while a query is in its error state, which is what the banner's text "Retrying automatically" means (`WorkflowsPage.tsx:117`). Library retries would only delay the moment `workflowsQuery.error` is set (`WorkflowsPage.tsx:73`), and with it the banner, the header's Disconnected dot (`WorkflowsPage.tsx:102`, `web/src/components/AppHeader.tsx:43-44`), and the disabled Run button (`WorkflowsPage.tsx:178`). `workflows.spec.ts:67-69` aborts every `/api` request and expects the banner and the disabled button at once.

**L8–L9** — `refetchIntervalInBackground: true`, with the comment "Monitoring keeps polling while the tab is hidden." By default the library stops interval refetches while the window is not focused. For a dashboard that someone leaves open in a background tab, that would mean stale lists and a false "Local workspace" label when they come back, until the next poll. Keeping the timer running costs two small requests per second to a server on the same machine, which is cheap. Stop and think about what the opposite default protects: a public site paying for API calls, which Patchbay is not.

**L10–L11** — `networkMode: 'always'`, with the comment "The loopback server stays reachable when the browser reports itself offline." The default mode `'online'` asks the library's `onlineManager` whether the browser is online and, when it says no, parks each query in `fetchStatus: 'paused'` without calling the query function. In version 5 that manager starts as online and flips only on the window's `offline` and `online` events; it never reads `navigator.onLine`. Patchbay's server is on `127.0.0.1` (`README.md:60`, `README.md:109`), which works with Wi-Fi off, and the whole application is meant to keep working without internet (`README.md:40`, `docs/roadmap.md:18`). Under the default, a page left open when the laptop's radio goes off would silently stop polling with no banner, its lists frozen, until the browser fires `online` again; and if the first fetch had not finished yet, `isPending` would stay true and the page would show "Connecting to your workspace…" (`WorkflowsPage.tsx:120-124`) for as long as the query stays paused. `'always'` makes the query function run, and `request` then reports what actually happened.

**L12–L12** — Closes `queries`.

**L13–L15** — `mutations: { networkMode: 'always' }` applies the same rule to `useMutation`. The only mutation is the run start (`WorkflowsPage.tsx:54-68`). Under the default mode, clicking Run while the browser thought it was offline would leave the mutation paused with `isPending` true: the button would read "Starting…" (`WorkflowsPage.tsx:184`) and stay disabled, with no request sent and no error shown. No `retry` is set here because mutations default to zero retries, and a start must never be repeated automatically: the server already refuses a second start of a busy workflow (`runner.go:18`).

**L16–L17** — Close `defaultOptions` and the constructor call.

## State and rendering

`api.ts` holds no state. Its types are erased at build time, and `request` keeps nothing between calls; every call is a fresh `fetch`. The state in this chapter lives in the `QueryClient` created at `queryClient.ts:3`, which is module scope: created once, shared by every component, and alive until the page is unloaded.

Inside that client, the server data lives in a cache keyed by query key. The page registers two entries, `['workflows']` and `['runs']` (`WorkflowsPage.tsx:43, 48`), whose values are the arrays `request` returned. Three things trigger a fetch of each entry: mounting the page, the one-second interval (`WorkflowsPage.tsx:45, 50`), and the library's remaining defaults, which refetch when the window regains focus and when the browser fires an `online` event. Because `retry` is off and the interval is on, a failure never pauses anything; the next tick simply tries again. A refetch that returns the same JSON does not re-render the page: the library compares the new result structurally with the cached one and keeps the old object when they match, so `workflowsQuery.data` is the same reference and React sees no change.

The data flows from the response to the screen in three steps. `request` parses the body (`api.ts:78`) and resolves the Promise the query function returned. The client stores the value and notifies the `useQuery` subscriptions, so `WorkflowsPage` re-renders and reads `workflowsQuery.data` and `runsQuery.data` (`WorkflowsPage.tsx:70-71`). The page then derives everything else without further state: the selected workflow, its history filtered by `workflowId` (`WorkflowsPage.tsx:79-82`), and the props it hands to `Sidebar`, `StepList`, `ExecutionHistory`, and `RunDetails`, which only format what they are given (`format.ts`). The run start is the one write into the cache from the page: `onSuccess` calls `queryClient.setQueryData(['runs'], ...)` to put the new run first (`WorkflowsPage.tsx:62-65`), the runs subscription re-renders, and the next poll replaces the whole array with the server's order. The replacement is safe because the server saved the run before answering `202` (`AGENTS.md:83`), so the polled list already contains it.

Errors reach the user along two separate tracks. A query failure, which is any rejection from `request` during a poll, sets `error` on that query while `data` keeps the last good list. `WorkflowsPage.tsx:73-74` picks the first such error, `errorMessage` extracts `error.message` (`format.ts:19-21`), and the page renders an `ErrorBanner` with "Retrying automatically." appended (`WorkflowsPage.tsx:116-118`), marks the header disconnected (`WorkflowsPage.tsx:102`), and disables the Run button (`WorkflowsPage.tsx:178`). When a later poll succeeds, `error` clears and all three revert (`workflows.spec.ts:73-74`). A mutation failure, which is a rejection from the `POST`, sets `startMutation.error`; the page shows it in a second banner without the retry text (`WorkflowsPage.tsx:76, 119`) and clears it with `startMutation.reset()` when the user picks another workflow (`WorkflowsPage.tsx:88`). Neither track throws during render, because no query sets `throwOnError`, so the router's error page (`web/src/router.tsx:55`) is reserved for genuine rendering bugs.

Two more places hold state that this chapter only touches. The open view is a URL search parameter (`?view=`) owned by TanStack Router, not by the query client (`router.tsx:26-32`). And the selected run id is component state in `WorkflowsPage` (`WorkflowsPage.tsx:36`). When the page unmounts, for example on a visit to `/canvas`, its two queries lose their last subscriber: the interval stops, any in-flight `fetch` is aborted through the `signal` passed at `WorkflowsPage.tsx:44, 49`, and the cached arrays stay in the client for the library's default five minutes. Returning to the page renders the cached lists immediately and starts polling again.

3. The Go server is running on `127.0.0.1:8080`, the page is open with its lists loaded, and the laptop's Wi-Fi is switched off, so the browser fires `offline`. <details><summary>Answer</summary>With the default <code>'online'</code> mode the <code>offline</code> event sets the library's <code>onlineManager</code> to offline, so the next interval tick parks both queries in <code>fetchStatus: 'paused'</code> without calling <code>request</code>; <code>error</code> is never set, so there is no banner, the header keeps saying "Local workspace", and the lists freeze even though the server is reachable on loopback, until the browser fires <code>online</code>. (A fresh load in that state would behave normally: the manager starts as online and only the events change it.) <details><summary>Answer</summary>The <code>QueryClient</code> from <code>queryClient.ts:3</code> owns it; the page only reads it through <code>useQuery</code> and writes it once through <code>setQueryData</code>. Duplication within the optimistic write is prevented by the <code>filter</code> on <code>item.id</code> at <code>WorkflowsPage.tsx:64</code>. The next poll replaces the whole array with the server's list, and that list contains the new run because the runner saved it before <code>Start</code> returned and the handler answered <code>202</code> (<code>AGENTS.md:83</code>, <code>api.go:65, 84</code>). So the entry converges on the server's order rather than drifting.</details>

5. A result saved before TCP support arrives as `{"healthy":true,"url":"...","expectedStatus":204,"statusCode":204,"durationMs":12,"reason":"..."}` with no `type`. Which member of `CheckOutput` does it satisfy, how does `outputPresentation` decide, and why is `type` optional on only one member?

<details><summary>Answer</summary>It satisfies the HTTP member at <code>api.ts:32-38</code>, where <code>type?</code> may be absent; the TCP member at <code>api.ts:39</code> requires <code>type: 'tcp.check'</code>. <code>outputPresentation</code> tests <code>output.type === 'tcp.check'</code> at <code>format.ts:73</code>; <code>undefined</code> fails that test, so the HTTP branch at <code>format.ts:82-87</code> runs. The asymmetry mirrors the Go rule "An absent Type means HTTP" (<code>workflow.go:47-48</code>, <code>AGENTS.md:125-126</code>): old HTTP rows were written without a type and are never rewritten, while TCP results have always identified themselves (<code>tcp.go:29</code>). Today the HTTP executor still writes no type (<code>http.go:39</code>), so every HTTP result takes this path.</details>

6. `request` accepts an `init` object but never looks inside it. Trace what the `signal` in `{ signal }` at `WorkflowsPage.tsx:44` does, who aborts it, and what the page shows afterward.

<details><summary>Answer</summary><code>request</code> passes <code>init</code> straight to <code>fetch</code> at <code>api.ts:66</code>, so the signal is attached to the HTTP request. TanStack Query created the signal for this query function call and aborts it when the query is no longer wanted, most often when <code>WorkflowsPage</code> unmounts on a visit to <code>/canvas</code> and the last subscriber goes away. <code>fetch</code> then rejects with an <code>AbortError</code>, which the library recognizes and discards rather than recording as an error, so no banner appears and the cached arrays stay as they were. <code>api.ts</code> needs no code for this; forwarding <code>init</code> is enough.</details>
